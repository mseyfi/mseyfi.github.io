1. The warehouse analogy: why model weights are only the beginning

Training stores more than a model's forward-pass weights. During backward propagation the system needs gradients. AdamW also keeps exponential moving estimates of each parameter's gradient and squared gradient. A mixed-precision configuration may maintain full-precision master parameters. Activations saved during forward are needed later for gradients; their size depends on batch, sequence length, hidden size, layer implementation and activation-checkpoint strategy.

Analogy: a laboratory with four ledgers. The parameters are the current recipe. Gradients are proposed changes to the recipe. AdamW's first and second moments are two separate ledgers that remember the history of those suggestions. Saved activations are the intermediate measurements needed to reconstruct how the recipe generated its result. Training memory must accommodate the recipe, both moment ledgers, proposed changes and intermediate measurements.
Limit of the analogy: Tensors are not conceptual records; they have explicit dtypes, layouts, shard ownership and temporary all-gather copies. Real optimizers may maintain different precision or state representations. The 18 bytes/parameter example below is a particular configuration, not a universal formula.

2. Start with the bytes: parameters, gradients and Adam moments

Suppose each parameter uses 2 bytes for the forward weight, 4 bytes for an FP32 master copy, 4 bytes for an FP32 gradient buffer, and 4 bytes for each of Adam's two moment estimates. Our explicitly defined model of memory is

\[\underbrace{M_{\mathrm{state}}}_{\mathrm{bytes}}=P(2_{\mathrm{weight}}+4_{\mathrm{master}}+4_{\mathrm{gradient}}+4_{m}+4_{v})=18P\]

For \(P=7\times 10^9\) parameters, the theoretical optimizer/model state alone occupies 126 billion bytes, roughly 117.3 GiB. This does not include activations, temporary buffers, CUDA runtime memory, optimizer kernel workspaces, fragmentation, sequence-specific caches or replicated shards. Some BF16 training strategies use different master-weight and gradient representations; the exact memory should always be measured.

How does FSDP change this?

Full-shard FSDP or ZeRO Stage 3 distributes persistent parameters, gradients and optimizer states across \(D\) ranks. An idealized lower bound per rank is \(18P/D\) bytes for the above state model, but the actual peak can be substantially higher because each rank all-gathers the current module's parameters, uses temporary buffers and stores activations. FSDP2 uses device meshes and DTensor abstractions; its exact API and kernel costs should be studied separately in the distributed-training track.

3. Gradient accumulation is not keeping K entire batches in memory

For equal-sized microbatches with mean losses \(\mathcal L_1,\ldots,\mathcal L_K\), the average batch gradient is

\[\nabla_\theta\frac{1}{K}\sum_{i=1}^{K}\mathcal L_i=\sum_{i=1}^{K}\frac{1}{K}\nabla_\theta\mathcal L_i.\]

PyTorch's gradient buffers accumulate unless you zero them. If each microbatch loss is divided by K, calling loss.backward() K times gives the same gradient as one large batch under ideal deterministic conditions and equally weighted samples. For variable-length sequences, tokens and per-example losses, you may need token-count weighting rather than a simple mean of microbatch means.

Analogy: adding up votes before changing a policy. Each microbatch contributes a vote (gradient) on how to change the model. Instead of revising the policy after every vote, we accumulate K scaled votes, then update the parameter once. The vote sum is stored; we do not keep all K meetings active simultaneously.
Important limit: Gradient accumulation does not reproduce large-batch BatchNorm statistics or all stochastic effects. Microbatch-specific dropout, batch-dependent objectives and uneven weighting can make it differ from a true full batch.

Example gradients: \(g_i=[0.8,-0.4,0.2,1.0,-0.6,0.4,\ldots]\). Each selected gradient is divided by K. The toy uses SGD with learning rate 0.1 so the arithmetic is visible; a real AdamW update has moment estimates and weight decay.

Ready

The optimizer step occurs only after K microbatches. This reduces activation memory relative to one giant simultaneous batch, but requires K forward/backward computations and can incur more kernel launch overhead. Effective global batch size for equal microbatches is

\[B_{\text{effective}}=B_{\text{micro}}\times K\times D_{\text{data-parallel}}.\]

Changing K alters effective batch size only if you keep other factors fixed. If you increase K while decreasing microbatch size, the global batch can stay constant.

4. Activation checkpointing: trade extra compute for memory

Autograd generally needs intermediate forward activations to compute gradients during backward. Checkpointing intentionally does not retain selected intermediate activations. Instead, it runs the relevant forward segment again during backward to reconstruct them. The saved state is smaller, but the GPU does extra work.

Analogy: recalculating a spreadsheet. Instead of storing every intermediate cell in memory, save a few input checkpoints and recalculate intermediate values when they are needed. The tradeoff is extra arithmetic.

The optimal checkpoint granularity is workload dependent: full layer checkpoints, selective activation checkpointing, memory-efficient attention and compiler decisions interact. Do not assume a fixed 50% memory reduction or a fixed speed penalty for all architectures.

5. Runnable PyTorch: accumulation + BF16 + optional checkpoint

This small CPU/GPU-compatible example demonstrates explicit microbatch loss scaling and the exact optimizer-step boundary. On a CUDA GPU, BF16 autocast is enabled; CPU uses FP32. The model is deliberately small so you can run it without a GPU.

import torch, contextlib
from torch import nn

device = "cuda" if torch.cuda.is_available() else "cpu"
torch.manual_seed(42)
model = nn.Sequential(
    nn.Linear(64, 128), nn.GELU(), nn.Linear(128, 1)
).to(device)
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
K, microbatch, updates = 4, 2, 3
opt.zero_grad(set_to_none=True)

for step in range(updates):
    total_loss = 0.0
    for i in range(K):
        x = torch.randn(microbatch, 64, device=device)
        y = torch.randn(microbatch, 1, device=device)
        ctx = (torch.autocast("cuda", dtype=torch.bfloat16)
               if device == "cuda" else contextlib.nullcontext())
        with ctx:
            pred = model(x)
            raw_loss = ((pred.float() - y) ** 2).mean()
        (raw_loss / K).backward()
        total_loss += raw_loss.item() / K
    opt.step()  # exactly once per K backward calls
    opt.zero_grad(set_to_none=True)
    print(step, "mean microbatch loss", total_loss)

6. Review questions and source notes

Why doesn't gradient accumulation multiply parameter memory by K?

Each microbatch runs sequentially, and its temporary activations can be released after backward. Gradient tensors are added into existing gradient buffers rather than creating a separate copy for each microbatch.

Does AdamW require exactly 18 bytes per parameter?

No. 18 is the sum in a declared BF16-forward / FP32-master / FP32-gradient / FP32-moment configuration. Other optimizers, native low-precision gradients, compressed optimizers and sharding modify the count.

If microbatch=2, K=4, data-parallel ranks=8, what is effective batch size?

\(2\times4\times8=64\) sequences, assuming equal batches and standard gradient synchronization.

When can accumulation differ from a full batch?

For batch-dependent operations, data ordering, stochastic components, uneven batch losses or different treatment of tokens/examples. Gradient synchronization scheduling and numerical rounding may also differ.
