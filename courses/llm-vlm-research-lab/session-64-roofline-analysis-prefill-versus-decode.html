Roofline Analysis: Prefill versus Decode

Why do GPUs with tremendous compute power still produce LLM tokens slowly? We will connect a simple warehouse analogy to real bandwidth equations, a roofline model, tensor shapes, KV-cache memory and PyTorch profiling.

1. The problem: why decoding is not just a smaller prefill

In a decoder-only Transformer, processing a prompt and generating a response both execute the same model layers. But the shapes of the work are very different. During prefill, many prompt tokens are processed in parallel. During decode, the model usually produces only one new token per sequence per step, using attention keys and values saved from earlier tokens. One phase often uses compute units efficiently, while the other often spends time moving model weights and KV data through memory.

Analogy: a warehouse that ships books. Prefill resembles loading hundreds of orders onto a conveyor belt. Workers bring out a reference manual once and use its instructions for many orders. Decode resembles handling a single new order, but workers may still have to fetch the same manual repeatedly. The manual represents model weights; moving it represents HBM traffic. Batching many customers lets several token computations reuse weights.
Where the analogy breaks: GPUs do not literally load a complete model from storage for each token; weights reside in GPU HBM, some may be cached, and execution consists of fused tensor kernels. A real decode step also streams the growing attention KV cache. The analogy describes memory traffic relative to arithmetic, not exact physical movements.

Two costs matter separately: FLOPs (how much arithmetic) and bytes transferred (how much data moves). A system can be slow even with idle arithmetic units when it cannot feed those units quickly enough.

3. Roofline model: arithmetic intensity is the key

The arithmetic intensity (AI) of a kernel is FLOPs per byte transferred from the limiting memory level. The basic roofline ceiling is

\[\text{Attainable FLOP/s} \le \min(F_{\text{peak}},\, BW_{\mathrm{HBM}}\cdot AI)\]

For a large linear weight matrix, if one single token requires about \(2P\) floating-point operations and reads approximately \(P b\) weight bytes, then for batch \(B\) with ideal weight reuse:

\[AI_{\text{decode,weight-only}}\approx\frac{2BP}{Pb}=\frac{2B}{b}\quad\left[\frac{\text{FLOP}}{\text{byte}}\right]\]

Here \(P\) is the number of parameters used in these linear operations, \(b\) is bytes per weight, and \(B\) is the number of sequences decoding a token together. This is a simplified upper-bound reasoning tool, not a measured end-to-end LLM kernel intensity. It neglects activation, KV-cache, cache hierarchy, dequantization, launch, and other costs.

Prefill has a different shape

For a linear layer in prefill, \(\mathbf X\in\mathbb R^{(BL)\times K}\) multiplies \(\mathbf W\in\mathbb R^{K\times N}\). If many input rows share the same weights, a tile can perform much more arithmetic per weight byte than the single-token matrix-vector case. The simple weight-only ratio grows approximately with the number of rows \(BL\), before saturating because other memory traffic and compute limits dominate.

Prefill also includes quadratic causal attention interactions. FlashAttention reduces the I/O burden of that computation by tiling Q/K/V in fast on-chip memory and avoiding materializing the full \(L\times L\) attention probability matrix in HBM. It does not make attention mathematically linear in \(L\).

4. KV cache: the second memory bottleneck

The KV cache is a per-layer collection of earlier keys and values. For each new generated token, attention reads the relevant past keys and values, then appends the new ones. Grouped-Query Attention (GQA) reduces the number of stored K/V heads while maintaining more query heads.

\[M_{\text{KV}}=\underbrace{2}_{K,V}\cdot B\cdot L\cdot N_{\text{layers}}\cdot H_{\text{kv}}\cdot d_h\cdot b_{\text{kv}}\]

Every factor is explicit: number of sequences \(B\), cached tokens per sequence \(L\), layers, KV heads, head dimension, and bytes per cached value. The ideal tensor-storage estimate ignores paging metadata, allocator fragmentation, cache padding and potential per-layer variation.

Analogy: a notebook that grows with the conversation. KV caching lets you reuse old notes rather than rewriting them before every sentence. GQA shares some of those notes across multiple query heads. But even a shared notebook grows as more tokens arrive.
Limit: The cache is not a natural-language summary; it stores high-dimensional layer-dependent tensors. GQA reduces stored KV projections, not the causal sequence length or the need for attention over prior tokens.

5. PyTorch experiment: compare shapes and cost

Start with a small synthetic matrix multiplication that isolates weight reuse. Run it on the same GPU, synchronize before timing, and compare tokens-per-step across decode-style batch sizes and prefill-style row counts. This example measures one matrix multiply, not full model inference.

import torch, time
device = "cuda" if torch.cuda.is_available() else "cpu"
dtype = torch.bfloat16 if device == "cuda" else torch.float32
D = 2048
W = torch.randn(D, D, device=device, dtype=dtype)

def bench(rows, trials=30):
    x = torch.randn(rows, D, device=device, dtype=dtype)
    for _ in range(8):
        _ = x @ W
    if device == "cuda":
        torch.cuda.synchronize()
    t0 = time.perf_counter()
    for _ in range(trials):
        y = x @ W
    if device == "cuda":
        torch.cuda.synchronize()
    elapsed = (time.perf_counter() - t0) / trials
    return rows, elapsed * 1e3, (rows * 2 * D * D / elapsed) / 1e12

for rows in [1, 2, 8, 32, 128, 512]:
    print("rows, latency_ms, effective_TFLOP/s:", bench(rows))

As rows increase, GEMM kernels may achieve better utilization, but overall latency can also rise. More throughput does not imply lower latency for an individual request. For meaningful production comparisons, use vLLM or a similar server and report TTFT, ITL/TPOT, p50/p95 request latency, batch concurrency, prompt/output lengths and model accuracy.

Lab: falsify the simple roofline estimate

  • Fix one model, one GPU, warmup, dtype and exact prompt lengths.
  • Profile prefill and decode separately and record bytes moved, FLOPs (or proxy measurements), kernel utilization and GPU memory.
  • Vary the active sequence count; measure the point where aggregate throughput increases while tail latency becomes unacceptable.
  • Repeat for GQA and longer contexts to observe KV I/O growth; compare to the weight-only estimate.

6. Understanding check and spaced repetition

Why does increasing batch size increase decode arithmetic intensity?

The same weight matrices can be reused across more sequence rows. In the idealized weight-only model, the FLOP count grows with B but weight bytes do not grow proportionally during the batch, so AI scales as roughly 2B/b until other bottlenecks dominate.

Does FlashAttention reduce attention FLOPs from quadratic to linear?

No. Standard exact dense attention still has quadratic arithmetic complexity in the sequence length during prefill. FlashAttention reduces HBM reads/writes and intermediate storage by using on-chip tiling and an online softmax.

Does reducing K/V heads reduce the number of query heads?

Not necessarily. GQA shares key/value heads among multiple query heads. It primarily reduces KV projection and cache size without requiring fewer query heads.

Numerical example: 32 layers, B=1, L=4096, 8 KV heads, 128 dims, BF16. How large?

\(2\cdot1\cdot4096\cdot32\cdot8\cdot128\cdot2=536{,}870{,}912\) bytes = 512 MiB of ideal KV tensors.
