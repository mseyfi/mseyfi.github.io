    Visual token efficiency

    One image can become hundreds or thousands of tokens, and a short video can become tens of thousands. These visual tokens usually far outnumber the text tokens, so they decide most of the prefill time and the KV-cache memory of a VLM. This session counts that cost, then builds the main ways to cut it: token merging (ToMe), pruning by attention inside the language model (FastV), fixed-budget resamplers and dynamic token counts. It ends with how to measure the accuracy versus cost trade-off without fooling yourself.

    Time: 3 to 4 hours (reading 2 hours, exercises 1 to 2 hours)Level: Beginner to interview levelBefore this: Sessions 164 (ViT), 177 (anatomy of a VLM), 178 (connectors) and 180 (high resolution); session 80 (the KV cache) helps

    What you will learn

    • Why visual tokens dominate the cost of a VLM: token counts, prefill FLOPs and KV-cache memory for real models (LLaVA-1.5, LLaVA-NeXT, Qwen2-VL), and what video does to them
    • The three places to remove tokens: inside the vision encoder, in the connector, and inside the language model
    • Token merging (ToMe): bipartite soft matching on keys, size-weighted averages and proportional attention, with the token schedule and its FLOPs
    • Pruning by attention (FastV): rank image tokens by the attention they receive at layer K, drop R% of them, and the theoretical FLOPs ratio
    • Fixed-budget resamplers (Q-Former, Perceiver) versus dynamic token counts (AnyRes tiling, Qwen2-VL native resolution, Matryoshka tokens)
    • How to measure the trade-off honestly: wall-clock latency with FlashAttention, end-to-end time, random and pooling baselines at the same budget, and vision-centric benchmarks

    Why this matters

    Ask LLaVA-1.5 “What is in this picture?”. The question is about 10 text tokens. The picture is 576 tokens. The language model spends more than 90% of its prefill work on the image, and the image also fills more than 90% of the KV cache. For a video it is worse: 32 frames at 576 tokens each are 18,432 tokens, before the user has typed a word.

    A visual token is one vector that the language model reads in place of a piece of the image (one patch, or a merged group of patches). In session 177 we counted them with \(V = (H/P)(W/P)/r^2\). In session 180 we saw that reading documents and charts needs more of them: tiling and native resolution push one image to thousands of tokens. This session is the other side of the same coin. Visual tokens are expensive, many of them carry little information (sky, wall, white paper), and there are good ways to remove them.

    Interview tipCommon questions: “Why is a VLM slower than the same LLM on text?”, “How would you serve a video-LLM at 10× lower cost?”, “How does ToMe work?”, “What does FastV prune, and where?”, “Q-Former or MLP projector, and why?”. Strong answers start with a token count and a FLOPs or memory number, then name where in the model the tokens are removed.

    The ideas here are used in real systems. Fixed-budget resamplers (BLIP-2’s 32 queries, Flamingo’s and Idefics2’s 64 latents) were designed to cap the token count. Pixel shuffle (a 2 × 2 merge) is used in Qwen2-VL, InternVL, Idefics3 and SmolVLM (session 178). Training-free methods such as ToMe and FastV can be added to a model that is already trained. Long-video systems (session 206) depend on token compression to fit hours of video into a context window.

The main survey of this area is Jin et al. (2024), and the book chapter on video-language models (Noyan et al., chapter 9) shows the same problem for video.

    Where the cost goes

    Let a request have \(V\) visual tokens and \(T\) text tokens, so the language model reads \(n = V + T\) tokens in prefill. The visual share of the input is

    \[ f_{\text{vis}} = \frac{V}{V + T} \tag{183.1} \]

    With 576 visual tokens and 40 text tokens, \(f_{\text{vis}} = 93.5\%\). Two costs grow with \(n\).

    Prefill compute

    In prefill (the first forward pass over the whole prompt, session 78), every token passes through every layer. For one Llama-style layer with hidden width \(d\), MLP width \(m\) and a SwiGLU MLP (three weight matrices), the FLOPs are about

    \[ C(n) = \underbrace{2n\,(4d^2 + 3dm)}_{\text{weight matrices}} + \underbrace{4n^2 d}_{\text{attention scores and mixing}} \tag{183.2} \]
    Read the symbols
    \(n\)
    the number of tokens in the prompt (visual plus text)
    \(d\)
    the hidden width of the language model (4,096 for a 7B Llama)
    \(m\)
    the inner width of the MLP (11,008 for Llama 2 7B and Vicuna-7B)
    \(4d^2\)
    the four attention projections \(W_Q, W_K, W_V, W_O\), each \(d \times d\), one multiply-add each (2 FLOPs)
    \(3dm\)
    the three MLP matrices (gate, up, down)
    \(4n^2 d\)
    the score matrix \(QK^\top\) and the weighted sum with \(V\), each \(n^2 d\) multiply-adds (we ignore the causal mask, which halves this)

    The first term is linear in \(n\): every token costs the same. The second term is quadratic and only matters when \(n\) is large. Multiply by the number of layers \(L\) for the whole model. Each visual token costs exactly as much as a text token, so removing visual tokens is the most direct way to cut prefill.

    KV-cache memory

    After prefill, the model keeps the keys and values of every token in every layer (session 80). The memory is

    \[ M_{\text{KV}} = 2 \cdot L \cdot n_{\text{kv}} \cdot d_h \cdot b \cdot n \tag{183.3} \]
    Read the symbols
    \(2\)
    one key and one value per token per layer
    \(L\)
    the number of layers (32 for a 7B Llama)
    \(n_{\text{kv}}, d_h\)
    the number of key-value heads and their width; Vicuna-7B uses full multi-head attention, so \(n_{\text{kv}} d_h = 32 \times 128 = 4{,}096\)
    \(b\)
    bytes per number (2 for FP16 or BF16)

    Every decode step reads this whole cache from memory, so a larger cache also makes each generated token slower and leaves less room for other users in the batch.

    Worked example: LLaVA-1.5-7B, one image

    Tokens. 576 visual + 40 text = 616 tokens. Visual share: \(576/616 = 93.5\%\).

    Prefill. With \(d = 4096\), \(m = 11008\), \(L = 32\): \(32 \cdot C(616) = 8.18 \times 10^{12}\) FLOPs. The 40 text tokens alone would cost \(32 \cdot C(40) = 0.52 \times 10^{12}\). So the image adds \(93.7\%\) of the prefill work. At this length the quadratic attention term is only about 2.4% of \(C(n)\); the cost is almost all in the weight matrices, and so almost exactly proportional to the number of tokens.

    KV cache. \(2 \cdot 32 \cdot 4096 \cdot 2 = 524{,}288\) bytes = 0.5 MiB per token. The image costs \(576 \times 0.5 = 288\) MiB per request.

    Video. 32 frames at 576 tokens: 18,432 visual tokens, \(4.18 \times 10^{14}\) prefill FLOPs, and 9 GiB of KV cache for one request. Now the attention term is 43% of \(C(n)\): long inputs make the quadratic part matter.

    Use Figure 1 to try other models. All of them run through the same 7B language model shape here, so that only the token count changes.

    Watch outGrouped-query attention changes the KV numbers. Qwen2-VL-7B, for example, has 4 KV heads of width 128 and 28 layers, so it stores far less per token than Vicuna-7B. Always read \(n_{\text{kv}}\) from the model’s config.json before you compute memory.

    Three places to remove tokens

    A visual token passes through three parts of the model: the vision encoder, the connector, and the language model (session 177). You can remove tokens in any of them, and the choice decides what you save and what you risk.

    1. Inside the vision encoder. Merge or drop patch tokens between ViT layers. This saves encoder compute and, if the reduced set is passed on, also the language model’s work. Example: ToMe. The language model never sees the dropped tokens, and the reduction does not know the user’s question.
    2. In the connector. Map the \(N\) patch vectors to fewer tokens: pool or merge neighbors (pixel shuffle, 2 × 2 average pooling), or pull out a fixed number \(Q\) with learned queries (Q-Former, Perceiver resampler). This is usually part of the design and trained with the model. It also does not know the question (except InstructBLIP-style Q-Formers that also read the instruction).
    3. Inside the language model. Run the first few layers on all tokens, then drop visual tokens that the model is not using. Example: FastV. This can use the question, because by layer \(K\) the text tokens have already looked at the image. But the first \(K\) layers still pay full price, and the encoder is not made cheaper.
    AnalogyPacking for a trip. You can pack less at home (encoder), use a compression bag with a fixed size (resampler), or carry everything to the hotel and throw away what you did not use after the first day (pruning in the LLM). The last option knows best what you need, but you already paid to carry it on day one.

    There is a second axis: merge or prune. Pruning deletes a token and its information. Merging replaces several tokens by one average, so the information is blurred but not lost. Most methods are a mix: LLaVA-PruMerge, for example, keeps the tokens that the encoder’s class token attends to most, and merges the information of the pruned tokens into the kept ones, reaching about 14× fewer visual tokens on LLaVA-1.5 [Certain, from the paper’s abstract].

    Token merging (ToMe)

    Token merging (ToMe, Bolya et al., 2022) speeds up a trained ViT without retraining. In every block, between the attention and the MLP, it merges the \(r\) most similar pairs of tokens. After \(L\) layers, \(rL\) tokens are gone. The trick is to find similar pairs quickly: comparing all pairs, or clustering, would be too slow to do in every layer.

    Bipartite soft matching

    ToMe splits the current tokens into two sets by position: \(\mathcal{A}\) holds tokens 0, 2, 4, …; \(\mathcal{B}\) holds tokens 1, 3, 5, …. Then:

    \[ s_{ij} = \frac{\mathbf{k}_i^\top \mathbf{k}_j}{\lVert \mathbf{k}_i \rVert\,\lVert \mathbf{k}_j \rVert}, \quad i \in \mathcal{A},\ j \in \mathcal{B}; \qquad j^*(i) = \argmax_{j \in \mathcal{B}} s_{ij} \tag{183.4} \]
    Read the symbols
    \(\mathbf{k}_i\)
    the key vector of token \(i\) in this layer’s attention, averaged over heads; keys already summarize “what this token contains”, so no extra computation is needed
    \(s_{ij}\)
    cosine similarity between token \(i\) in \(\mathcal{A}\) and token \(j\) in \(\mathcal{B}\)
    \(j^*(i)\)
    the best partner in \(\mathcal{B}\) for token \(i\)

    Each \(\mathcal{A}\) token keeps only one edge, to its best partner. ToMe sorts these edges by similarity and merges the top \(r\) of them; the other \(\mathcal{A}\) tokens stay. Because every edge goes from \(\mathcal{A}\) to \(\mathcal{B}\), no chains form, and the whole step is a matrix product plus a sort. At most \(|\mathcal{A}|\), about half the tokens, can be merged in one layer. The class token is protected (it is never merged).

    Size-weighted merging and proportional attention

    When token \(a\) merges into token \(b\), the result is the average weighted by size, where the size \(s\) counts how many original patches a token stands for:

    \[ \mathbf{x}_{b} \leftarrow \frac{s_a \mathbf{x}_a + s_b \mathbf{x}_b}{s_a + s_b}, \qquad s_b \leftarrow s_a + s_b \tag{183.5} \]

    A merged token is now one vector in place of several. In attention it would get the weight of one token, which is less than the original group had. ToMe fixes this with proportional attention: add \(\log s\) to the attention logits of each key,

    \[ \text{Attn}(Q, K, V) = \softmax\!\left( \frac{Q K^\top}{\sqrt{d_h}} + \log \mathbf{s} \right) V \tag{183.6} \]

    Why \(\log s\)? Because \(e^{z + \log s} = s\, e^{z}\): a key that stands for \(s\) identical tokens gets exactly \(s\) times the weight, as if the copies were still there. The code below checks this: merging two identical tokens with proportional attention gives the same output as not merging, to about \(10^{-7}\).

    AnalogyA town meeting where neighbors who agree send one speaker. The speaker says what they all think (the average), and when there is a vote, the speaker holds up as many hands as the people sent (proportional attention).
    Algorithm 1: one ToMe step inside a ViT block
    1. input: tokens \(\mathbf{x}_1..\mathbf{x}_N\), sizes \(s_1..s_N\), merge count \(r\)
    2. run attention with the \(\log \mathbf{s}\) bias (183.6); keep the keys \(\mathbf{k}\), averaged over heads
    3. \(\mathcal{A} \leftarrow\) even positions, \(\mathcal{B} \leftarrow\) odd positions; protect the class token
    4. for each \(i \in \mathcal{A}\): \(j^*(i) \leftarrow \argmax_j s_{ij}\), \(\;e_i \leftarrow \max_j s_{ij}\) // formula 183.4
    5. \(r \leftarrow \min(r, |\mathcal{A}|)\); merge the \(r\) tokens of \(\mathcal{A}\) with the largest \(e_i\) into their \(j^*(i)\) // formula 183.5
    6. concatenate the unmerged \(\mathcal{A}\) tokens and all \(\mathcal{B}\) tokens: \(N - r\) tokens
    7. run the MLP on the \(N - r\) tokens

    The token schedule

    With a constant \(r\), layer \(\ell\) ends with \(N_\ell = N_0 - \ell r\) tokens (until half of the tokens can no longer be merged). The total cost is the sum of the per-layer costs:

    \[ N_\ell = N_0 - \ell\, r, \qquad \text{cost} \approx \sum_{\ell=1}^{L} C_{\text{ViT}}(N_{\ell-1}, N_\ell) \tag{183.7} \]

    Here \(C_{\text{ViT}}\) is a ViT layer’s cost with attention on \(N_{\ell-1}\) tokens and the MLP on \(N_\ell\) tokens (merging happens in between).

    Worked example: ToMe in the CLIP encoder of LLaVA-1.5

    CLIP ViT-L/14 at 336 px has \(N_0 = 577\) tokens (576 patches and a class token), 24 layers, width 1,024 and MLP width 4,096. With \(r = 16\) per layer, the last layer ends with \(577 - 24 \times 16 = 193\) tokens. Counting each layer as \(2N_{\ell-1} \cdot 4d^2 + 4N_{\ell-1}^2 d\) for attention and \(2N_\ell \cdot 2dm\) for the MLP, the encoder needs 64.9% of its original FLOPs (about 1.54× fewer). With \(r = 8\): 385 tokens and 82.1%.

    The bigger saving is downstream: if the 192 merged patch tokens are passed to the language model in place of 576, its prefill work falls to about one third. But the language model was trained on a regular 24 × 24 grid, and merged tokens no longer sit on a grid, so without fine-tuning accuracy can drop more than in the encoder alone [Likely].

    ToMe reported about 2× the throughput of ViT-L at 512 px and ViT-H at 518 px off the shelf with a 0.2–0.3% accuracy drop on ImageNet, and 2.2× for ViT-L on video, where it merges similar tokens across frames too [Certain, from the paper]. Video is where merging shines: a static background repeated over 16 frames is exactly the kind of redundancy it removes.

    Pruning by attention inside the language model (FastV)

    FastV (Chen et al., 2024) looked at the attention maps of LLaVA-1.5 and found something surprising. In the first two layers, image tokens receive a fair share of attention. After layer 2, an average image token receives only about 0.21% of the attention that an average system-prompt token receives, even though image tokens were about 64% of the input tokens in their tests [Certain, from the paper]. In deep layers the model mostly ignores most image tokens. So why keep computing them?

    The rule

    Run the language model normally up to layer \(K\). At layer \(K\), compute how much attention each image token receives, averaged over heads and over all query tokens:

    \[ a_j = \frac{1}{H\, n} \sum_{h=1}^{H} \sum_{i=1}^{n} A^{(K)}_{h,i,j}, \qquad j \in \text{image tokens} \tag{183.8} \]
    Read the symbols
    \(A^{(K)}_{h,i,j}\)
    the attention probability from query token \(i\) to key token \(j\) in head \(h\) of layer \(K\)
    \(H\), \(n\)
    the number of heads and the number of tokens
    \(a_j\)
    the importance score of image token \(j\): how much the rest of the sequence looks at it

    Keep the top \((1 - R)\) fraction of image tokens by \(a_j\), drop the rest, and run layers \(K+1\) to \(L\) on the shorter sequence. Text tokens are never dropped. The dropped tokens also leave the KV cache of those layers, so decoding gets cheaper too. No training is needed.

    Algorithm 2: FastV prefill
    1. input: sequence of \(n = n_{\text{sys}} + V + T\) tokens, filter layer \(K\), drop ratio \(R\)
    2. run layers \(1..K\) on all \(n\) tokens; at layer \(K\), also return the attention probabilities
    3. \(a_j \leftarrow\) mean over heads and queries of the attention to image token \(j\) // formula 183.8
    4. keep \(\lceil (1-R)\,V \rceil\) image tokens with the largest \(a_j\), in their original order, with their original position ids
    5. run layers \(K+1..L\) on \(\hat n = n_{\text{sys}} + (1-R)V + T\) tokens
    6. decode as usual; layers after \(K\) keep only \(\hat n\) entries in the KV cache

    What it saves, in theory

    \[ \rho = \frac{K\, C(n) + (L - K)\, C(\hat n)}{L\, C(n)}, \qquad \hat n = n - R\,V \tag{183.9} \]

    \(\rho\) is the fraction of prefill FLOPs that remains, with \(C\) from formula (183.2). The KV cache shrinks by the same kind of ratio, with \(n\) in place of \(C(n)\).

    Worked example: FastV with K = 2, R = 50%

    LLaVA-1.5-7B, 576 image tokens and 40 other tokens, so \(n = 616\) and \(\hat n = 40 + 288 = 328\). With \(L = 32\): \(\rho = (2\,C(616) + 30\,C(328)) / (32\,C(616)) = 0.556\). Prefill FLOPs fall by about 44%. The KV cache falls to \((2 \cdot 616 + 30 \cdot 328)/(32 \cdot 616) = 56.2\%\).

    For LLaVA-1.5-13B (\(d = 5120\), \(m = 13824\), \(L = 40\)) the same setting gives \(\rho = 0.551\). The paper reports about 45% fewer FLOPs for this model with no loss on its benchmark average (73.6 before and after on captioning, A-OKVQA and MMMU) [Certain, from the paper]. Its own FLOPs formula is slightly different, so do not expect every digit to match.

    With \(R = 75\%\): \(\hat n = 184\) and \(\rho = 0.338\). Moving the filter to \(K = 16\) with \(R = 50\%\) keeps \(\rho = 0.763\): late pruning saves little, because half the layers already paid full price.

    The practical catches

    • It needs the attention matrix. Fast kernels such as FlashAttention never write the \(n \times n\) attention probabilities to memory (session 124). FastV needs them at layer \(K\), so that layer must run a slower path or recompute the scores. Wen et al. (2025) report that FastV, SparseVLM and MustDrop do not support FlashAttention, and that SparseVLM had only 2.8% more FLOPs than FastV but 26.8% more latency [Certain, from the paper].
    • Position bias. Endo et al. (2024) found that pruning after a shallow layer keeps tokens concentrated at the bottom of the image, and traced it to the long-distance decay of RoPE [Certain, from the paper]. They also found that early-layer pruning keeps good scores on many benchmarks but fails on localization tasks.
    • The first \(K\) layers and the encoder still pay in full. With small \(K\) this is a small part of prefill, but the vision encoder cost is untouched.
    • It interacts with batching. Different requests keep different tokens, which is fine for a serving engine with paged KV memory, but harder for code that assumes fixed shapes.
    Interview tip“Where would you prune visual tokens?” A good answer compares three places: before the LLM (cheap, compatible with every kernel, blind to the question), at a shallow LLM layer (question-aware, needs attention scores, has position bias), and in the connector with training (best accuracy per token, but needs a training run).

    Fixed budgets and dynamic token counts

    Pruning and merging change a model after the fact. The connector decides the token count by design (session 178). There are two families.

    A fixed-budget resampler uses \(Q\) learned query vectors that cross-attend to all patch features and return exactly \(Q\) tokens, whatever the image size. BLIP-2’s Q-Former uses 32 queries; Flamingo’s Perceiver resampler and Idefics2 use 64 latents [Certain]. The cost is constant and easy to plan for, and a video of 64 frames at 32 tokens each is only 2,048 tokens. The risk is the other side of the same fact: a dense page of text needs more than 32 or 64 vectors, so fine detail is lost.

    A dynamic token count grows with the image. LLaVA-NeXT picks the best grid of 336 px tiles for the image’s aspect ratio and adds a low-resolution overview, so a 672 × 672 grid costs \(5 \times 576 = 2{,}880\) tokens before padding is removed [Certain, from the config and the tiling rule]. Qwen2-VL resizes the image to multiples of 28 pixels inside a pixel budget and makes one token per 28 × 28 area (14 px patches, then a 2 × 2 merge):

    \[ V_{\text{fixed}} = Q, \qquad V_{\text{Qwen2-VL}} = \frac{H'}{28} \cdot \frac{W'}{28}, \quad H' W' \in [\,3{,}136,\ 12{,}845{,}056\,] \text{ pixels} \tag{183.10} \]
    Read the symbols
    \(Q\)
    the number of learned queries of a resampler (32 or 64 in the models above)
    \(H', W'\)
    the image size after Qwen2-VL rounds each side to a multiple of 28 and scales it into the pixel budget
    \([3{,}136,\ 12{,}845{,}056]\)
    the default min_pixels and max_pixels in Qwen2-VL’s preprocessor config, which give between 4 and 16,384 tokens per image [Certain]

    A 1920 × 1080 frame becomes 1932 × 1092 and costs \(69 \times 39 = 2{,}691\) tokens. A 4K frame costs 10,549. The user can lower max_pixels to cap the cost: with \(1280 \times 28 \times 28\) pixels, the same 4K frame costs 1,222 tokens. A dynamic count spends tokens where there are pixels, which is right for documents. But the cost of a request is no longer known before you see the image, which matters for serving and for batching (session 84).

    A middle path is nested tokens. Matryoshka Multimodal Models (M3, Cai et al., 2024) train one model to work with several pooled versions of LLaVA’s 24 × 24 grid, from coarse to fine, so the user can choose the number of tokens per request. They report that COCO-style benchmarks need only about 9 tokens to reach accuracy close to using all 576 [Certain, from the paper], which says as much about those benchmarks as about the method.

    Measuring the trade-off honestly

    A token-reduction paper usually shows one number: “we keep 25% of the tokens and lose only 1 point”. That number can be true and still misleading. The pitfalls are the same as in any efficiency work (session 82), plus some special to vision.

    Measure time, not only FLOPs

    FLOPs are a proxy. The real goal is latency (time to first token, time per output token) and throughput (requests per second on a fixed GPU budget). Only the prefill part shrinks with visual tokens; the vision encoder, the decode steps and any overhead of the method do not shrink, or shrink less. This is Amdahl’s law:

    \[ \text{speedup} = \frac{1}{\,e + p\,\rho + (1 - e - p)\,\delta + o\,} \tag{183.11} \]
    Read the symbols
    \(e, p\)
    the fractions of the original end-to-end time spent in the vision encoder and in the LLM prefill; the rest, \(1 - e - p\), is decoding
    \(\rho\)
    the fraction of prefill time that remains after reduction (formula 183.9, if prefill is compute-bound)
    \(\delta\)
    the fraction of decode time that remains (a smaller KV cache helps a little)
    \(o\)
    the extra time the method adds (scoring, sorting, a non-flash attention layer), as a fraction of the original time

    Compare at equal budgets, against simple baselines

    The most important control is boring: at the same number of kept tokens, compare against random dropping and plain average pooling. Wen et al. (2025) did this on LLaVA-1.5-7B across several benchmarks. As a percentage of the full 576-token model’s average score [Certain, Table 1 of the paper]:

    MethodKeep 144 tokens (−75%)Keep 64 tokens (−88.9%)
    Random dropping95.0%89.1%
    2D average pooling96.4%87.6%
    FastV89.8%78.2%
    SparseVLM93.5%87.3%

    At these aggressive budgets, the attention-based methods were not better than the two simple baselines. This does not mean attention scores are useless; FastV was designed for \(R = 50\%\), where it loses little. It means a method must beat random and pooling at the same budget before its scoring rule gets credit. Random dropping and pooling also have a hidden advantage: they cover the whole image evenly, which a position-biased score does not.

    Choose benchmarks that need the pixels

    Many benchmark questions can be answered from a blurry thumbnail, or even without the image. Token reduction looks free on those. Test where detail matters: text reading (TextVQA, DocVQA, ChartQA), counting, and localization (referring expressions, grounding boxes), and for video, questions about short events and exact timestamps (session 192). Endo et al. found exactly this split: early pruning kept good scores on many benchmarks but failed on localization [Certain, from the paper].

    A checklist

    Algorithm 3: an honest token-reduction evaluation
    1. fix the model, the prompt template, the decoding settings and the hardware; use the fastest attention kernel for the baseline too
    2. for each budget \(V' \in \{V, V/2, V/4, V/9\}\): run your method, random dropping and average pooling // equal tokens
    3. score on a detail-heavy set (text reading, counting, grounding, short video events) and a general set
    4. measure time to first token, time per output token, peak memory and throughput at your real batch size
    5. plot accuracy against measured time (a Pareto curve), not against kept tokens alone
    6. report the encoder time and the method’s overhead separately // formula 183.11

    Code: ToMe, proportional attention and FastV in PyTorch

    This file implements bipartite soft matching with sizes, checks proportional attention, runs the FastV selection rule on a causal attention map, computes the FLOPs ratio of formula (183.9), and builds the random and pooling baselines at equal budget. It runs on a CPU in under a second and is deterministic.

    import math, torch
import torch.nn.functional as F
torch.manual_seed(0)

# ---------- 1) ToMe: bipartite soft matching with sizes (formulas 183.4, 183.5) ----------
def tome_merge(x, k, size, r):
    """x: (N, D) tokens, k: (N, Dk) keys (mean over heads), size: (N, 1). Remove r tokens."""
    N = x.shape[0]
    r = min(r, N // 2)                                   # at most half can be merged
    kn = k / k.norm(dim=-1, keepdim=True)
    a, b = kn[0::2], kn[1::2]                            # alternate split into sets A and B
    scores = a @ b.T                                     # cosine similarity, (|A|, |B|)
    best, dst = scores.max(dim=-1)                       # best partner in B for each A token
    order = best.argsort(descending=True)
    src, keep_a = order[:r], order[r:]                   # the r most similar edges are merged
    xa, xb = x[0::2] * size[0::2], x[1::2] * size[1::2]  # weight by size before summing
    sa, sb = size[0::2], size[1::2]
    xb = xb.index_add(0, dst[src], xa[src]); sb = sb.index_add(0, dst[src], sa[src])
    kb = k[1::2]                                         # (keys are recomputed by the next layer)
    x_new = torch.cat([xa[keep_a], xb]) / torch.cat([sa[keep_a], sb])
    return x_new, torch.cat([k[0::2][keep_a], kb]), torch.cat([sa[keep_a], sb])

N, D = 576, 64                                           # a 24 x 24 grid of visual tokens
x = torch.randn(N, D); size = torch.ones(N, 1)
for layer in range(4):                                   # 4 layers, r = 64 each
    x, k, size = tome_merge(x, x, size, r=64)
    print(layer, x.shape[0], int(size.sum().item()))     # 512, 448, 384, 320 tokens; sizes always sum to 576

# ---------- 2) proportional attention (formula 183.6): a merged pair counts twice ----------
dh = 16
q = torch.randn(1, dh); keys = torch.randn(3, dh); vals = torch.randn(3, dh)
keys_dup = torch.cat([keys, keys[2:3]]); vals_dup = torch.cat([vals, vals[2:3]])   # token 2 appears twice
full = F.softmax(q @ keys_dup.T / math.sqrt(dh), -1) @ vals_dup
s = torch.tensor([1.0, 1.0, 2.0])                                                   # after merging: size 2
prop = F.softmax(q @ keys.T / math.sqrt(dh) + s.log(), -1) @ vals
print((full - prop).abs().max().item())                  # about 1e-7: identical output

# ---------- 3) FastV: rank image tokens by attention received at layer K (formula 183.8) ----------
def fastv_keep(attn, img_slice, R):
    """attn: (H, n, n) attention probabilities of layer K. Returns indices of image tokens to keep."""
    score = attn.mean(dim=0).mean(dim=0)[img_slice]      # average over heads and over all queries
    n_keep = round((1 - R) * score.numel())
    idx = score.topk(n_keep).indices.sort().values       # keep the original order
    return idx + img_slice.start

H, n_sys, V, T = 8, 35, 576, 40
n = n_sys + V + T
logits = torch.randn(H, n, n)
mask = torch.ones(n, n).tril().bool()
attn = logits.masked_fill(~mask, float("-inf")).softmax(-1)  # a causal attention map
keep = fastv_keep(attn, slice(n_sys, n_sys + V), R=0.5)
print(keep.numel())                                       # 288 image tokens survive after layer K

# ---------- 4) the theoretical FLOPs ratio (formula 183.9) for LLaVA-1.5-7B ----------
def layer_flops(n, d=4096, m=11008):                     # Llama layer with a SwiGLU FFN, formula 183.2
    return 2 * n * (4 * d * d + 3 * d * m) + 4 * n * n * d
def fastv_ratio(V, T, K, R, L=32):
    n, nh = V + T, T + round((1 - R) * V)
    return (K * layer_flops(n) + (L - K) * layer_flops(nh)) / (L * layer_flops(n))
print(round(fastv_ratio(576, 40, K=2, R=0.5), 3))         # 0.556: about 44% fewer prefill FLOPs

# ---------- 5) honest baselines at the same budget: random and 2x2 average pooling ----------
grid = torch.randn(24, 24, D)
g = torch.Generator().manual_seed(0)
rand_keep = torch.randperm(V, generator=g)[:144].sort().values
pooled = F.avg_pool2d(grid.permute(2, 0, 1), 2).permute(1, 2, 0).reshape(-1, D)
print(rand_keep.numel(), pooled.shape[0])                 # 144 and 144: compare methods at equal tokens

    In a real model, tome_merge runs inside every ViT block between attention and MLP, with the attention keys as the metric and the sizes passed to the next block’s attention as the \(\log \mathbf{s}\) bias. fastv_keep runs once, at layer \(K\) of the language model, and the kept indices are used to slice the hidden states, the position ids and the KV cache of the following layers. Keep the original position ids of the kept tokens: renumbering them would tell the model the image is smaller than it is.

    Common mistakes

    • Reporting only FLOPs or kept tokens. A method that breaks FlashAttention or sorts on the CPU can save FLOPs and lose time. Report time to first token and throughput on real hardware.
    • No random or pooling baseline. Without them you cannot tell whether your scoring rule helps or whether any reduction to that budget would do as well.
    • Testing only on easy benchmarks. If the questions can be answered from a thumbnail, every method looks lossless. Include text reading, counting and grounding.
    • Renumbering positions after pruning. Kept tokens must keep their original position ids (or M-RoPE coordinates); otherwise the model’s sense of where things are is wrong.
    • Merging without proportional attention. A merged token that stands for 10 patches then gets the attention weight of one, and the image is under-weighted.
    • Forgetting the KV cache. Pruning only the prefill hidden states but storing the full KV cache saves compute but not memory, and memory is what limits the batch size.
    • Ignoring GQA when estimating memory. Models with few KV heads store several times less per token; use the real config, formula (183.3).
    • Merging across time for tasks that need exact time. Temporal merging is great for classification and bad for “when did the goal happen?”.

    Interview questions

    Why is a VLM request often much more expensive than a text request of similar length in words?basic
    Because the image becomes many tokens: 576 for LLaVA-1.5, up to about 2,880 for LLaVA-NeXT tiling, and about 2,700 for a 1080p image in Qwen2-VL. Each visual token costs the same as a text token in every layer (formula 183.2) and in the KV cache (183.3). With a 40-token question, the image is over 90% of the prefill work and memory. Video multiplies this by the number of frames.
    Explain ToMe’s bipartite soft matching. Why not cluster the tokens?core
    Split the tokens into alternating sets A and B. For each A token, find its most similar B token by cosine similarity of the attention keys (averaged over heads). Sort these edges by similarity and merge the top r A tokens into their partners with a size-weighted average. It is one matrix product and one sort per layer, with no iterations, so it is almost as cheap as pruning. Clustering (k-means) or full pairwise matching would need iterations or sequential steps in every layer, which would eat the savings. The cost of the simplicity: at most half the tokens can merge per layer, and the match is greedy.
    What is proportional attention and why is it needed?core
    After merging, one token stands for \(s\) patches. Without a correction, softmax gives it the weight of one key. Adding \(\log s\) to its logits multiplies its unnormalized weight by \(s\), because \(e^{z+\log s} = s e^z\). If the merged patches were identical, the output is exactly the same as before merging. It keeps the attention distribution close to the original one, which matters when the model is used off the shelf.
    How does FastV choose tokens, and what does it save with K = 2, R = 50% on LLaVA-1.5-7B?core
    At layer K it averages, over heads and all query positions, the attention each image token receives, keeps the top half of the image tokens, and runs the remaining layers on the shorter sequence. With 576 image and 40 other tokens, the later 30 layers see 328 tokens instead of 616. By formula (183.9) the prefill FLOPs fall to 55.6% (about 44% saved), and the KV cache of those layers shrinks too. The paper reports about 45% fewer FLOPs on LLaVA-1.5-13B with no loss on its average score.
    Why do attention-based pruning scores tend to keep the bottom of the image?advanced
    Image tokens are placed in raster order (top-left first), and the text comes after them. RoPE makes attention scores decay with relative distance on average, so query tokens in the text attend more to the nearby, later image tokens, which are the bottom rows. In shallow layers, which focus on short distances, this effect is strong. A score that averages attention over queries therefore prefers the bottom of the image for reasons that have nothing to do with content. Fixes: compute the score without RoPE, mix in uniform spatial sampling, or prune later. Endo et al. (2024) documented this effect.
    Q-Former with 32 queries or an MLP projector with 576 tokens: how do you choose?core
    The resampler gives a fixed, small cost, which is great for many images, video and small models, and its cost is known before you see the input. But it compresses every image to 32 vectors, so dense text and small objects suffer, and it has its own training cost. The MLP keeps every patch: better detail and simpler training, but 18× more tokens. For documents choose many tokens (often with tiling); for long video or edge devices choose a small budget, or a middle path such as a 2 × 2 pixel-shuffle merge (144 tokens from 576).
    A paper shows its pruning method keeps 98% accuracy at 25% of the tokens. What do you check?advanced
    (1) Random dropping and average pooling at the same budget: Wen et al. found these reach 95.0% and 96.4% at 144 tokens on LLaVA-1.5-7B, above FastV’s 89.8%. (2) Whether the benchmarks need detail: add text reading, counting, grounding. (3) Measured latency and throughput with FlashAttention in the baseline, not only FLOPs. (4) End-to-end time including the vision encoder and decoding (formula 183.11). (5) Whether the KV cache really shrinks. (6) Whether the baseline is the same model with the same prompts and decoding.
    Halving the prefill FLOPs gave only a 1.2× faster request. Why?core
    Amdahl’s law (formula 183.11). Prefill is only part of the request time; the vision encoder and the decoding of the answer are not halved. With 10% encoder, 40% prefill and 50% decode, halving prefill gives \(1/(0.1 + 0.2 + 0.5) = 1.25\times\) at best, less with overhead. Also, at small batch sizes prefill may not be compute-bound, so fewer FLOPs do not mean proportionally less time.
    How would you cut the token cost of a 1-hour video QA system?advanced
    Combine several levels. Sample frames sparsely (for example 1 fps or less), and skip near-duplicate frames using cheap embeddings. Reduce tokens per frame: pooling or a resampler to tens of tokens. Merge across time where the scene is static (ToMe-style). Retrieve only the relevant segments for the question (Video-RAG) and give those segments more tokens. Keep timestamps for every kept token. Then measure on questions about short events, because those break first.
    Why can FastV not simply run with FlashAttention, and what can you do?advanced
    FlashAttention computes the softmax in tiles and never writes the full attention probability matrix to memory, so the per-key attention sums are not available. Options: run layer K with a standard attention implementation (slower for that layer), compute scores only from a few query rows (for example the last text tokens) in a cheap separate pass, or use a score that does not need attention (key norms, similarity to the text, uniform sampling). Report the real latency whichever you choose.
    Merge or prune: which is safer, and why?basic
    Merging is usually safer at the same token count, because the information of the removed tokens is averaged into a kept token instead of being deleted. Pruning is simpler and keeps kept tokens unchanged, which is good when the dropped tokens are truly background. Many methods do both: choose important tokens to keep, then merge the rest into them (LLaVA-PruMerge).

Default: the frame becomes 3836 × 2156, so \(137 \times 77 = 10{,}549\) tokens. With the lower cap it is scaled to 1316 × 728: \(47 \times 26 = 1{,}222\) tokens. 5. \(1/(0.7 + 0.15) = 1.18\times\). 6. Let token \(t\) with logit \(z_t\) and value \(\mathbf{v}_t\) appear \(s\) times. Its total weight in the softmax is \(s e^{z_t}/Z\), where \(Z = \sum_{j \ne t} e^{z_j} + s e^{z_t}\). With one copy and logit \(z_t + \log s\), the weight is \(e^{z_t + \log s}/Z' = s e^{z_t}/Z'\), with \(Z' = \sum_{j \ne t} e^{z_j} + s e^{z_t} = Z\). The weights of all tokens are the same, so the output \(\sum_j w_j \mathbf{v}_j\) is the same.

    Key takeaways

    • Visual tokens usually far outnumber text tokens (183.1); each costs as much as a text token in prefill (183.2) and in the KV cache (183.3). One LLaVA-1.5 image is 576 tokens and 288 MiB of KV cache; 32 frames are 9 GiB.
    • Tokens can be removed in the encoder, in the connector, or inside the LLM. Earlier is cheaper and simpler; later can use the question.
    • ToMe merges the \(r\) most similar pairs per layer with bipartite matching on keys (183.4), size-weighted averages (183.5) and proportional attention (183.6).
    • FastV ranks image tokens by the attention they receive at layer \(K\) (183.8) and drops \(R\%\); \(K = 2\), \(R = 50\%\) keeps about 55% of prefill FLOPs (183.9). It needs attention probabilities and has a position bias.
    • Resamplers fix the budget (32 or 64 tokens); AnyRes and native resolution make it grow with the image (183.10); nested tokens let the user choose.
    • Measure honestly: real latency (183.11), random and pooling baselines at equal budget, and benchmarks that need the pixels.

    Key formulas

    \[ C(n) = 2n(4d^2 + 3dm) + 4n^2 d, \qquad M_{\text{KV}} = 2 L\, n_{\text{kv}} d_h\, b\, n \]

    \[ \text{speedup} = \frac{1}{e + p\rho + (1 - e - p)\delta + o} \]
