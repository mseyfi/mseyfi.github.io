    Gradient accumulation and gradient checkpointing

    Two tricks let you train with a batch, or a model, that does not fit in GPU memory. Gradient accumulation runs many small batches and takes one optimizer step, so you get a large batch with the memory of a small one. Gradient checkpointing throws most activations away in the forward pass and recomputes them in the backward pass, so you trade about one extra forward pass for a large cut in activation memory.

    Time: 2.5 to 3.5 hours (reading 1.5 to 2 hours, exercises 1 to 1.5 hours)Level: Beginner to interview levelBefore this: Sessions 4, 25 and 38 (backprop and AdamW, counting FLOPs and memory, memory math for training)

    What you will learn

    • Why gradient accumulation gives the same gradient as one big batch, and how to compute the effective batch size in sequences and in tokens
    • How to scale the loss across micro-batches, and the token-count trap that silently changed the gradients of many fine-tuning runs in 2024
    • Where accumulation is not exactly the same as a big batch: normalization over the batch, data-parallel synchronization, numerics
    • Gradient (activation) checkpointing: keep only the block inputs, recompute the rest in the backward pass
    • The memory and compute trade-off: the square-root rule of Chen et al., and why one checkpoint per transformer block is usually best
    • Selective recomputation (Korthikanti et al.): recompute only the attention core, for a few percent of extra compute
    • How to use both in PyTorch and Hugging Face, and how to check that the gradients did not change

    Why this matters

    In session 38 we added up the bytes of one training step and saw that they often do not fit. Two parts of the bill grow with the work you do: the activations grow with the batch size and with the sequence length. This session gives you the two standard tools that attack exactly that part, without buying more GPUs.

    Gradient accumulation solves the batch problem. The recipe says “4 million tokens per step”, but your GPU can hold the activations of only 8,192 tokens. So you run many small batches, add up their gradients, and take one optimizer step at the end. Gradient checkpointing (also called activation checkpointing or activation recomputation) solves the depth and length problem. It keeps only a few activations during the forward pass and recomputes the others when the backward pass needs them. You pay with extra compute, about one more forward pass.

    Interview tipTypical questions: “Is gradient accumulation exactly the same as a bigger batch?”, “How do you scale the loss?”, “What does gradient checkpointing cost, in memory and in time?”, “What is selective recomputation?”. Each one has a short, exact answer below.

    Both tools are everywhere. Llama 2 was trained with a global batch of about 4 million tokens per step [Certain], far more than one GPU can hold, so the batch is split across GPUs and, when needed, across accumulation steps. Hugging Face Trainer has the flags gradient_accumulation_steps and gradient_checkpointing; Megatron-LM, DeepSpeed and PyTorch FSDP all support both. [Certain] And a small mistake in the first one, the token-count trap, changed the gradients of many fine-tuning runs until it was found and fixed in October 2024. [Certain]

    Gradient accumulation: one big batch, in pieces

    Recall from session 4 that the mini-batch gradient is an average of per-example gradients. A micro-batch is the batch that actually goes through the GPU in one forward and backward pass. The global batch (or effective batch) is the set of examples that together produce one optimizer step. Accumulation makes the global batch \(K\) times larger than the micro-batch:

    1. Run forward and backward on micro-batch 1. PyTorch adds the new gradient into each parameter’s .grad buffer.
    2. Do the same for micro-batches 2, 3, …, \(K\). Do not call optimizer.step() and do not zero the gradients in between.
    3. After micro-batch \(K\): clip, call optimizer.step(), then zero_grad().
    AnalogyYou want the average height of 1,000 people, but your room holds only 100. You measure ten groups of 100, write down each group’s total, and divide the sum of the totals by 1,000 at the end. You never needed a room for 1,000 people. The answer is the same.

    With data parallelism on \(N_{\text{dp}}\) GPUs (session 44), each GPU processes its own micro-batches and the gradients are averaged across GPUs before the step. So the effective batch is:

    \[ B_{\text{eff}} = b \cdot K \cdot N_{\text{dp}} \ \text{sequences}, \qquad T_{\text{eff}} = b \cdot K \cdot N_{\text{dp}} \cdot s \ \text{tokens} \tag{39.1} \]
    Read the symbols
    \(b\)
    micro-batch size: sequences per forward pass on one GPU
    \(K\)
    number of accumulation steps (micro-batches per optimizer step)
    \(N_{\text{dp}}\)
    number of data-parallel copies of the model (often the number of GPUs)
    \(s\)
    sequence length in tokens (for packed sequences, every token is real)

    Only \(b\) and \(s\) decide the activation memory on one GPU. \(K\) and \(N_{\text{dp}}\) change the batch the optimizer sees, not the memory. That is the whole point.

    Worked example: a 4-million-token batch on 64 GPUs

    Take the Llama 2 setting: sequences of \(s = 4{,}096\) tokens and about 4 million tokens per step. \(4{,}194{,}304 / 4{,}096 = 1{,}024\) sequences per step. Say you have 64 GPUs and each one fits a micro-batch of \(b = 2\) sequences. Then one round of all GPUs covers \(2 \times 64 = 128\) sequences, so you need \(K = 1{,}024 / 128 = 8\) accumulation steps. With 128 GPUs you would need \(K = 4\); with 512 GPUs and \(b = 2\), no accumulation at all.

    Why the gradient is exactly the same

    The gradient is a linear operation: the gradient of a sum is the sum of the gradients. Split a batch of \(B\) examples into \(K\) micro-batches \(\mathcal{B}_1, \dots, \mathcal{B}_K\) of equal size \(B/K\). Then

    \[ \nabla_\theta \frac{1}{B}\sum_{i=1}^{B} \ell_i \;=\; \sum_{k=1}^{K} \nabla_\theta \Big( \frac{1}{K} \cdot \underbrace{\frac{K}{B} \sum_{i \in \mathcal{B}_k} \ell_i}_{\text{mean loss of micro-batch } k} \Big) \tag{39.2} \]

    In words: if each micro-batch computes its mean loss, divide it by \(K\) before backward(). The .grad buffers then hold exactly the full-batch gradient after \(K\) micro-batches. Forget the \(1/K\) and the gradient is \(K\) times too large. With Adam this is partly hidden (Adam divides by \(\sqrt{\hat v}\), which also grows), but gradient clipping, the \(\varepsilon\) term and weight decay all see a different scale, so the run is not the run you designed.

    Figure 1 shows the gradient buffer of a tiny linear model filling up, micro-batch by micro-batch.

    What accumulation does not give you for free

    Formula (39.2) holds when the loss is a plain sum or average over examples. Three things can break it:

    • Normalization over the batch. BatchNorm computes a mean and variance over the micro-batch, so 8 micro-batches of 4 are not one batch of 32. Transformers use LayerNorm or RMSNorm, which work per token, so LLMs are safe. [Certain] Vision backbones with BatchNorm are not.
    • Losses that compare examples inside the batch. A contrastive loss like CLIP’s (session 166) scores every image against every text in the batch. Accumulation does not give you more negatives; you need tricks such as gradient caching instead. [Certain]
    • Different numbers of tokens per micro-batch. This is the most common one in LLM work, and it gets its own section next.

    Small differences also come from rounding (sums in a different order), from dropout masks (different random numbers), and from the data order. These are noise, not bias. [Certain]

    Scaling the loss: the token-count trap

    For language models the loss is an average over tokens, not over sequences. When the sequences are padded, only the real (non-padding) tokens count: their labels are real token ids, and the padding positions get the label −100, which cross_entropy ignores. The correct loss for one optimizer step is the sum over all real tokens in all \(K\) micro-batches, divided by their total number:

    \[ \mathcal{L}_{\text{step}} = \frac{1}{N_{\text{tot}}} \sum_{k=1}^{K} \sum_{t \in \mathcal{B}_k} \ell_t, \qquad N_{\text{tot}} = \sum_{k=1}^{K} n_k \tag{39.3} \]
    Read the symbols
    \(\ell_t\)
    the cross-entropy of one real token \(t\)
    \(n_k\)
    the number of real tokens in micro-batch \(k\)
    \(N_{\text{tot}}\)
    the number of real tokens in the whole optimizer step (on all GPUs)

    The natural code does something else. Each micro-batch calls cross_entropy(..., reduction="mean"), which divides by its own \(n_k\), and then the result is divided by \(K\):

    \[ \mathcal{L}_{\text{naive}} = \frac{1}{K} \sum_{k=1}^{K} \frac{1}{n_k} \sum_{t \in \mathcal{B}_k} \ell_t \quad\Rightarrow\quad \text{weight of one token in } \mathcal{B}_k = \frac{1}{K\, n_k} \tag{39.4} \]

    In the correct loss every token has weight \(1/N_{\text{tot}}\). In the naive loss, a token in a short micro-batch counts much more than a token in a long one. The two agree only when all \(n_k\) are equal, which is true for packed pretraining data and false for padded fine-tuning data with sequences of very different lengths.

    Worked example: one long and one short micro-batch

    Micro-batch A has 1,000 real tokens with mean loss 2.0. Micro-batch B has 10 real tokens with mean loss 5.0. The naive loss is \((2.0 + 5.0)/2 = 3.5\). The correct loss is \((1{,}000 \times 2.0 + 10 \times 5.0)/1{,}010 = 2{,}050/1{,}010 = 2.030\). The 10 tokens of B have half of the total weight in the naive loss (0.5) instead of \(10/1{,}010 = 0.0099\): each of them counts \(0.5/0.0099 = 50.5\) times too much. The gradient follows the same wrong weights.

    This is exactly the bug that Hugging Face described in its blog post “Fixing Gradient Accumulation” (October 16, 2024): the Trainer averaged the loss per micro-batch, so training with accumulation gave different (higher) losses than the same batch without it. The fix: compute the loss with reduction="sum" and divide by the number of real tokens in the whole accumulation step. [Certain] Explore it in Figure 2.

    The same trap across GPUs

    Data parallelism averages the gradients over the \(N_{\text{dp}}\) GPUs. If every GPU divides by its own token count, you get the same mean-of-means error, now across GPUs. The fix: before the backward passes, all-reduce (sum) the real-token count over all micro-batches and all GPUs to get \(N_{\text{tot}}\). Each GPU then uses \(\text{sum of its token losses} \times N_{\text{dp}} / N_{\text{tot}}\); the factor \(N_{\text{dp}}\) cancels the averaging that DDP does. [Certain for the arithmetic]

    Watch outLogging is affected too. If you log the average of the \(K\) micro-batch means, your loss curve is the naive loss even when your gradient is correct. Log \(\sum \ell_t / N_{\text{tot}}\).

    The cost of accumulation

    Accumulation adds no FLOPs: \(K\) micro-batches of size \(b\) cost the same as one batch of size \(Kb\) would. It costs time in another way: the \(K\) micro-batches run one after another, so the step takes \(K\) times longer, and small micro-batches can use the GPU less efficiently than large ones. With data parallelism, you should not all-reduce the gradients after every micro-batch, only after the last one. DDP’s no_sync() context manager skips the communication for the first \(K - 1\) micro-batches. [Certain] With ZeRO-2/3 or FSDP the gradients are sharded, so frameworks usually reduce after every micro-batch anyway, or keep an extra unsharded buffer. [Likely] Gradients are often accumulated in FP32 even when the backward pass runs in BF16, because adding many small BF16 numbers loses precision (session 37). [Likely]

    Algorithm 1: one optimizer step with gradient accumulation (token-correct)
    1. input: micro-batches \(\mathcal{B}_1, \dots, \mathcal{B}_K\) on each of \(N_{\text{dp}}\) GPUs, optimizer, clip value \(c\)
    2. \(N_{\text{tot}} \leftarrow \text{all\_reduce\_sum}\big(\sum_k n_k\big)\) // real tokens in the whole step, all GPUs
    3. for \(k = 1, \dots, K\) do
    4. \(S_k \leftarrow \sum_{t \in \mathcal{B}_k} \ell_t\) // forward, cross-entropy with reduction = sum
    5. backward of \(S_k \cdot N_{\text{dp}} / N_{\text{tot}}\), with gradient sync only if \(k = K\) // .grad adds up; formula (39.3)
    6. end for
    7. clip the global gradient norm to \(c\); optimizer.step(); scheduler.step(); zero the gradients
    8. log \(\sum_k S_k / N_{\text{tot}}\) (summed over GPUs) as the step loss

    Gradient checkpointing: forget now, recompute later

    Backpropagation needs values from the forward pass. For \(Y = XW\), the weight gradient is \(X^\top G\), so \(X\) must still be in memory when the backward pass reaches this layer (session 4, formula 4.4). Normally PyTorch saves every such tensor during the forward pass and frees it during the backward pass. The peak, just before the backward pass starts, holds the saved tensors of every layer. For a GPT-style block, Korthikanti et al. count them:

    \[ M_{\text{layer}} = s\,b\,d \left( 34 + \frac{5\,h\,s}{d} \right) \ \text{bytes (16-bit activations)} \tag{39.5} \]
    Read the symbols
    \(s, b, d, h\)
    sequence length, micro-batch size, model width, number of attention heads
    \(34\,sbd\)
    inputs of the linear layers, norms, GELU and dropout masks
    \(5\,h s^2 b\)
    the attention scores, softmax output and its dropout mask: the part that grows with \(s^2\)

    (This is formula 25.13 of session 25, written for one layer.) Gradient checkpointing keeps only a few tensors, the checkpoints, and drops the rest. In the backward pass, when a dropped tensor is needed, it runs the forward pass of that part again, starting from the nearest checkpoint. The usual choice for transformers is one checkpoint per block: keep only the block input, a tensor of \(s \times b \times d\) numbers (\(2sbd\) bytes in BF16).

    AnalogyYou hike a long trail and must later walk back the same way, reading every signpost in reverse order. You could photograph every signpost (a lot of storage). Or you photograph only one signpost per kilometer, and on the way back you walk each kilometer forward again from its photo to see the signposts in between. Less storage, more walking.

    With one checkpoint per block, the peak memory is the \(L\) stored block inputs plus the full activations of the one block that is being recomputed:

    \[ M_{\text{full ckpt}} \approx 2\,s\,b\,d\,L \;+\; M_{\text{layer}} \tag{39.6} \]

    Korthikanti et al. write the first term, \(2sbdL\), as the memory of “full activation recomputation”. [Certain] The second term is the working space of one block, which we add because it is also in memory at the peak.

    Worked example: a 7B-sized model at 4,096 tokens

    Take \(L = 32\), \(d = 4{,}096\), \(h = 32\), \(s = 4{,}096\), \(b = 1\) (the shape of Llama 2 7B and Llama 3 8B, with the GPT-style constant 34 as an approximation). Here \(sbd = 16{,}777{,}216\).

    No checkpointing: \(16{,}777{,}216 \times (34 + 5 \times 32) = 3.25\) GB per layer, 104.2 GB for 32 layers. Not storing the score matrices (FlashAttention, or selective recomputation): \(16{,}777{,}216 \times 34 = 0.57\) GB per layer, 18.3 GB in total. One checkpoint per block: \(2 \times 16{,}777{,}216 \times 32 = 1.07\) GB of block inputs, plus 0.57 GB for the block being recomputed: 1.64 GB. That is 63 times less than no checkpointing, and 11 times less than FlashAttention alone.

    Figure 3 runs the whole schedule on a small network of 8 layers, so you can watch memory rise and fall.

    How many checkpoints? The square-root rule

    Chen et al. (2016) asked how to place checkpoints in a chain of \(n\) layers. Put one checkpoint every \(c\) layers. Let \(I\) be the size of one checkpoint (a layer input) and \(A\) the full saved size of one layer. At the peak you hold \(n/c\) checkpoints and one rebuilt segment of \(c\) layers:

    \[ M(c) \approx \frac{n}{c}\, I + c\, A, \qquad c^{*} = \sqrt{\frac{n\, I}{A}}, \qquad M(c^{*}) = 2\sqrt{n\, I\, A} \tag{39.7} \]

    The first term falls with \(c\), the second grows; setting the derivative \(-nI/c^2 + A\) to zero gives \(c^*\). When \(I\) and \(A\) are similar (a chain of simple layers), \(c^* \approx \sqrt{n}\) and memory grows only as \(\sqrt{n}\) instead of \(n\). That is the result of Chen et al.: \(O(\sqrt{n})\) memory for the cost of one extra forward pass; they trained a 1,000-layer residual network with memory going from 48 GB to 7 GB, for about 30% more running time. [Certain]

    For a transformer block, the inside is much larger than the input. In units of \(sbd\) bytes with FlashAttention: \(I = 2\), \(A = 34\), \(n = 32\). Then \(c^* = \sqrt{32 \times 2 / 34} = 1.37\). Checking whole numbers: \(c = 1\) gives \(64 + 34 = 98\), \(c = 2\) gives \(32 + 68 = 100\), \(c = 4\) gives \(16 + 136 = 152\). So one checkpoint per block is the best choice, which is why every framework offers exactly that. [Certain for the arithmetic]

    The cost: about one extra forward pass

    Recomputation runs the forward pass of every checkpointed segment a second time. In FLOPs per token, training normally costs \(2N\) (forward) \(+ 4N\) (backward) \(= 6N\) (session 25). With full recomputation:

    \[ \underbrace{2N}_{\text{forward}} + \underbrace{2N}_{\text{recompute}} + \underbrace{4N}_{\text{backward}} = 8N, \qquad \frac{8N}{6N} = 1.33 \tag{39.8} \]

    So the GPU does about 33% more matrix work. The attention-score FLOPs scale the same way (forward, recompute, backward in the ratio 1 : 1 : 2), so the ratio stays at 4/3 for any sequence length. In measured time the overhead is usually 30–40%, the range Korthikanti et al. quote; they measured 36% per layer for their 530B and 1T models. [Certain] This is also why MFU falls with recomputation: the recomputed FLOPs are real work for the hardware but not “useful” model FLOPs (session 51).

    Selective recomputation

    Look again at formula (39.5). The \(5hs/d\) part (the attention scores and softmax) is most of the memory at long sequence lengths: 160 out of 194 units in the worked example, 82%. But it is cheap to recompute: the scores \(QK^\top\) and the product with \(V\) are a small share of the FLOPs when \(s\) is not much larger than \(d\). The linear layers are the reverse: little memory each, most of the FLOPs. Korthikanti et al. therefore recompute only the attention core (\(QK^\top\), softmax, softmax dropout, and the product with \(V\)) and store everything else. [Certain] This removes the \(5hs/d\) term and costs only the attention-score forward again, about \(4\,s\,d\) FLOPs per token per layer:

    \[ \frac{\text{FLOPs with selective}}{\text{FLOPs without}} = \frac{72\,d + 16\,s}{72\,d + 12\,s} \quad \text{(per token per layer, } 12d^2 \text{ weights per layer)} \tag{39.9} \]

    At \(s = d = 4{,}096\) this is \(88/84 = 1.048\), about 5% more FLOPs in this simple count. The paper reports 2.7% extra FLOPs for GPT-3 175B and 1.6% for the 530B model (their \(d\) is much larger than \(s\)), and, together with sequence parallelism, 29–32% higher throughput than full recomputation. [Certain]

    Interview tip“FlashAttention already does selective recomputation.” True in effect: FlashAttention never stores the \(s \times s\) score matrix; its backward pass recomputes the scores block by block from \(Q\), \(K\) and the saved softmax statistics. [Certain] So with FlashAttention the \(5hs/d\) term is gone already, and the remaining choice is between storing the \(34\,sbd\) and full block checkpointing.

    Figure 4 puts the formulas together for the 7B-sized shape. You pick the length, the micro-batch and the strategy; it gives the activation memory and the extra compute.

    Using both in practice

    Algorithm 2: a block-checkpointed forward and backward pass
    1. input: blocks \(f_1, \dots, f_L\), input \(x_0\)
    2. for \(i = 1, \dots, L\) do // forward, no internal activations saved
    3. save \(x_{i-1}\) (and the random-number state, for dropout); \(x_i \leftarrow f_i(x_{i-1})\) without saving anything inside \(f_i\)
    4. end for; compute the loss from \(x_L\) and its gradient \(g_L = \partial \mathcal{L} / \partial x_L\)
    5. for \(i = L, \dots, 1\) do // backward
    6. restore the random-number state; recompute \(x_i = f_i(x_{i-1})\), this time saving the internal activations
    7. backprop through \(f_i\): \(g_{i-1} \leftarrow\) input gradient, add the weight gradients into .grad
    8. free the internal activations of \(f_i\) and the checkpoint \(x_{i-1}\)
    9. end for

    In PyTorch this is torch.utils.checkpoint.checkpoint(block, x, use_reentrant=False). The non-reentrant version is the one PyTorch recommends, and by default it saves and restores the random-number state so that dropout makes the same mask both times (preserve_rng_state=True). [Certain] In Hugging Face Transformers, model.gradient_checkpointing_enable() wraps every decoder layer this way; the KV cache must be off during training (use_cache=False), and the library warns and turns it off for you. [Likely]

    The code below checks three claims on a tiny 6-layer model, on the CPU, in about a second: correct accumulation equals the big batch, the naive version does not, and checkpointing gives the same gradients with fewer saved activations. It measures saved activations with saved_tensors_hooks, which sees every tensor that autograd stores for the backward pass.

    import torch, torch.nn as nn, torch.nn.functional as F
from torch.utils.checkpoint import checkpoint
torch.manual_seed(0)
V, D, NL, T = 50, 64, 6, 16                     # vocab, width, layers, max length

class Block(nn.Module):                          # pre-norm MLP block with a residual
    def __init__(s):
        super().__init__(); s.n = nn.LayerNorm(D)
        s.f = nn.Sequential(nn.Linear(D, 4 * D), nn.GELU(), nn.Linear(4 * D, D))
    def forward(s, x): return x + s.f(s.n(x))

class TinyLM(nn.Module):
    def __init__(s):
        super().__init__(); s.emb = nn.Embedding(V, D)
        s.blocks = nn.ModuleList(Block() for _ in range(NL)); s.out = nn.Linear(D, V)
    def forward(s, x, ckpt=False):
        h = s.emb(x)
        for b in s.blocks:                       # checkpoint = keep only the block input
            h = checkpoint(b, h, use_reentrant=False) if ckpt else b(h)
        return s.out(h)

# 4 micro-batches of 2 sequences each; real lengths differ a lot, the rest is padding
lens = [[16, 14], [3, 2], [15, 16], [4, 1]]
batches = []
for pair in lens:
    x = torch.randint(0, V, (2, T)); y = torch.randint(0, V, (2, T))
    for i, n in enumerate(pair): y[i, n:] = -100     # -100 = ignored by cross_entropy
    batches.append((x, y))
model = TinyLM()
params = list(model.parameters())
def grads(): return torch.cat([p.grad.flatten() for p in params])

# (1) reference: all 8 sequences in ONE batch, mean over all real tokens
model.zero_grad()
X = torch.cat([b[0] for b in batches]); Y = torch.cat([b[1] for b in batches])
F.cross_entropy(model(X).flatten(0, 1), Y.flatten(), ignore_index=-100).backward()
g_ref = grads().clone()

# (2) correct accumulation: sum of token losses / total real tokens of the WHOLE step
n_total = sum((y != -100).sum() for _, y in batches)
model.zero_grad()
for x, y in batches:
    loss = F.cross_entropy(model(x).flatten(0, 1), y.flatten(), ignore_index=-100, reduction="sum")
    (loss / n_total).backward()                  # .grad adds up across micro-batches
print("correct  :", (grads() - g_ref).abs().max().item())          # about 3e-8: rounding only

# (3) the token-count trap: mean per micro-batch, then divide by K
model.zero_grad()
for x, y in batches:
    loss = F.cross_entropy(model(x).flatten(0, 1), y.flatten(), ignore_index=-100)
    (loss / len(batches)).backward()
print("naive    :", (grads() - g_ref).abs().max().item(), "norm ratio",
      (grads().norm() / g_ref.norm()).item())    # about 0.15 and 1.42: a different gradient

# (4) checkpointing: same gradients, fewer saved activations
def saved_bytes(ckpt):
    total = [0]
    def pack(t): total[0] += t.numel() * t.element_size(); return t
    model.zero_grad()
    with torch.autograd.graph.saved_tensors_hooks(pack, lambda t: t):
        loss = F.cross_entropy(model(X, ckpt).flatten(0, 1), Y.flatten(), ignore_index=-100)
    loss.backward()
    return total[0], grads().clone()
b0, g0 = saved_bytes(False); b1, g1 = saved_bytes(True)
print("saved KB :", b0 // 1024, b1 // 1024, (g0 - g1).abs().max().item())   # 2793 288 0.0

    With PyTorch 2.8 on a CPU this prints a difference of about \(3 \times 10^{-8}\) for the correct accumulation, about 0.15 (and a gradient norm 1.42 times too large) for the naive one, and 2,793 KB versus 288 KB of saved tensors with checkpointing, with identical gradients. [Certain: we ran it] The naive gradient is too large here because the two short micro-batches (5 and 5 real tokens) get the same weight as the long ones (30 and 31 tokens).

    Other ways to save activation memory, all covered later: offloading activations to CPU memory, sequence parallelism, which splits the \(34\,sbd\) part across tensor-parallel GPUs (session 48), and lower-precision activations. In session 41 you measure all of this on a real GPU.

    Common mistakes

    • Forgetting the \(1/K\). The gradient becomes \(K\) times too large; clipping and weight decay now act differently, and the learning rate you tuned is wrong.
    • The token-count trap. Averaging per micro-batch and then over micro-batches (39.4) when the micro-batches have different numbers of real tokens. Use reduction="sum" and divide by the total real-token count of the whole step, on all GPUs.
    • Calling optimizer.step() or the scheduler every micro-batch. The step and the learning-rate schedule count optimizer steps, not micro-batches. Also: clip the gradient once, after the last micro-batch.
    • Syncing gradients every micro-batch in DDP. Correct but slow; use no_sync() for the first \(K - 1\) micro-batches.
    • Assuming accumulation works with BatchNorm or contrastive losses. Batch statistics and in-batch negatives depend on the micro-batch, not on the effective batch.
    • Checkpointing with dropout but without restoring the random state. The recomputed forward then uses a different dropout mask and the gradients are wrong. PyTorch’s default (preserve_rng_state=True) handles it; custom recomputation code must too.
    • Checkpointing a block whose forward has side effects (it updates a counter, a cache, or a running statistic). The side effect happens twice. Keep the KV cache off in training.
    • Expecting checkpointing to help the weights. It only reduces activation memory. If weights, gradients and optimizer states do not fit, you need sharding, 8-bit states or LoRA instead.

    Interview questions

    What is gradient accumulation, and what is the effective batch size?basic
    You run \(K\) micro-batches through forward and backward, let the gradients add up in the .grad buffers, and call optimizer.step() once at the end. The optimizer sees the gradient of all \(K\) micro-batches together. The effective batch is \(b \cdot K \cdot N_{\text{dp}}\) sequences, or that times \(s\) in tokens (39.1). Memory depends only on the micro-batch \(b\).
    Is accumulation exactly equivalent to a larger batch?core
    For losses that are plain averages over examples or tokens, yes, up to floating-point rounding, because the gradient is linear (39.2), provided you normalize correctly: divide by the total count of the whole step. It is not equivalent with BatchNorm (statistics are per micro-batch), with in-batch contrastive losses (fewer negatives), or when you average per micro-batch while the micro-batches contain different numbers of tokens. Dropout masks and data order differ as well, but that is only noise.
    Explain the token-count trap with numbers.core
    Micro-batch A has 1,000 real tokens with mean loss 2.0; B has 10 with mean loss 5.0. Mean of means: 3.5. True per-token mean: \(2{,}050 / 1{,}010 = 2.03\). Each token of B got weight 0.05 instead of 0.00099, 50.5 times too much. Fix: reduction="sum" and divide by the total number of real tokens across all micro-batches (and all GPUs). Hugging Face fixed this in its Trainer in October 2024.
    How does the token-count trap appear with data parallelism, and how do you fix it?advanced
    DDP averages gradients over GPUs. If each GPU normalizes by its own token count, the result is a mean of per-GPU means, the same bias. All-reduce the real-token count first to get \(N_{\text{tot}}\), have each GPU backprop \(\text{(sum of its token losses)} \cdot N_{\text{dp}} / N_{\text{tot}}\), so that DDP’s division by \(N_{\text{dp}}\) leaves exactly \(\sum \ell_t / N_{\text{tot}}\).
    What does gradient checkpointing store, and what does it recompute?basic
    It stores only chosen tensors, usually the input of every transformer block (\(2sbd\) bytes in BF16), and drops the internal activations. During the backward pass, each block’s forward is run again from its stored input, this time keeping the internals, and then the block is backpropagated and its internals freed. Peak memory is about \(2sbdL\) plus one block’s activations (39.6).
    What does full checkpointing cost in compute and time?core
    One extra forward pass: \(2N + 2N + 4N = 8N\) FLOPs per token instead of \(6N\), 33% more (39.8). Measured slowdowns are typically 30–40%. MFU drops because recomputed FLOPs do not count as useful model FLOPs, while hardware FLOPs utilization can stay high.
    Derive the square-root rule. Why do transformers usually checkpoint every block instead?advanced
    With a checkpoint every \(c\) of \(n\) layers, the peak is \(M(c) \approx (n/c) I + cA\). Minimizing gives \(c^* = \sqrt{nI/A}\) and \(M^* = 2\sqrt{nIA}\); for similar \(I\) and \(A\) that is \(O(\sqrt{n})\) memory (Chen et al. 2016). In a transformer block, the saved inside activations are much larger than the block input (\(A = 34\), \(I = 2\) in units of \(sbd\) bytes), so for 32 layers \(c^* = 1.37\): one checkpoint per block (98 units) beats every two blocks (100) and every four (152).
    What is selective activation recomputation?advanced
    From Korthikanti et al. (2022): recompute only the attention core (\(QK^\top\), softmax, softmax dropout, attention times \(V\)), store everything else. That part is most of the activation memory at long sequences (the \(5hs/d\) term of 39.5) but a small share of FLOPs, so it removes the \(s^2\) memory for about 2–3% extra FLOPs at GPT-3 scale (2.7% for 175B, 1.6% for 530B). FlashAttention gets the same effect inside its kernel.
    Your 7B fine-tune runs out of memory. In what order do you try accumulation, checkpointing and other options?core
    First see which part is too big (session 38). If it is the activations: lower the micro-batch and raise \(K\) to keep the effective batch (no extra compute), turn on FlashAttention, then turn on block checkpointing (about 33% more compute). If the states (16 bytes per parameter, 112 GB for 7B) do not fit, neither tool helps: you need ZeRO/FSDP sharding, 8-bit optimizer states, CPU offload, or LoRA/QLoRA.
    Why must recomputation restore the random-number state?core
    Dropout draws a random mask in the forward pass. If the recomputed forward draws a different mask, the activations used in the backward pass are not the ones that produced the loss, and the gradient is wrong. PyTorch’s checkpoint saves the RNG state with the checkpoint and restores it before recomputing (preserve_rng_state=True by default).

    1. You want 2 million tokens per step with sequences of 8,192 tokens, 32 GPUs and a micro-batch of 1. How many accumulation steps do you need?
    2. Three micro-batches have 200, 50 and 750 real tokens and mean losses 3.0, 4.0 and 2.0. Compute the naive loss (39.4) and the correct loss (39.3).
    3. In the same example, by what factor is one token of the 50-token micro-batch over-weighted by the naive loss?
    4. With formula (39.7), \(n = 64\) simple layers and \(I = A\): what segment length is best, and how much memory (in units of \(I\)) do you need, compared with no checkpointing?
    5. For \(L = 32\), \(d = 4{,}096\), \(s = 8{,}192\), \(b = 1\): how much memory do the stored block inputs (\(2sbdL\)) take in BF16?
    6. Use formula (39.9) to compute the FLOP overhead of selective recomputation at \(d = 4{,}096\) and \(s = 16{,}384\).
    Answerscheck
    1. \(2{,}097{,}152 / 8{,}192 = 256\) sequences per step; one round of all GPUs gives \(1 \times 32 = 32\); \(K = 256/32 = 8\). 2. Naive: \((3.0 + 4.0 + 2.0)/3 = 3.0\). Correct: \((600 + 200 + 1{,}500)/1{,}000 = 2.3\). 3. Naive weight \(1/(3 \times 50) = 0.00667\); correct weight \(1/1{,}000 = 0.001\): 6.67 times too much. 4. \(c^* = \sqrt{64} = 8\); \(M = 64/8 + 8 = 16\) units versus \(64\) without checkpointing (4 times less), for one extra forward pass. 5. \(2 \times 8{,}192 \times 4{,}096 \times 32 = 2{,}147{,}483{,}648\) bytes = 2.15 GB (2 GiB). 6. \((72 \times 4{,}096 + 16 \times 16{,}384)/(72 \times 4{,}096 + 12 \times 16{,}384) = 557{,}056/491{,}520 = 1.133\): about 13% more FLOPs, because at long sequences the attention core is no longer cheap.

    Key takeaways

    • Gradient accumulation runs \(K\) micro-batches and steps once; the effective batch is \(b K N_{\text{dp}}\) sequences (39.1), and memory depends only on \(b\).
    • Because the gradient is linear, accumulation equals the big batch (39.2), if the loss is normalized by the total count of the whole step.
    • For tokens with padding, use the sum of token losses divided by the step’s real-token count (39.3); the mean of micro-batch means (39.4) over-weights short micro-batches. Do the same across GPUs.
    • Checkpointing keeps only block inputs and recomputes the rest in the backward pass: memory goes from \(L \cdot sbd(34 + 5hs/d)\) to about \(2sbdL\) plus one block (39.5, 39.6), 104 GB to 1.6 GB in the 7B example.
    • The price is one extra forward pass: \(8N\) instead of \(6N\) FLOPs, 33% (39.8). Selective recomputation of the attention core costs only a few percent (39.9).
    • The square-root rule (39.7) says checkpoint every \(\sqrt{n}\) layers for simple chains; for transformer blocks, one checkpoint per block is best.

    Key formulas

    \[ T_{\text{eff}} = bKN_{\text{dp}}s, \qquad \mathcal{L}_{\text{step}} = \frac{1}{N_{\text{tot}}}\sum_{k}\sum_{t \in \mathcal{B}_k}\ell_t \]
    \[ M_{\text{full ckpt}} \approx 2sbdL + sbd\Big(34 + \frac{5hs}{d}\Big), \qquad M(c) \approx \frac{n}{c}I + cA, \qquad \text{FLOPs: } 6N \to 8N \]
