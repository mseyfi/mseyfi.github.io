    Weight PTQ 1: from OBQ to GPTQ

    Rounding every weight to the nearest 4-bit or 3-bit value is simple, but at 3 bits it breaks large models. GPTQ quantizes a layer one column at a time and, after each column, changes the weights that are not yet quantized so that the layer output stays almost the same. This session builds GPTQ step by step from its parent method OBQ, with the math, the speed tricks and working code.

    Time: 3 to 4 hours (reading 2 hours, exercises 1 to 2 hours)Level: Intermediate to interview levelBefore this: Quantization math (session 103), number formats (session 105), basic linear algebra

    What you will learn

    • Why post-training quantization of LLM weights is solved one layer at a time, with the objective ‖WX − ŴX‖²
    • What the Hessian H = 2XXᵀ is, why it depends only on the calibration inputs, and how it tells which weights matter
    • The OBQ step: quantize one weight, then move the remaining weights to cancel its error (and how to derive it)
    • Why OBQ costs O(d_row·d_col³) and how a fixed column order brings GPTQ to O(max(d_row·d_col², d_col³))
    • Lazy batch updates, the Cholesky form of the inverse Hessian, and dampening
    • Practical GPTQ: calibration data, groups, act-order, kernels, and what the paper actually measured

    Why this matters

    When an LLM generates text one token at a time, each step must read every weight from GPU memory. The math per weight is tiny, so the speed is set by how many bytes we read. Store the weights in 4 bits instead of 16, and we read 4 times fewer bytes. The hard part is doing this without making the model worse.

    The simplest method is round-to-nearest (RTN): put each weight on the nearest point of the quantization grid from session 103. RTN works well at 8 bits. At 4 bits it starts to hurt, and at 3 bits it can destroy a model. The GPTQ paper (Frantar et al., 2022) shows this on OPT-175B: WikiText2 perplexity is 8.34 in FP16, 10.54 with 4-bit RTN, and about 7,300 with 3-bit RTN. GPTQ gets 8.37 at 4 bits and 8.68 at 3 bits, on the same grid. [Certain] It quantized the 175B model in about 4 hours on one A100 GPU, using only 128 short pieces of random web text. [Certain]

    The difference is one idea. RTN rounds every weight on its own. GPTQ rounds the weights of a layer one column at a time, and after each column it changes the weights that are not yet rounded so that their change cancels the error just made. The layer output stays close to the original, even though many weights are rounded "the wrong way".

    Interview tipTypical questions: “What does GPTQ minimize?”, “What is the Hessian in GPTQ and why does it not depend on the weights?”, “Why is GPTQ so much faster than OBQ?”, “What are act-order and group size?”. Each is answered below with numbers.

    GPTQ is one of the most used methods to make 4-bit checkpoints of open models; GPTQ models load in Hugging Face Transformers and in serving engines such as vLLM. [Likely] This is the first of two sessions on weight-only post-training quantization (PTQ: quantize after training, with no retraining). The next one, session 107, adds AWQ, outliers and mixed precision.

    The layer-wise problem: keep WX close to ŴX

    Quantizing all weights of a large model together is a huge problem with no good solution. So PTQ methods cut it into small problems: one linear layer at a time. Take a linear layer with weight matrix \(W \in \R^{d_{row} \times d_{col}}\). It maps an input vector of size \(d_{col}\) to an output of size \(d_{row}\). Run a small set of calibration texts through the model and collect the inputs of this layer as the columns of a matrix \(X \in \R^{d_{col} \times n}\) (\(n\) = number of tokens). We want quantized weights \(\hat W\) whose outputs on these inputs are as close as possible to the original outputs:

    \[ \hat W^{*} = \argmin_{\hat W \text{ on the grid}} \; \big\lVert W X - \hat W X \big\rVert_F^2 \tag{106.1} \]
    Read the symbols
    \(W\)
    the original weights of the layer (FP16), one row per output channel
    \(\hat W\)
    the quantized weights; every entry must be a point on the fixed quantization grid of its row
    \(X\)
    calibration inputs of this layer, one column per token
    \(\lVert \cdot \rVert_F^2\)
    sum of the squares of all entries (Frobenius norm squared)

    Note what this objective cares about: not the weights, but the outputs. A weight that only meets small inputs can be rounded badly with little harm. Two weights whose inputs move together can make errors that cancel.

    The objective splits into one independent problem per row. Write \(\mathbf{w}\) for one row of \(W\), \(\hat{\mathbf{w}}\) for its quantized version and \(\delta = \hat{\mathbf{w}} - \mathbf{w}\) for the change (all row vectors). Then

    \[ E(\delta) = \lVert \mathbf{w} X - \hat{\mathbf{w}} X \rVert^2 = \delta\, X X^\top \delta^\top = \tfrac12\, \delta\, H\, \delta^\top \tag{106.2} \]
    \[ H = 2 X X^\top \in \R^{d_{col} \times d_{col}} \tag{106.3} \]

    \(H\) is the Hessian (matrix of second derivatives) of the row error with respect to the weights. Because the error is exactly quadratic, formula (106.2) is not an approximation. Two facts make \(H\) very useful:

    • \(H\) depends only on the inputs \(X\), not on the weights. All \(d_{row}\) rows of the layer share the same \(H\).
    • \(H\) is small: \(d_{col} \times d_{col}\). For a layer with 4,096 inputs it is a 4,096 × 4,096 matrix, built once from the calibration data.
    AnalogyA team of rowers must keep the boat on a straight line. You force each rower, one by one, to a fixed rhythm that is a little off. After each one is fixed, the rowers who are still free adjust their strokes to cancel the push. RTN fixes all rowers at once and lets the pushes add up.

    The Hessian tells which weights matter

    Write formula (106.2) out entry by entry:

    \[ E(\delta) = \tfrac12 \sum_{j} H_{jj}\, \delta_j^2 \; + \; \sum_{j \lt k} H_{jk}\, \delta_j\, \delta_k, \qquad H_{jk} = 2 \sum_{t=1}^{n} x_{jt}\, x_{kt} \tag{106.4} \]

    The two parts say two different things:

    • Diagonal \(H_{jj}\): twice the energy of input channel \(j\). An input channel whose activations are 6 times larger has a 36 times larger \(H_{jj}\), so the same rounding error on its weight costs 36 times more. This is why channels with large activations ("outlier channels") are a big topic in LLM quantization (session 107).
    • Off-diagonal \(H_{jk}\): how much inputs \(j\) and \(k\) move together. If they are positively correlated and we round \(w_j\) up, we can cancel most of the damage by moving \(w_k\) down. RTN never uses this. GPTQ is built on it.

    If \(H\) were diagonal (all inputs uncorrelated), the best rounding would be RTN, because the error would be a sum of independent terms. Real LLM activations are strongly correlated, so there is a lot to gain.

    Worked example: two weights, correlated inputs

    One row with two weights \(\mathbf{w} = (0.6,\ 0.6)\). The grid is the integers. The two inputs have equal energy and correlation 0.9: \(XX^\top = \begin{pmatrix} 1 & 0.9 \\ 0.9 & 1 \end{pmatrix}\).

    RTN rounds both up to \((1, 1)\). Then \(\delta = (0.4, 0.4)\) and \(E = 0.16 + 0.16 + 2 \cdot 0.9 \cdot 0.16 = 0.608\). Both errors push the output the same way.

    Round one, then compensate. Round \(w_1\) to 1 (error \(+0.4\)). Formula (106.5) below says: move \(w_2\) by \(-0.9 \times 0.4 = -0.36\), to \(0.24\). Now round \(w_2\) to 0. Result \((1, 0)\), \(\delta = (0.4, -0.6)\), \(E = 0.16 + 0.36 - 2 \cdot 0.9 \cdot 0.24 = 0.088\). That is 7 times smaller than RTN, and a search over all grid points shows it is the best possible. Note that \(w_2 = 0.6\) was rounded to 0, the "wrong" way. Try it in Figure 1.

    OBS and OBQ: quantize one weight, fix the rest

    The compensation step comes from a 1993 pruning method, Optimal Brain Surgeon (OBS) (Hassibi and Stork). OBS removes one weight from a network (sets it to 0) and changes all other weights to cancel the damage, using the inverse Hessian. Optimal Brain Quantization (OBQ) (Frantar and Alistarh, 2022, in the "Optimal Brain Compression" paper) uses the same math, but instead of "set the weight to 0" the constraint is "set the weight to its grid value".

    Let \(F\) be the set of weights in a row that are still in full precision, and \(H_F\) the Hessian restricted to them. We force weight \(q\) to \(\operatorname{quant}(w_q)\) (its nearest grid point) and choose the change \(\delta_F\) of the free weights that keeps the error (106.2) as small as possible. This is a quadratic minimized under one linear constraint; a Lagrange multiplier gives the exact answer:

    \[ \delta_F = -\,\frac{w_q - \operatorname{quant}(w_q)}{[H_F^{-1}]_{qq}} \cdot (H_F^{-1})_{:,q}, \qquad \Delta E_q = \frac{\big(w_q - \operatorname{quant}(w_q)\big)^2}{2\,[H_F^{-1}]_{qq}} \tag{106.5} \]
    Read the symbols
    \(\operatorname{quant}(w_q)\)
    weight \(q\) rounded to the nearest grid point
    \(H_F^{-1}\)
    the inverse of the Hessian of the weights still free (\(F\) includes \(q\))
    \((H_F^{-1})_{:,q}\)
    column \(q\) of that inverse: the direction in which all free weights move
    \(\delta_F\)
    the change of all free weights; its entry \(q\) moves \(w_q\) exactly onto the grid
    \(\Delta E_q\)
    the increase of the output error caused by this step, after the best compensation

    Check it on the worked example: \(H^{-1} = (2XX^\top)^{-1}\) has \([H^{-1}]_{21} / [H^{-1}]_{11} = -0.9\), so \(\delta_2 = -(0.6 - 1)(-0.9) = -0.36\). And \(\Delta E = 0.4^2 / (2 \cdot 2.632) = 0.0304\): this is the error just before \(w_2\) is rounded.

    OBQ is greedy: at each step it picks the weight whose quantization costs least,

    \[ q^{*} = \argmin_{q \in F} \; \frac{\big(\operatorname{quant}(w_q) - w_q\big)^2}{[H_F^{-1}]_{qq}} \tag{106.6} \]

    then applies (106.5), removes \(q\) from \(F\), and repeats until the row is done. After removing \(q\), we need the inverse of the smaller Hessian. We do not invert again: one step of Gaussian elimination on the old inverse gives it.

    \[ H_{F \setminus q}^{-1} = \Big( H_F^{-1} - \frac{1}{[H_F^{-1}]_{qq}}\, (H_F^{-1})_{:,q}\, (H_F^{-1})_{q,:} \Big)_{-q} \tag{106.7} \]

    Here \((\cdot)_{-q}\) means "drop row and column \(q\)". This costs \(O(d_{col}^2)\) per weight instead of \(O(d_{col}^3)\) for a new inverse.

    Algorithm 1: OBQ for one row (greedy order)
    1. input: row \(\mathbf{w}\), inverse Hessian \(H^{-1} = (2XX^\top)^{-1}\), grid
    2. \(F \leftarrow\) all \(d_{col}\) weights
    3. while \(F\) is not empty:
    4.   pick \(q\) in \(F\) with the smallest \((\operatorname{quant}(w_q) - w_q)^2 / [H_F^{-1}]_{qq}\) // formula (106.6)
    5.   \(\mathbf{w}_F \leftarrow \mathbf{w}_F + \delta_F\) // formula (106.5); now \(w_q = \operatorname{quant}(w_q)\)
    6.   \(H_F^{-1} \leftarrow\) Gaussian elimination of row and column \(q\) // formula (106.7), \(O(d_{col}^2)\)
    7.   \(F \leftarrow F \setminus \{q\}\)
    8. return \(\mathbf{w}\) (now all on the grid)

    Watch Algorithm 1 run in Figure 2. It is one row of 5 weights on the integer grid. The inputs have correlation \(\rho^{|j-k|}\) between channels \(j\) and \(k\), so \(XX^\top_{jk} = \rho^{|j-k|}\) and \(H = 2XX^\top\). Every number is computed in your browser: the scores of (106.6), the move \(\delta_F\) of (106.5), and the elimination (106.7) of the inverse Hessian. Each step adds exactly \(\Delta E_q\) to the error, so the sum of the \(\Delta E_q\) is the final error \(E = \tfrac12 \delta H \delta^\top\). The figure checks this at every step.

    OBQ is accurate, but the cost is a problem. Each row needs \(d_{col}\) steps, each step updates a \(d_{col} \times d_{col}\) inverse, and each row has its own order, so its own sequence of inverses. That is \(O(d_{col}^3)\) per row and \(O(d_{row} \cdot d_{col}^3)\) per layer. The GPTQ paper reports that OBQ quantizes ResNet-50 (25M parameters) in about 1 hour on one GPU; models with billions of parameters are out of reach. [Certain]

    GPTQ step 1: one fixed order for all rows

    The first GPTQ insight is empirical: the greedy order of (106.6) helps only a little over any fixed order, especially on large layers. The paper's explanation: weights with large individual errors get quantized late, when only a few free weights remain to compensate, so the gain of the clever order is partly lost. [Certain, as the paper's finding] You can see a tiny version of this in Figure 2: on row B the fixed left-to-right order beats the greedy order at \(\rho = 0.9\) and loses at \(\rho = 0.5\).

    So GPTQ quantizes column by column, left to right, in the same order for every row. Now the free set \(F\) is the same for all rows at every step. And \(H_F\) depends only on \(X\), not on the weights. So all rows share one sequence of inverse Hessians, and formula (106.7) runs only \(d_{col}\) times per layer (once per column), not \(d_{row} \cdot d_{col}\) times. The update (106.5) of all rows at once becomes one outer product.

    \[ \text{OBQ: } O\big(d_{row} \cdot d_{col}^3\big) \quad \longrightarrow \quad \text{GPTQ: } O\big(\max\{d_{row} \cdot d_{col}^2,\ d_{col}^3\}\big) \tag{106.8} \]

    The gain is a factor of \(\min\{d_{row}, d_{col}\}\). For a 4,096 × 4,096 layer that is a factor of 4,096: about \(2.8 \times 10^{14}\) basic operations become about \(6.9 \times 10^{10}\) (constant factors ignored). Figure 5 lets you change the shape.

    GPTQ step 2: lazy batch updates

    A direct implementation of step 1 is still slow on a GPU. After each column it updates the whole remaining weight matrix and the whole inverse with an outer product: only a few FLOPs per number read from memory. The GPU waits for memory, not for compute (the memory-bound problem from session 82).

    The fix: the rounding decision for column \(j\) only depends on the updates that have reached column \(j\). Updates to columns far to the right can wait. So GPTQ works on a block of \(B = 128\) columns at a time. Inside the block it does the column-by-column work on a small slice. When the block is done, it applies all the waiting updates to the rest of the matrix in one matrix multiplication, which a GPU runs efficiently. With \(Q\) the set of columns in the block and \(\mathbf{e}\) their errors:

    \[ \delta_F = -\big(\mathbf{w}_Q - \operatorname{quant}(\mathbf{w}_Q)\big)\, \big([H_F^{-1}]_{QQ}\big)^{-1} (H_F^{-1})_{Q,:} \tag{106.9} \]

    This is the multi-weight version of (106.5). The number of FLOPs does not change, and the result is exactly the same as column by column (the code below checks it). Only the memory traffic falls. The paper reports an order of magnitude speed-up from this trick on very large models. [Certain]

    GPTQ step 3: the Cholesky form, and dampening

    Applying (106.7) thousands of times collects rounding errors in floating point. The paper observed that for models above a few billion parameters, \(H_F^{-1}\) becomes indefinite (it gets negative eigenvalues) in at least a few layers. Then (106.5) pushes the weights in wrong directions and the layer is ruined. [Certain]

    Two fixes work together. First, dampening: add a small constant to the diagonal before inverting. GPTQ uses 1% of the average diagonal value:

    \[ H \leftarrow H + \lambda I, \qquad \lambda = 0.01 \cdot \tfrac{1}{d_{col}} \textstyle\sum_j H_{jj} \tag{106.10} \]

    This also helps when some input channels are always zero in the calibration data, which would make \(H\) singular (not invertible).

    Second, the Cholesky trick. When we quantize column \(j\), the update needs only one row of the current inverse, row \(j\), from the diagonal to the right. With the fixed order, these rows are exactly what a Cholesky decomposition computes. Write \(H^{-1} = U^\top U\) with \(U\) upper triangular. Then for every step \(j\) and every \(k \ge j\):

    \[ [H_{F_j}^{-1}]_{jk} = U_{jj}\, U_{jk}, \qquad \text{so} \qquad \frac{(H_{F_j}^{-1})_{j,k}}{[H_{F_j}^{-1}]_{jj}} = \frac{U_{jk}}{U_{jj}} \tag{106.11} \]

    where \(F_j\) is the set of columns \(j, j+1, \dots\) still free at step \(j\). So we compute \(U\) once, at the start, with a fast and stable library routine, and never apply (106.7) at all. In the algorithm below, the scaled error is \(e = (w_j - q_j) / U_{jj}\) and the update of the rest of the row is \(-e \cdot U_{j,j:}\). We checked (106.11) numerically on random matrices.

    Algorithm 2: GPTQ for one layer (all rows at once)
    1. input: \(W \in \R^{d_{row} \times d_{col}}\), calibration inputs \(X\), block size \(B\), grid per row
    2. \(H \leftarrow 2XX^\top + \lambda I\) // formulas (106.3), (106.10)
    3. \(U \leftarrow \operatorname{Cholesky}(H^{-1})\), upper triangular // formula (106.11), computed once
    4. for \(i = 0, B, 2B, \dots\): // one block of B columns
    5.   \(E \leftarrow 0^{d_{row} \times B}\)
    6.   for \(j = i, \dots, i + B - 1\):
    7.     \(Q_{:,j} \leftarrow \operatorname{quant}(W_{:,j})\) // round the whole column
    8.     \(E_{:,j-i} \leftarrow (W_{:,j} - Q_{:,j}) / U_{jj}\) // scaled error, one number per row
    9.     \(W_{:,j:i+B} \leftarrow W_{:,j:i+B} - E_{:,j-i}\, U_{j,\,j:i+B}\) // compensate inside the block
    10.   \(W_{:,i+B:} \leftarrow W_{:,i+B:} - E\, U_{i:i+B,\; i+B:}\) // lazy update, one matmul, formula (106.9)
    11. return \(Q\)

    Now watch Algorithm 2 run in Figure 3, on a layer of 3 rows and 6 columns. The calibration inputs are 32 tokens with correlation \(\rho\) between neighboring input channels (\(x_j = \rho\, x_{j-1} + \sqrt{1-\rho^2}\, z_j\), fixed seed). The figure computes \(H = 2XX^\top/n\) (dividing by the number of tokens \(n\) only rescales \(H\) and does not change the result), adds the dampening (106.10), and takes the Cholesky factor \(U\) of \(H^{-1}\) (106.11). Each row has its own min-max grid with \(2^b\) levels. Then it runs the loop, one line at a time.

    How much better than RTN is GPTQ? It depends on the bit width and on how correlated the inputs are. Figure 4 runs both on a layer of 32 × 64 weights with 256 calibration tokens.     Running GPTQ on a real model

    Calibration and the order of layers

    The paper's calibration set is 128 random segments of 2,048 tokens from the C4 web dataset: about 262,000 tokens, with nothing task-specific. [Certain] The model is processed one transformer block at a time: load the block on the GPU, run the calibration inputs through it, collect \(H\) for each of its linear layers, quantize them, then run the inputs through the quantized block to get the inputs of the next block. So each layer is fitted to the inputs it will really see, errors of earlier layers included. This is why one 80 GB GPU is enough even for a 175B model. [Certain]

    Algorithm 3: quantizing a whole model with GPTQ
    1. input: model, calibration batches (e.g. 128 × 2,048 tokens), bits, group size
    2. \(Z \leftarrow\) hidden states after the embedding layer, for all calibration tokens
    3. for each transformer block:
    4.   run \(Z\) through the block with hooks; for every linear layer add \(2XX^\top\) of its inputs to its \(H\)
    5.   for each linear layer of the block: \(\hat W \leftarrow \operatorname{GPTQ}(W, H)\) // Algorithm 2
    6.   \(Z \leftarrow\) output of the quantized block on \(Z\) // next block sees real, quantized inputs
    7. save integer weights, scales and zero points; embeddings and output layer usually stay FP16

    Groups

    The basic grid has one scale and one zero point per row. With groups, every \(g\) consecutive weights of a row get their own scale and zero point (session 103). GPTQ fits well with groups: the grid of a group is chosen when the algorithm reaches its first column, from the already updated weights. The cost is extra bits. With an FP16 scale and a \(b\)-bit zero point per group, the overhead is \((16 + b)/g\) bits per weight: \(19/128 \approx 0.15\) for 3-bit with \(g = 128\). On OPT-175B, 3-bit GPTQ with \(g = 128\) reaches 8.45 perplexity (FP16: 8.34). [Certain] 4-bit with \(g = 128\) is the most common setting for published GPTQ checkpoints. [Likely]

    Worked example: memory of a 70B model

    In FP16: \(70 \times 10^9 \times 2\) bytes = 140 GB, two 80 GB GPUs at least. At 4 bits with \(g = 128\) (FP16 scale + 4-bit zero point): \(4 + 20/128 = 4.156\) bits per weight, so \(70 \times 10^9 \times 4.156 / 8 = 36.4\) GB, plus the FP16 embeddings and output layer. It fits on one 80 GB GPU, with room for the KV cache. The GPTQ paper did the same for OPT-175B at 3 bits: about 63 GB with FP16 embeddings, run on one A100 80 GB instead of five. [Certain]

    Act-order

    The fixed order does not have to be left to right. The GPTQ code has an option, usually called act-order (desc_act), that sorts the columns by \(H_{jj}\), largest first: the weights that meet the largest activations are quantized while many free weights can still compensate. It often improves accuracy, as in Figure 4. [Likely] With groups, it means a group's columns are no longer next to each other in memory, which needs an extra index at inference time and can slow some kernels; "static groups" (fix the groups before reordering) is a common workaround. [Likely]

    Kernels: where the speed comes from

    GPTQ only changes the stored weights. At inference, a mixed-precision kernel reads the 3-bit or 4-bit integers, turns them back into FP16 inside the GPU's fast on-chip memory, and multiplies with FP16 activations. During decoding (batch size 1, matrix-vector products) the time is mostly reading weights, so fewer bytes means more speed. The paper measured, for 3-bit OPT-175B, 71 ms per token on one A100 versus 230 ms for FP16 on five A100s (3.24×), and 130 ms on two A6000s versus 589 ms on eight (4.53×). [Certain] For large batches (prefill, busy servers) the matmuls become compute-bound and the gain shrinks; kernels such as Marlin were built to keep 4-bit fast at moderate batch sizes. [Likely] See session 104 for this trade-off.

    GPTQ in PyTorch

    The code builds a toy layer with correlated inputs and a few outlier channels, then compares RTN, GPTQ (Algorithm 2) and GPTQ with act-order. It also checks that the fast GPTQ (Cholesky, blocks) gives exactly the same weights as the slow version that applies formulas (106.5) and (106.7) column by column. It runs on CPU in a few seconds; we ran it with PyTorch 2.8.

    import torch
torch.manual_seed(0)
torch.set_default_dtype(torch.float64)

# 1) a toy layer: W is (d_row, d_col), X holds n calibration inputs as columns
d_row, d_col, n, rho = 64, 128, 512, 0.8
Z = torch.randn(d_col, n)
X = torch.empty(d_col, n); X[0] = Z[0]
for j in range(1, d_col):                       # neighbouring input channels are correlated
    X[j] = rho * X[j - 1] + (1 - rho**2) ** 0.5 * Z[j]
X[::16] *= 6.0                                  # a few "outlier" input channels
W = torch.randn(d_row, d_col)

def make_grid(W, bits):                         # per-row asymmetric min-max grid
    lo, hi = W.min(1).values, W.max(1).values
    scale = (hi - lo) / (2**bits - 1)
    zero = torch.round(-lo / scale)
    return scale, zero, 2**bits - 1

def quant(col, scale, zero, qmax):              # round one column to its row's grid
    q = torch.clamp(torch.round(col / scale) + zero, 0, qmax)
    return scale * (q - zero)

def rel_err(W, Q, X):                           # ||WX - QX||^2 / ||WX||^2
    return (((W - Q) @ X) ** 2).sum() / ((W @ X) ** 2).sum()

def rtn(W, bits):
    s, z, m = make_grid(W, bits)
    return torch.stack([quant(W[:, j], s, z, m) for j in range(W.shape[1])], 1)

def gptq(W, X, bits, block=32, damp=0.01, act_order=False):
    W = W.clone(); H = 2 * X @ X.T              # formula (106.3)
    s, z, m = make_grid(W, bits)
    perm = torch.argsort(torch.diag(H), descending=True) if act_order else torch.arange(W.shape[1])
    W, H = W[:, perm], H[perm][:, perm]
    H += damp * torch.diag(H).mean() * torch.eye(H.shape[0])            # dampening, (106.10)
    U = torch.linalg.cholesky(torch.cholesky_inverse(torch.linalg.cholesky(H)), upper=True)  # (106.11)
    Q = torch.zeros_like(W)
    for i in range(0, W.shape[1], block):
        e = min(i + block, W.shape[1]); Err = torch.zeros(W.shape[0], e - i)
        for j in range(i, e):
            Q[:, j] = quant(W[:, j], s, z, m)
            Err[:, j - i] = (W[:, j] - Q[:, j]) / U[j, j]
            W[:, j:e] -= Err[:, j - i : j - i + 1] * U[j, j:e]       # update inside the block
        W[:, e:] -= Err @ U[i:e, e:]                                  # lazy update of the rest
    return Q[:, torch.argsort(perm)]

def obq_fixed_order(W, X, bits, damp=0.01):     # formulas (106.5) and (106.7), no tricks
    W = W.clone(); H = 2 * X @ X.T
    H += damp * torch.diag(H).mean() * torch.eye(H.shape[0])
    s, z, m = make_grid(W, bits); Hinv = torch.linalg.inv(H); Q = torch.zeros_like(W)
    for q in range(W.shape[1]):
        Q[:, q] = quant(W[:, q], s, z, m)
        W -= torch.outer((W[:, q] - Q[:, q]) / Hinv[q, q], Hinv[:, q])
        Hinv -= torch.outer(Hinv[:, q], Hinv[q, :]) / Hinv[q, q]    # remove weight q
    return Q

for bits in (3, 4):
    print(bits, "bits  RTN %.5f   GPTQ %.5f   GPTQ+act-order %.5f" % (
        rel_err(W, rtn(W, bits), X), rel_err(W, gptq(W, X, bits), X),
        rel_err(W, gptq(W, X, bits, act_order=True), X)))
Q1, Q2 = gptq(W, X, 4), obq_fixed_order(W, X, 4)
print("same result as plain OBQ in fixed order:", torch.equal(Q1, Q2), (Q1 - Q2).abs().max().item())

    Common mistakes

    • Too little or wrong calibration data. \(H\) is estimated from the calibration tokens. Too few tokens give a noisy or singular \(H\); text very different from the real use (for example only English prose for a code model) fits the layers to the wrong inputs.
    • No dampening. Without \(\lambda I\), dead input channels make \(H\) singular and the Cholesky fails or the weights blow up. 1% of the mean diagonal is the usual default; raise it if a layer fails.
    • Using full-precision inputs for later blocks. Each block should be calibrated on the outputs of the already quantized blocks, as in Algorithm 3. Otherwise errors of earlier layers are not taken into account.
    • Thinking GPTQ fixes outliers. GPTQ reduces the effect of rounding, but one huge weight still stretches the grid of its row or group. Smaller groups, AWQ-style scaling or rotations handle that (session 107, session 109).
    • Forgetting the overhead bits. "4-bit" with \(g = 128\) is about 4.16 bits per weight; \(g = 32\) is about 4.6. Compare methods at equal real size.
    • Measuring only perplexity on one dataset. Check a few downstream tasks too, especially long-context and reasoning tasks, which can be hurt more than WikiText2 shows. [Likely]
    • Expecting a big prefill speed-up. Weight-only quantization mainly speeds up memory-bound decoding. At large batch sizes the gain can disappear, depending on the kernel.
    • Act-order with groups on a kernel that does not support it. The model may load but run slowly, or the reordering may be ignored. Check what your serving engine supports. [Likely]

    Interview questions

    What objective does GPTQ minimize, and why layer by layer?basic
    For each linear layer it minimizes \(\lVert WX - \hat W X\rVert_F^2\) over quantized \(\hat W\), where \(X\) are the layer's inputs on a small calibration set. Solving the whole network at once would need backpropagation through the full model and many steps; the layer-wise problem is a quadratic per row with a closed-form compensation step, it needs only forward passes, and it fits in memory one block at a time.
    What is the Hessian in GPTQ, and why does it not depend on the weights?core
    The row error is \(\delta XX^\top \delta^\top\), exactly quadratic in the weight change \(\delta\), so its Hessian is the constant \(H = 2XX^\top\). It is built only from the inputs. That is why all rows of a layer share it and why one fixed column order lets GPTQ reuse a single sequence of inverse Hessians for all rows. Its diagonal measures input-channel energy; its off-diagonal entries measure correlation, which is what makes compensation possible.
    Derive the OBQ / OBS update for one weight.advanced
    Minimize \(\tfrac12 \delta H \delta^\top\) subject to \(\mathbf{e}_q^\top \delta^\top = \operatorname{quant}(w_q) - w_q\). The Lagrangian gives \(H\delta^\top = \mu\, \mathbf{e}_q\), so \(\delta^\top = \mu H^{-1}\mathbf{e}_q\). The constraint gives \(\mu = (\operatorname{quant}(w_q) - w_q)/[H^{-1}]_{qq}\). So \(\delta = -\frac{w_q - \operatorname{quant}(w_q)}{[H^{-1}]_{qq}} (H^{-1})_{:,q}\), and the error is \(\tfrac12 \mu^2 [H^{-1}]_{qq} = \frac{(w_q - \operatorname{quant}(w_q))^2}{2[H^{-1}]_{qq}}\). With "quant" replaced by 0 this is OBS pruning.
    Why is GPTQ so much faster than OBQ?core
    Three reasons. (1) A fixed column order for all rows: since \(H\) depends only on \(X\), all rows share the same sequence of inverses, so the \(O(d_{col}^2)\) inverse update runs \(d_{col}\) times per layer instead of \(d_{row} d_{col}\) times: from \(O(d_{row} d_{col}^3)\) to \(O(\max\{d_{row} d_{col}^2, d_{col}^3\})\). (2) Lazy batch updates in blocks of 128 columns turn many memory-bound outer products into a few compute-bound matmuls. (3) The Cholesky form precomputes all needed rows of the inverse once with a fast, stable kernel. The paper reports more than three orders of magnitude speed-up over OBQ.
    Lazy batching does not reduce FLOPs. Why does it help?core
    Updating the whole remaining matrix after each column is an outer product: each weight is read and written for about one multiply-add, so the GPU is limited by memory bandwidth. Because the rounding of column \(j\) only depends on updates already applied to column \(j\), the updates for far columns can be collected and applied once per block as a matrix multiply \(E\,U_{\text{block}, \text{rest}}\), which reuses data in fast memory and runs near peak compute. The result is exactly the same.
    Why does GPTQ need a Cholesky decomposition and dampening?advanced
    Repeated Gaussian-elimination updates of \(H^{-1}\) accumulate floating-point error and, on models above a few billion parameters, made \(H_F^{-1}\) indefinite in some layers, which sends the compensation in wrong directions. With a fixed order, the only thing needed at step \(j\) is row \(j\) of the current inverse from the diagonal on, which equals \(U_{jj} U_{j,j:}\) for the upper Cholesky factor \(U\) of \(H^{-1}\). So one stable Cholesky replaces all the updates. Dampening (\(\lambda\) = 1% of the mean diagonal) keeps \(H\) well conditioned and invertible even with dead input channels.
    When does GPTQ beat RTN by a lot, and when not?core
    The gain comes from correlated inputs (off-diagonal \(H\)) and from low bit widths, where rounding errors are large. If \(H\) is diagonal, compensation is zero and GPTQ equals RTN. At 8 bits both are near lossless. At 4 and especially 3 bits the gap is large: on OPT-175B, 3-bit RTN has perplexity about 7,300 while GPTQ has 8.68.
    How would you choose the calibration data, and what if it does not match deployment?core
    The paper used 128 random 2,048-token segments of C4, generic web text. More tokens make \(H\) better estimated; the data should cover the input distribution of deployment (for a code or chat model include code or chat-formatted text). With a mismatch, GPTQ fits each layer to the wrong input statistics; the model can do well on the calibration domain and worse elsewhere, so evaluate on held-out tasks from the real use.
    What are group size and act-order, and how do they interact?advanced
    Group size \(g\) gives every \(g\) consecutive weights of a row their own scale and zero point (overhead about \((16+b)/g\) bits per weight), which limits the damage from large weights. Act-order quantizes columns in order of decreasing \(H_{jj}\), so high-activation weights are quantized early while many weights can still compensate. Together, a group's columns are spread out in the original order, so the kernel needs a group index per column and loses some memory locality; "static groups" decide the groups before reordering to avoid this. [Likely]
    Weight-only 4-bit GPTQ: why does it speed up decoding more than prefill?core
    Decoding with a small batch is a sequence of matrix-vector products whose time is dominated by reading the weights; reading 4 times fewer bytes gives close to that speed-up, minus dequantization cost. Prefill and large batches are matrix-matrix products that are compute-bound, and the compute still happens in FP16 after dequantization, so the gain is small or can even be negative. The GPTQ paper measured 3.24× per token for 3-bit OPT-175B at batch size 1 on A100.
    How much memory does a 70B model need at 4 bits with group size 128?basic
    With an FP16 scale and a 4-bit zero point per group of 128: \(4 + 20/128 \approx 4.16\) bits per weight, so \(70 \times 10^9 \times 4.156/8 \approx 36.4\) GB, plus FP16 embeddings and output head, plus the KV cache. In FP16 it would be 140 GB.

Compensation: \(\delta_2 = \rho\,(w_1 - q_1) = (-0.9)(-0.4) = +0.36\), so \(w_2\) becomes \(0.96\), which rounds to 1. Same point \((1, 1)\), same error 0.032: here RTN was already the best choice. 3. The factor is \(\min\{11008, 4096\} = 4096\).     Key takeaways

    • Weight PTQ is solved layer by layer: keep \(WX\) close to \(\hat W X\) on calibration inputs (106.1). The error of each row is exactly \(\tfrac12 \delta H \delta^\top\) with \(H = 2XX^\top\) (106.2, 106.3).
    • \(H\) depends only on the inputs. Its diagonal says which weights matter; its off-diagonal says which weights can cancel each other's errors (106.4).
    • OBQ quantizes one weight and moves the free weights by \(-\frac{w_q - \operatorname{quant}(w_q)}{[H^{-1}]_{qq}}(H^{-1})_{:,q}\) (106.5), greedily (106.6), updating the inverse by Gaussian elimination (106.7). Accurate but \(O(d_{row} d_{col}^3)\).
    • GPTQ: one fixed column order for all rows (106.8), lazy block updates of 128 columns (106.9), dampening (106.10) and the Cholesky factor of \(H^{-1}\) computed once (106.11).
    • Result: 175B models at 3 to 4 bits in about 4 GPU hours, near-FP16 perplexity at 4 bits, and 3 to 4.5 times faster decoding with the right kernels.

    Key formulas

    \[ \min_{\hat W} \lVert WX - \hat W X\rVert_F^2, \quad H = 2XX^\top, \quad \delta_F = -\frac{w_q - \operatorname{quant}(w_q)}{[H_F^{-1}]_{qq}}\,(H_F^{-1})_{:,q} \]
    \[ H^{-1} = U^\top U, \qquad e_j = \frac{w_j - q_j}{U_{jj}}, \qquad \mathbf{w}_{j:} \leftarrow \mathbf{w}_{j:} - e_j\, U_{j,j:} \]
