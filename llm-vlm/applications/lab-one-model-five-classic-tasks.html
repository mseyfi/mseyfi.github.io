    Why this matters

    Five tasks have shaped NLP for twenty years: sentiment (is this text positive or negative?), named entity recognition (which words are people, places and companies?), natural language inference (does sentence A imply sentence B?), extractive question answering (which words of a passage answer the question?) and summarization (write a short version). In this lab you solve all five on their standard public datasets, with two kinds of models, and you write down the quality, the cost and the speed of each.

    The two kinds of models are the two answers that the industry gives today. The first is a fine-tuned encoder in the BERT style (session 33): a 108M-parameter model that reads the whole text in both directions, with a small task-specific output layer (a head) on top. The second is a small decoder LLM (Qwen2.5-0.5B-Instruct, 494M parameters) that treats every task as text in, text out: first only with a prompt, then with a LoRA adapter trained on the same examples as the encoder (session 57).

    The question is practical and comes up in every applied team: “Do we still need BERT, or can a small LLM do it?” The honest answer depends on the task, the metric, the latency budget and the price, and you can only give it with measurements. That is what this lab produces: one table, five rows, three methods, with the right metric and a cost column.

    Interview tipA common design question is “You need to tag entities in 50 million support tickets per day. Would you use an LLM?” A strong answer compares quality and cost per million examples, and knows that the encoder needs one forward pass while the decoder pays for every generated token (formulas 159.10 and 159.11 on this page).

    Step 1: one pretrained model, five task shapes

    The five tasks look different, but there are only three output shapes. Sentiment and NLI give one label per input. NER gives one label per token. Extractive QA gives a span: a start position and an end position inside the passage. Summarization is the odd one: it gives new text, so it needs a model that can generate.

    AnalogyA pretrained encoder is like an experienced reader who has read millions of pages. A head is a small form the reader fills in after reading: one box for “positive or negative”, one box per word for “what kind of name is this”, or two marks on the page for “the answer starts here and ends there”. The reader stays the same; only the form changes. A decoder LLM is a reader who answers every form by writing a sentence.

    For an encoder, each shape gets its own small head on top of the final hidden vectors \(\mathbf{h}_1, \dots, \mathbf{h}_n\) (one vector of size \(d = 768\) per token). For one label per input, BERT reads the vector of the special first token [CLS]:

    \[ p(y \mid x) = \softmax\!\left(W \mathbf{h}_{\text{[CLS]}} + \mathbf{b}\right)_y, \qquad W \in \R^{C \times d} \tag{159.1} \]

    For one label per token, the same kind of linear layer is applied to every token. A word such as “Blackburn” may be split into several sub-tokens; we put the label on the first sub-token only and ignore the others in the loss, as the BERT paper did [Certain]. With \(S\) the set of first sub-tokens:

    \[ \mathcal{L}_{\text{tok}} = -\frac{1}{|S|} \sum_{t \in S} \log \softmax\!\left(W \mathbf{h}_t + \mathbf{b}\right)_{y_t} \tag{159.2} \]

    For a span, two vectors \(\mathbf{w}_s\) and \(\mathbf{w}_e\) give every context token a start score and an end score. The answer is the pair with the highest total score, with the start before the end and at most \(L_{\max}\) tokens (we use 30):

    \[ s_i = \mathbf{w}_s^\top \mathbf{h}_i, \quad e_j = \mathbf{w}_e^\top \mathbf{h}_j, \qquad (\hat{i}, \hat{j}) = \argmax_{i \le j \le i + L_{\max} - 1} \; (s_i + e_j) \tag{159.3} \]
    Read the symbols
    \(\mathbf{h}_t\)
    the final hidden vector of token \(t\) (768 numbers for BERT-base)
    \(C\)
    the number of labels: 2 for SST-2, 3 for MNLI, 9 BIO tags for CoNLL-2003
    \(W, \mathbf{b}\)
    the new head, created with random values and trained with the rest of the model
    \(S\)
    the positions of the first sub-token of each word; other sub-tokens get the label -100, which the loss skips
    \(s_i, e_j\)
    the start score of token \(i\) and the end score of token \(j\); training uses cross-entropy over the start position and over the end position

    Every head is just a linear layer of size \((d + 1) \times C\):

    \[ |\theta_{\text{head}}| = (d + 1)\, C \tag{159.4} \]
    Worked example: the heads are tiny

    With \(d = 768\): SST-2 \(769 \times 2 = 1{,}538\), MNLI \(769 \times 3 = 2{,}307\), CoNLL-2003 \(769 \times 9 = 6{,}921\), SQuAD \(769 \times 2 = 1{,}538\) (one start and one end score). The full models have 108,311,810 parameters for SST-2 and 107,726,601 for NER: Hugging Face drops BERT’s pooler layer (590,592 weights) for token classification and QA, because those heads read every token, not [CLS]. So 99.99% of what you fine-tune is the shared encoder; the head is under 0.01%.

    The decoder has no task heads. It already has one head, the language-model head over 151,936 tokens, and every task becomes “write the answer as text”. Step through Figure 1 to compare the three ways for each task.

    Step 2: every task as text for the decoder

    For the two classification tasks we do not let the model write freely. A free answer can be “Positive!”, “The sentiment is positive” or a long explanation, and then the parser decides your accuracy. Instead we score each allowed label: we append the label to the prompt, add up the log-probabilities of its tokens, and pick the label with the highest total (session 144 calls this comparing label likelihoods):

    \[ \hat{y} = \argmax_{y \in \mathcal{Y}} \; \sum_{t=1}^{|y|} \log p_\theta\!\left(y_t \mid \text{prompt},\, y_{\lt t}\right) \tag{159.5} \]
    Read the symbols
    \(\mathcal{Y}\)
    the set of label words, such as {negative, positive}
    \(y_t\)
    the \(t\)-th token of label \(y\); in Qwen’s vocabulary “positive”, “negative” and “neutral” are one token each, while “entailment” and “contradiction” are three tokens each
    \(p_\theta\)
    the decoder’s next-token probability

    Summing log-probabilities can favor short labels, because every extra token adds a negative number. Once the model has written “contr”, the tokens “ad” and “iction” are almost certain, so the effect is usually small; still, check the confusion matrix for a bias toward “neutral”, and try the mean per token if you see one [Likely]. For the other three tasks the model must generate, and we use greedy decoding (always the most likely next token), so every run is repeatable.

    LoRA tuning uses the same prompts. Each training row is a (prompt, completion) pair, and the loss is next-token cross-entropy on the completion tokens \(C\) only, as in session 54:

    \[ \mathcal{L}_{\text{SFT}} = -\frac{1}{|C|} \sum_{t \in C} \log p_\theta\!\left(x_t \mid x_{\lt t}\right) \tag{159.6} \]

    With \(r = 16\) on all seven linear layers of every block, LoRA trains 8,798,208 weights, 1.78% of the model (session 62 derives this count). After training we merge the adapter into the weights, so the LoRA model has exactly the speed of the base model.

    Algorithm 1: one task, all methods, one set of rules
    1. input: task \(\tau\), train subset \(D_{tr}\) (5,000 rows, seed 0), test subset \(D_{te}\), metric \(m_\tau\)
    2. encoder: add the head for the shape of \(\tau\); fine-tune all weights on \(D_{tr}\) (3 epochs, LR \(2 \times 10^{-5}\))
    3. predict on \(D_{te}\); map sub-token or window outputs back to words or characters
    4. decoder, prompted: for \(k \in \{0, 3\}\): put the first \(k\) rows of \(D_{tr}\) in the prompt as examples
    5. if \(\tau\) is a classification task: label scoring (159.5) else: greedy generation, then parse
    6. decoder + LoRA: train an adapter on \(D_{tr}\) with loss (159.6), 1 epoch; merge it; predict 0-shot
    7. for every method: score with \(m_\tau\) on the same \(D_{te}\); save every prediction for paired tests
    8. measure p50 latency at batch 1 on 50 test inputs // bench.py, Step 6

    Step 3: the shared code

    One file holds everything that must be identical across methods: the data subsets, the prompts, the parsers and the metrics. The other scripts import it. Keeping this in one place is how you make sure that a difference in the table comes from the model and not from the plumbing.

    # tasks.py: the five tasks, their data, their prompts and their metrics
import os, re, string, collections
from datasets import load_dataset
from rouge_score import rouge_scorer

N_TRAIN = int(os.environ.get("N_TRAIN", 5000))   # same training examples for every method
N_EVAL = int(os.environ.get("N_EVAL", 1000))     # summarization uses at most 500
NER_TAGS = ["O", "B-PER", "I-PER", "B-ORG", "I-ORG", "B-LOC", "I-LOC", "B-MISC", "I-MISC"]
NLI_LABELS = ["entailment", "neutral", "contradiction"]
SST_LABELS = ["negative", "positive"]

def load(task):
    """Return (train, test) with a fixed seeded subset."""
    if task == "sst2":
        ds = load_dataset("nyu-mll/glue", "sst2"); tr, te = ds["train"], ds["validation"]
    elif task == "mnli":
        ds = load_dataset("nyu-mll/glue", "mnli"); tr, te = ds["train"], ds["validation_matched"]
    elif task == "conll":
        ds = load_dataset("lhoestq/conll2003"); tr, te = ds["train"], ds["test"]
    elif task == "squad":
        ds = load_dataset("rajpurkar/squad"); tr, te = ds["train"], ds["validation"]
    elif task == "cnndm":   # load one of the three train shards only: we need 5,000 rows, not 287k
        ds = load_dataset("abisee/cnn_dailymail", data_files={
            "train": "3.0.0/train-00000-of-00003.parquet", "test": "3.0.0/test-00000-of-00001.parquet"})
        tr, te = ds["train"], ds["test"]
    n_eval = min(N_EVAL, 500 if task == "cnndm" else N_EVAL, len(te))
    tr = tr.shuffle(seed=0).select(range(min(N_TRAIN, len(tr))))
    te = te.shuffle(seed=0).select(range(n_eval))
    return tr, te

# ---------- prompts for the decoder: (user message, target text) ----------
def to_chat(task, ex):
    if task == "sst2":
        u = ("Classify the sentiment of this movie review sentence. "
             "Answer with one word: positive or negative.\n\nSentence: " + ex["sentence"])
        return u, SST_LABELS[ex["label"]]
    if task == "mnli":
        u = ("Premise: " + ex["premise"] + "\nHypothesis: " + ex["hypothesis"] +
             "\n\nIs the hypothesis entailed by the premise, neutral, or a contradiction? "
             "Answer with one word: entailment, neutral or contradiction.")
        return u, NLI_LABELS[ex["label"]]
    if task == "conll":
        u = ("Find the named entities in the sentence. Types: PER (person), ORG (organization), "
             "LOC (location), MISC (other names). Write one entity per line as TYPE: text. "
             "Write NONE if there is no entity.\n\nSentence: " + " ".join(ex["tokens"]))
        ents = bio_to_spans(ex["tokens"], [NER_TAGS[t] for t in ex["ner_tags"]])
        return u, "\n".join(f"{t}: {s}" for t, s in ents) or "NONE"
    if task == "squad":
        u = ("Answer the question with a short span copied exactly from the context.\n\n"
             "Context: " + ex["context"] + "\n\nQuestion: " + ex["question"])
        return u, ex["answers"]["text"][0]
    if task == "cnndm":
        u = "Summarize the news article in three short sentences.\n\nArticle: " + ex["article"][:4000]
        return u, ex["highlights"]

LABELS = {"sst2": SST_LABELS, "mnli": NLI_LABELS}        # scored, not generated
MAX_NEW = {"conll": 64, "squad": 24, "cnndm": 128}

def gold(task, ex):
    if task == "sst2": return SST_LABELS[ex["label"]]
    if task == "mnli": return NLI_LABELS[ex["label"]]
    if task == "conll": return bio_to_spans(ex["tokens"], [NER_TAGS[t] for t in ex["ner_tags"]])
    if task == "squad": return ex["answers"]["text"]
    if task == "cnndm": return ex["highlights"]

def parse(task, text):
    """Turn the decoder's text into a prediction of the same type as gold()."""
    text = text.strip()
    if task == "conll":
        out = []
        for line in text.split("\n"):
            m = re.match(r"\s*(PER|ORG|LOC|MISC)\s*:\s*(.+?)\s*$", line)
            if m: out.append((m.group(1), m.group(2)))
        return out
    if task == "squad": return text.split("\n")[0]
    return text

# ---------- metrics ----------
def bio_to_spans(tokens, tags):
    """BIO tags -> list of (type, text). A stray I- tag starts a new entity (as in seqeval)."""
    spans, cur = [], None
    for tok, tag in zip(tokens, tags):
        if tag == "O" or tag.startswith("B-") or (cur and tag[2:] != cur[0]):
            if cur: spans.append((cur[0], " ".join(cur[1]))); cur = None
        if tag != "O":
            if cur is None: cur = (tag[2:], [])
            cur[1].append(tok)
    if cur: spans.append((cur[0], " ".join(cur[1])))
    return spans

def entity_prf(preds, golds):
    """Micro P/R/F1 over (type, text) entities, counted as multisets per sentence."""
    tp = n_pred = n_gold = 0
    for p, g in zip(preds, golds):
        cp, cg = collections.Counter(p), collections.Counter(g)
        tp += sum((cp & cg).values()); n_pred += sum(cp.values()); n_gold += sum(cg.values())
    P = tp / n_pred if n_pred else 0.0; R = tp / n_gold if n_gold else 0.0
    return {"precision": P, "recall": R, "f1": 2 * P * R / (P + R) if P + R else 0.0}

def norm_answer(s):           # the official SQuAD v1.1 normalization
    s = "".join(ch for ch in s.lower() if ch not in set(string.punctuation))
    s = re.sub(r"\b(a|an|the)\b", " ", s)
    return " ".join(s.split())

def squad_f1(pred, gt):
    p, g = norm_answer(pred).split(), norm_answer(gt).split()
    common = sum((collections.Counter(p) & collections.Counter(g)).values())
    if common == 0: return 0.0
    P, R = common / len(p), common / len(g)
    return 2 * P * R / (P + R)

def squad_em_f1(preds, golds):
    em = sum(max(float(norm_answer(p) == norm_answer(g)) for g in gs) for p, gs in zip(preds, golds))
    f1 = sum(max(squad_f1(p, g) for g in gs) for p, gs in zip(preds, golds))
    return {"em": em / len(preds), "f1": f1 / len(preds)}

_rouge = rouge_scorer.RougeScorer(["rouge1", "rouge2", "rougeLsum"], use_stemmer=True)
def rouge(preds, golds):      # rougeLsum wants one sentence per line
    nl = lambda s: "\n".join(x.strip() for x in re.split(r"(?<=[.!?])\s+", s.strip()) if x.strip())
    sc = [_rouge.score(nl(g), nl(p)) for p, g in zip(preds, golds)]
    return {k: sum(s[k].fmeasure for s in sc) / len(sc) for k in ["rouge1", "rouge2", "rougeLsum"]}

def score(task, preds, golds):
    if task in ("sst2", "mnli"):
        return {"accuracy": sum(p == g for p, g in zip(preds, golds)) / len(golds)}
    if task == "conll": return entity_prf(preds, golds)
    if task == "squad": return squad_em_f1(preds, golds)
    if task == "cnndm": return rouge(preds, golds)

    Three details in this file matter. First, bio_to_spans turns BIO tags into entities the same way for the encoder and for the gold labels, and treats a stray I- tag as the start of a new entity, as the standard seqeval package does in its default mode. Second, norm_answer is the normalization of the official SQuAD v1.1 evaluation script: lower case, remove punctuation, remove the articles “a”, “an”, “the”, and collapse spaces. Third, ROUGE-Lsum needs one sentence per line, so rouge() splits the text into sentences first; without that, rougeLsum is the same as plain rougeL [Certain].

    # encoder.py: fine-tune BERT on one task.  Usage: python encoder.py conll
import sys, os, json, numpy as np, torch
from transformers import (AutoTokenizer, AutoModelForSequenceClassification, AutoModelForTokenClassification,
                          AutoModelForQuestionAnswering, Trainer, TrainingArguments, DataCollatorWithPadding,
                          DataCollatorForTokenClassification, set_seed)
from tasks import load, score, gold, bio_to_spans, NER_TAGS, SST_LABELS, NLI_LABELS

task = sys.argv[1]; set_seed(0)
ENC = os.environ.get("ENC", "google-bert/bert-base-cased")   # cased: capital letters matter for NER
tok = AutoTokenizer.from_pretrained(ENC)
tr, te = load(task)
args = TrainingArguments(output_dir=f"out/enc-{task}", learning_rate=3e-5 if task == "squad" else 2e-5,
                         num_train_epochs=float(os.environ.get("EPOCHS", 3)), per_device_train_batch_size=32,
                         per_device_eval_batch_size=64, warmup_ratio=0.1, weight_decay=0.01,
                         max_steps=int(os.environ.get("MAX_STEPS", -1)), bf16=torch.cuda.is_available(),
                         save_strategy="no", report_to="none", seed=0, logging_steps=50)

if task in ("sst2", "mnli"):                       # one label per text (or text pair)
    names = SST_LABELS if task == "sst2" else NLI_LABELS
    enc = (lambda b: tok(b["sentence"], truncation=True, max_length=128)) if task == "sst2" else \
          (lambda b: tok(b["premise"], b["hypothesis"], truncation=True, max_length=128))
    model = AutoModelForSequenceClassification.from_pretrained(ENC, num_labels=len(names))
    trainer = Trainer(model=model, args=args, train_dataset=tr.map(enc, batched=True),
                      data_collator=DataCollatorWithPadding(tok))
    trainer.train()
    logits = trainer.predict(te.map(enc, batched=True)).predictions
    preds = [names[i] for i in logits.argmax(-1)]

elif task == "conll":                              # one label per word
    def enc(b):
        out = tok(b["tokens"], is_split_into_words=True, truncation=True, max_length=256)
        out["labels"] = []
        for i, tags in enumerate(b["ner_tags"]):
            prev, lab = None, []
            for w in out.word_ids(i):              # label only the FIRST sub-token of each word
                lab.append(-100 if w is None or w == prev else tags[w]); prev = w
            out["labels"].append(lab)
        return out
    model = AutoModelForTokenClassification.from_pretrained(ENC, num_labels=len(NER_TAGS))
    trainer = Trainer(model=model, args=args, train_dataset=tr.map(enc, batched=True, remove_columns=tr.column_names),
                      data_collator=DataCollatorForTokenClassification(tok))
    trainer.train()
    te_enc = te.map(enc, batched=True, remove_columns=te.column_names)
    out = trainer.predict(te_enc)
    preds = []
    for ex, lg, lab in zip(te, out.predictions, out.label_ids):
        tags = [NER_TAGS[p] for p, l in zip(lg.argmax(-1), lab) if l != -100]   # back to one tag per word
        tags += ["O"] * (len(ex["tokens"]) - len(tags))                             # words cut by truncation

Notes on the two hard cases:

    • NER: sub-tokens back to words. The model predicts one tag per sub-token. We keep the prediction of the first sub-token of each word, so the number of predicted tags equals the number of words, and then we build entities with the same function as for the gold tags.
    • QA: windows over long passages. A SQuAD passage plus question is 183.6 BERT tokens on average in our test subset, but 6 of the 1,000 are longer than 512 tokens. The tokenizer cuts long inputs into windows of 384 tokens that overlap by 128 (stride). In training, a window that does not contain the answer is labeled with position 0 (the [CLS] token). In evaluation, we search the top 20 start and top 20 end scores in every window, keep spans of at most 30 tokens, and map the best span back to characters with the offset mapping (the character positions of every token).

    Why Lead-3? News articles put the main facts first. Copying the first three sentences is a strong summarization baseline on CNN/DailyMail, and many abstractive models of the 2017 era did not clearly beat it on ROUGE [Likely]. It costs nothing and needs no GPU. If your LoRA summarizer does not beat Lead-3, report that honestly.

That is one reason why summarization moved to encoder-decoder models (BART, T5, with 1,024 or more input tokens) and then to decoder LLMs.

    Step 6: the right metric for each task

    The table mixes five metrics. Each one exists because a simpler number would mislead. This step shows how.

    NER: entity F1, not token accuracy

    In the CoNLL-2003 test set, 82.5% of the 46,435 tokens have the tag O (not an entity). A model that predicts O everywhere has 82.5% token accuracy and finds no entity at all. So NER is scored on entities: an entity counts as correct only if its type and its exact boundaries are both right.

    \[ P = \frac{|\text{pred} \cap \text{gold}|}{|\text{pred}|}, \qquad R = \frac{|\text{pred} \cap \text{gold}|}{|\text{gold}|}, \qquad F_1 = \frac{2PR}{P + R} \tag{159.7} \]
    Read the symbols
    pred, gold
    the sets of predicted and true entities, each a triple (type, start, end) for the encoder, summed over all sentences (micro average)
    \(P, R\)
    precision: the share of predicted entities that are right; recall: the share of true entities that were found

    The decoder writes entity text, not positions. So in tasks.py we compare (type, text) pairs per sentence for both models, counted as multisets. This is a slightly easier test than position matching: if the same name appears twice in a sentence and the model finds it once, position matching knows which one it found, and text matching does not. On CoNLL this rarely matters, but say which version you report [Likely].

    QA: exact match and F1 after normalization

    SQuAD has up to three human answers per question in the validation set, and they often differ by a word (“1889” versus “March 1889”). The official script normalizes each string, then computes two scores and keeps the best over the gold answers \(G\):

    \[ \text{EM} = \max_{g \in G} \mathbb{1}\!\left[\operatorname{norm}(\hat{a}) = \operatorname{norm}(g)\right], \qquad F_1 = \max_{g \in G} \frac{2\, P_g R_g}{P_g + R_g}, \quad P_g = \frac{c_g}{|\hat{a}|},\; R_g = \frac{c_g}{|g|} \tag{159.8} \]
    Read the symbols
    \(\hat{a}, g\)
    the predicted answer and one gold answer, as lists of normalized words
    \(c_g\)
    the number of shared words (each word counted at most as often as it appears in both)
    \(\mathbb{1}[\cdot]\)
    1 if the two normalized strings are identical, else 0
    Worked example: F1 for “May 1889”

    Normalized prediction: [may, 1889], 2 words. Gold “March 1889”: 1 shared word, \(P = 1/2\), \(R = 1/2\), \(F_1 = 0.5\). Gold “1889”: 1 shared word, \(P = 1/2\), \(R = 1/1\), \(F_1 = 2 \cdot 0.5 \cdot 1 / 1.5 = 0.667\). Gold “in March 1889”: \(P = 1/2\), \(R = 1/3\), \(F_1 = 0.4\). The maximum is 0.667, and EM is 0.

    Summarization: ROUGE, and its limits

    ROUGE counts overlapping words (ROUGE-1), word pairs (ROUGE-2) and the longest common subsequence with the reference (session 149 derives all three). For multi-sentence summaries such as CNN/DM highlights, the usual choice is ROUGE-Lsum, which computes the longest common subsequence sentence by sentence. Two warnings. ROUGE rewards copying: Lead-3 copies the article and scores well. And ROUGE cannot see a wrong fact that uses the right words. Read 20 summaries yourself, and if you need a quality judgment, add an LLM judge with position swapping as in the session 62 lab.

    Is a difference real?

    Every number in your table is an estimate from a small test set. For an accuracy \(\hat{p}\) on \(n\) examples:

    \[ \mathrm{SE}(\hat{p}) = \sqrt{\frac{\hat{p}\,(1 - \hat{p})}{n}} \tag{159.9} \]

    With \(\hat{p} = 0.90\) on the 872 SST-2 sentences, SE = 0.0102, so a 95% interval is about \(\pm 2.0\) points. With \(\hat{p} = 0.80\) on 1,000 MNLI pairs, it is \(\pm 2.5\) points. Two methods 1.5 points apart are not clearly different on these test sets. For F1, EM and ROUGE there is no simple formula, so use a paired bootstrap: because all methods predict on the same examples, resample the examples and recompute the difference.

    Algorithm 2: paired bootstrap for the difference between two methods
    1. input: per-example predictions of methods \(a\) and \(b\) on the same \(n\) test examples, a metric \(m\), \(B = 1{,}000\) rounds, a fixed seed
    2. \(\Delta \leftarrow m(a) - m(b)\) on the full test set
    3. for \(r = 1, \dots, B\):
    4. draw \(n\) example indices with replacement
    5. \(\Delta_r \leftarrow m(a) - m(b)\) on those indices // the same indices for both methods
    6. report \(\Delta\) and the 2.5% and 97.5% quantiles of \(\Delta_1, \dots, \Delta_B\)
    7. if the interval contains 0: the difference is not clear on this test set

    For entity F1, resample whole sentences, not entities, and recompute the micro F1 from the resampled counts. The pairing is what makes this test strong: most examples are easy for both methods and cancel out.

    Step 7: cost and latency

    Quality is half the answer. The other half is what each prediction costs. Start with the compute. A forward pass costs about 2 FLOPs per weight per token (one multiply and one add), as in session 25. For an encoder that reads \(n_{in}\) tokens once, and a decoder that reads a prompt of \(n_p\) tokens and then writes \(n_{out}\) tokens:

    \[ C_{\text{enc}} \approx 2\, N_E\, n_{in}, \qquad C_{\text{dec}} \approx 2\, N_D \left(n_p + n_{out}\right) \tag{159.10} \]

    But at batch size 1 the FLOPs do not decide the time. The decoder writes its answer one token at a time, and each new token needs a full pass over the weights (session 78). Reading 494M BF16 weights is 0.988 GB per token. So a simple lower bound on the time (a “roofline”) takes the larger of the compute time and the memory time for each pass:

    \[ T \approx \max\!\left(\frac{2 N_D\, n_p\, b}{F}, \frac{2 N_D}{BW}\right) + (n_{out} - 1)\max\!\left(\frac{2 N_D\, b}{F}, \frac{2 N_D + b\, n_{ctx}\, \kappa}{BW}\right) \tag{159.11} \]
    Read the symbols
    \(N_E, N_D\)
    weights used in matrix multiplications: 85,645,056 for BERT-base (all but the embedding tables), 494,032,768 for Qwen2.5-0.5B (its tied embedding is also the output layer, so it is read at every step)
    \(F, BW\)
    the GPU’s peak dense BF16 FLOP rate and its memory bandwidth
    \(b\)
    the batch size; \(T\) is the time for the whole batch, so the time per example is \(T / b\)
    \(n_{ctx}, \kappa\)
    tokens already in the KV cache, and KV-cache bytes per token. For Qwen2.5-0.5B: K and V, 24 layers, 2 KV heads of size 64, 2 bytes each, so \(\kappa = 2 \cdot 24 \cdot 2 \cdot 64 \cdot 2 = 12{,}288\)

    The first term is the prefill (all prompt tokens in one pass); the second is the decode loop. The encoder has only the first term. The money follows directly. With a GPU price of \(c\) dollars per hour:

    \[ \text{cost per } 10^6 \text{ examples} = \frac{c}{3600} \cdot \frac{T}{b} \cdot 10^6 \tag{159.12} \]
    Worked example: QA on one L4 at batch 1

    Encoder, 183.6 tokens: compute \(2 \times 85.6\text{M} \times 183.6 / 121 \times 10^{12} = 0.26\) ms; memory \(0.171 \text{ GB} / 300 \text{ GB/s} = 0.571\) ms. The larger one wins: 0.571 ms.

    Decoder, 228.5 prompt tokens and 5.7 answer tokens (including the end token): the prefill compute is \(2 \times 494\text{M} \times 228.5 / 121 \times 10^{12} = 1.87\) ms, its memory time is \(0.988 / 300 = 3.29\) ms, so 3.29 ms. Then 4.7 decode steps of 3.29 ms each, plus a little for reading the KV cache: 15.52 ms. Total 18.82 ms. At $1 per GPU-hour, one million questions cost $0.16 with the encoder and $5.23 with the decoder, before any real-world overhead.

    The estimate ignores attention FLOPs, kernel launch overheads, tokenization and Python time, so real numbers are higher, often by a factor that is larger for small models [Likely]. Measure p50 and p90 latency (the median and the 90th percentile) yourself:

    Step 8: a toy you can run anywhere

    Before the GPU runs, here is the whole idea in about 70 lines of plain PyTorch, small enough for any CPU. A toy language has filler words, “names”, the words “good” and “bad”, and an answer marker “@”. One shared Transformer encoder is trained with three heads at once: a sequence label (more “good” or more “bad”?), BIO tags for names, and a start and end score for the name after “@”. The losses are just added.

    import torch, torch.nn as nn, torch.nn.functional as F
torch.manual_seed(0); torch.set_num_threads(1)

# A toy language: ids 0-9 are filler words, 10-19 names, 20 = "good", 21 = "bad", 22 = "@" (answer marker)
V, T, D = 23, 16, 64
def make(n, g):
    x = torch.randint(0, 10, (n, T), generator=g)
    tags = torch.zeros(n, T, dtype=torch.long)                        # 0 = O, 1 = B-NAME, 2 = I-NAME
    for i in range(n):
        for _ in range(2):                                            # two names of length 1 to 3
            L = int(torch.randint(1, 4, (1,), generator=g)); s = int(torch.randint(1, T - L, (1,), generator=g))
            if tags[i, s - 1:s + L + 1].any(): continue               # keep names apart
            x[i, s:s + L] = torch.randint(10, 20, (L,), generator=g); tags[i, s] = 1; tags[i, s + 1:s + L] = 2
    span = torch.zeros(n, 2, dtype=torch.long)                         # QA: the name right after "@"
    for i in range(n):
        st = int((tags[i] == 1).nonzero()[0]); en = st
        while en + 1 < T and tags[i, en + 1] == 2: en += 1
        x[i, st - 1] = 22; span[i] = torch.tensor([st, en])
    pol = torch.randint(0, 2, (n,), generator=g)                       # sentiment: 2 of one word, 1 of the other
    for i in range(n):
        free = ((tags[i] == 0) & (x[i] != 22)).nonzero().flatten()
        pos = free[torch.randperm(len(free), generator=g)[:3]]
        x[i, pos[:2]] = 20 if pol[i] == 1 else 21; x[i, pos[2]] = 21 if pol[i] == 1 else 20
    return x, pol, tags, span

class Model(nn.Module):                                                # ONE encoder, three small heads
    def __init__(self):
        super().__init__()
        self.emb = nn.Embedding(V, D); self.pos = nn.Parameter(torch.randn(T, D) * 0.02)
        layer = nn.TransformerEncoderLayer(D, 4, 128, dropout=0.0, batch_first=True)
        self.enc = nn.TransformerEncoder(layer, 2)
        self.cls = nn.Linear(D, 2)          # sequence classification: 2 labels
        self.tag = nn.Linear(D, 3)          # token classification: O, B, I
        self.span = nn.Linear(D, 2)         # extractive QA: a start score and an end score per token
    def forward(self, x):
        h = self.enc(self.emb(x) + self.pos)
        return self.cls(h.mean(1)), self.tag(h), self.span(h).unbind(-1)

def spans(tags):                                                       # BIO -> set of (start, end)
    out, s = set(), None
    for t, y in enumerate(tags + [0]):
        if s is not None and y != 2: out.add((s, t - 1)); s = None
        if y == 1 or (y == 2 and s is None): s = t
    return out

g = torch.Generator().manual_seed(0)
xtr, ptr, ttr, str_ = make(2000, g); xte, pte, tte, ste = make(500, g)
m = Model(); opt = torch.optim.AdamW(m.parameters(), lr=3e-3)
for step in range(300):

    Common mistakes

    1. Different training data per method. The encoder gets the full training set, the LLM gets 5,000 rows, or the shots come from the test set. Fix the subsets once, in one file.
    2. Token accuracy for NER. An all-O tagger gets 82.5% token accuracy on CoNLL-2003 with zero entities found. Report entity F1, and say whether you match by position or by text.
    3. Labels on every sub-token. If all sub-tokens of “Blackburn” get I-PER while only the first is compared, or the reverse, your F1 silently changes. Label the first sub-token, use -100 elsewhere, and map back to words the same way at test time.
    4. Truncating SQuAD contexts instead of using windows. Answers past token 384 become impossible. Use stride and return_overflowing_tokens, and map back with offsets.
    5. Letting the parser decide the score. Free-form classification answers (“The sentiment is clearly positive!”) need a parser that will be wrong sometimes. Use label scoring (159.5), or a strict format and a count of unparseable outputs.
    6. Using rougeLsum without newlines. Without one sentence per line it equals rougeL, and your numbers will not match published ones.
    7. Comparing latency with different batch sizes or prompts. The decoder’s cost depends heavily on the batch size and on the number of shots in the prompt (Figure 4). Report both next to every latency.
    8. Declaring a winner from a 1-point gap. On 872 or 1,000 examples the 95% interval is about ±2 points (159.9). Use the paired bootstrap (Algorithm 2).

    Interview questions

    Why is NER scored with entity-level F1 and not token accuracy?basic
    Most tokens are not entities: 82.5% of CoNLL-2003 test tokens have the tag O. A model that predicts O everywhere gets high token accuracy and finds nothing. Entity F1 counts an entity as correct only if its type and both boundaries are right, so a model that tags “York” instead of “New York” gets no credit for that entity. Precision punishes extra or split entities, recall punishes missed ones, and F1 balances both.
    How does BERT handle a word that is split into several sub-tokens for NER?core
    The tokenizer’s word_ids() tells which word each sub-token belongs to. In training, the first sub-token of each word gets the word’s label, and the other sub-tokens get -100 so the loss ignores them (formula 159.2). At test time you take the prediction of the first sub-token of each word, so you get exactly one tag per word, then build entities from the BIO tags. Labeling all sub-tokens is also possible, but training and evaluation must use the same rule.
    Explain exact match and F1 in SQuAD. Why report both?basic
    Both first normalize the strings: lower case, no punctuation, no articles, single spaces. EM is 1 if the normalized prediction equals one of the gold answers. F1 is the word-overlap F1 with the best gold answer. EM is strict: a correct but longer answer gets 0. F1 gives partial credit, but also to wrong answers that share words; “May 1889” gets F1 0.667 against the gold “1889”. Reported together, they show both exactness and closeness.
    How does a BERT QA model deal with passages longer than 512 tokens?core
    It cuts the passage into overlapping windows (for example 384 tokens with a stride of 128 tokens of overlap), each with the question in front. In training, a window that does not contain the answer is labeled with the [CLS] position. At test time each window proposes its best spans; we keep the highest start plus end score over all windows, with start before end and a maximum length, and map the token span back to characters with the offset mapping.
    You use a decoder LLM for sentiment. Why score the label words instead of generating an answer?core
    Generation can produce any text, and a parser must then guess the label, which adds errors that are not the model’s understanding. Label scoring (159.5) computes the log-probability of each allowed label after the prompt and picks the best, so every output is valid, the result is deterministic, and you also get a score you can calibrate or threshold. The cost is one forward pass over the prompt and the labels; no decoding loop is needed. Watch for length bias when labels have different numbers of tokens.
    Why can’t you summarize CNN/DailyMail with BERT, and what is Lead-3?basic
    An encoder outputs one vector per input token; it has no mechanism to generate new tokens one after another. You could build an extractive summarizer that scores sentences with an encoder, but abstractive summaries need a decoder (BART, T5 or a decoder LLM). Also, most CNN/DM articles are longer than BERT’s 512-token limit (396 of our 500 test articles). Lead-3 takes the first three sentences of the article; because news puts key facts first, it is a strong, free baseline that any summarizer must beat.
    Estimate the batch-1 latency of BERT-base versus a 0.5B decoder on an extractive QA example on a GPU with 300 GB/s.advanced
    At batch 1 both are limited by reading weights. BERT-base multiplies about 85.6M weights, 0.171 GB in BF16: one pass takes at least 0.57 ms. The decoder reads 0.988 GB per pass: 3.3 ms for the prefill and 3.3 ms for each of the 4.7 decode steps after it, about 18.8 ms in total, roughly 33 times the encoder. In practice add overheads, but the ratio shows the key point: the decoder pays per generated token, the encoder pays once.
    Why does batching help the decoder more than the encoder?advanced
    At batch 1 a decode step reads all weights to do only 2 FLOPs per weight, so the GPU’s compute is mostly idle (memory-bound). With batch b, the same weight read serves b sequences, so the time per example drops almost by b until compute or KV-cache reads become the limit. An encoder pass already processes all its input tokens at once, so it becomes compute-bound at a small batch and gains less. This is also why serving engines use continuous batching for decoders.
    Your LoRA-tuned decoder scores 1 point higher than BERT on 1,000 MNLI examples. Is it better?core
    Not clearly. At 80% accuracy on 1,000 examples, the standard error is 1.26 points and the 95% interval is about ±2.5 points per method. Since both methods predict the same examples, use a paired test: a paired bootstrap of the accuracy difference, or McNemar’s test on the examples where exactly one method is right. Even if the difference is real, weigh it against the cost: the decoder is several to many times slower per example (Figure 4).
    When would you choose a small decoder LLM over a fine-tuned encoder for a classic task?advanced
    When one model must serve many tasks (one base model plus small adapters), when the label set or schema changes often (a prompt change instead of retraining a head), when there are almost no labels (prompting works from zero examples), or when the output is free text such as a summary or an explanation. Choose the encoder when volume is high, latency is tight, labels are fixed and you have a few thousand labeled examples: then it is usually as good or better and far cheaper.
    Why must the decoder use left padding in batched generation, while the encoder does not care?core
    A decoder generates the next token after the last position of each row. With right padding, the shorter prompts end in pad tokens, so the model would continue after the padding. With left padding, all prompts end at the same position and generation continues right after the real text; the attention mask hides the pads. An encoder reads all tokens at once and the head reads fixed positions ([CLS] or each token), so pads on the right are simply masked.

    Key takeaways

    • Five tasks, three output shapes: one label per input (159.1), one label per token (159.2), a span (159.3), plus free text for summaries. Encoder heads are tiny (159.4): 1,538 to 6,921 weights on a 108M model.
    • A decoder LLM handles every task as text. Use label scoring (159.5) for classification and strict formats plus a parser for the rest; LoRA (159.6) teaches the format and the task with 1.78% of the weights.
    • Use the right metric: accuracy for SST-2 and MNLI, entity F1 (159.7) for NER, EM and F1 (159.8) for SQuAD, ROUGE-Lsum for CNN/DM, and always the same test examples for all methods.
    • On 1,000 examples a 95% interval is about ±2 points (159.9). Use paired tests before you call a winner.
    • At batch 1, the encoder pays one pass; the decoder pays one pass per generated token (159.11). For QA on an L4 the lower bound is 0.57 ms versus 18.8 ms; batching narrows the gap.
    • Pick the encoder for high-volume, fixed-label tasks; pick the decoder when tasks change, outputs are text, or one model must do everything.
