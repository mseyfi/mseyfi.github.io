    Vector search at scale

    A retrieval system turns every document, image or video frame into a vector, and then must find the closest vectors to a query among millions or billions, in a few milliseconds. This session shows why exact search is too slow and too big at that scale, and how three ideas fix it: clusters (IVF), compression (PQ) and graphs (HNSW). We do the memory and speed math, measure the recall versus latency trade-off, and end with FAISS on CPU and GPU, filters and updates.

    Time: 3 to 4 hours (reading 2 hours, exercises 1 to 2 hours)Level: Intermediate to interview levelBefore this: Sessions 11 and 150 (embeddings and semantic search), basic k-means

    What you will learn

    • Exact k-nearest-neighbor search: inner product, cosine and L2, why it is one matrix multiply, and what it costs in memory and time
    • Approximate nearest neighbor (ANN) search and its one quality number, recall@k
    • IVF: cluster the database with k-means, search only nprobe lists, and choose nlist from the cost formula
    • Product quantization: store each vector in a few bytes, and score it with table lookups (asymmetric distance computation)
    • HNSW: a layered small-world graph, greedy search from the top, and the parameters M, efConstruction and efSearch
    • Memory and speed math for 100 million vectors, and how to read a recall versus latency curve
    • FAISS index strings, CPU vs GPU, metadata filters, adds, deletes and re-training

    Why this matters

    In session 150 we turned text into vectors and found the best documents by comparing a query vector with every document vector. That works for ten thousand documents. A real company has one hundred million documents, a photo app has billions of images, and a video platform has one vector for every second of every video. Comparing with all of them for every query is too slow and needs too much memory.

    Vector search is the job of finding the \(k\) stored vectors closest to a query vector. At scale we accept a small loss of quality to win a large gain in speed and memory: we find most of the true nearest neighbors, not always all of them. This is called approximate nearest neighbor (ANN) search. Every retrieval-augmented generation (RAG) system (session 152), every image and video search engine, every recommendation system and every duplicate detector has an ANN index inside it.

    Three ideas carry almost all of the field, and this session builds each one by hand:

    • IVF (inverted file): cluster the vectors, and at query time look only inside the few clusters closest to the query.
    • PQ (product quantization): compress each vector from thousands of bytes to a few dozen bytes, and compute distances on the compressed codes.
    • HNSW (hierarchical navigable small world): link the vectors into a graph and walk the graph toward the query.
    Interview tip“Design semantic search over 100 million documents” is a common system-design question. The interviewer wants numbers: how many GB is the raw index, does it fit on one machine, which index type, what recall at what latency, and how you handle filters and updates. Every one of these is computed below.

    The tools are mature. FAISS, the library from Meta, implements all three ideas on CPU and GPU [Certain]. Vector databases (Milvus, Qdrant, Weaviate, pgvector, Elasticsearch and others) wrap the same algorithms with storage, filters and replication. [Likely] If you understand IVF, PQ and HNSW, you can read the settings of any of them.

    Exact search and what it costs

    We have \(N\) database vectors \(\mathbf{x}_1, \dots, \mathbf{x}_N \in \R^d\) and a query \(\mathbf{q} \in \R^d\). A similarity \(s(\mathbf{q}, \mathbf{x})\) says how close two vectors are (larger means closer). The exact k-nearest-neighbor (kNN) answer is the set of the \(k\) indices with the largest similarity:

    \[ \mathcal{N}_k(\mathbf{q}) = \operatorname{top-}k_{\,i \in \{1..N\}} \; s(\mathbf{q}, \mathbf{x}_i) \tag{151.1} \]

    Three similarities are common. Inner product \(\mathbf{q}^\top \mathbf{x}\). Cosine \(\mathbf{q}^\top \mathbf{x} / (\lVert \mathbf{q} \rVert \lVert \mathbf{x} \rVert)\). Negative L2 distance \(-\lVert \mathbf{q} - \mathbf{x} \rVert\). They are closely related:

    \[ \lVert \mathbf{q} - \mathbf{x} \rVert^2 = \lVert \mathbf{q} \rVert^2 + \lVert \mathbf{x} \rVert^2 - 2\, \mathbf{q}^\top \mathbf{x} \tag{151.2} \]
    Read the symbols
    \(\mathbf{q}, \mathbf{x}\)
    the query vector and one database vector, both with \(d\) numbers
    \(\lVert \cdot \rVert\)
    the length (L2 norm) of a vector
    \(\mathbf{q}^\top \mathbf{x}\)
    the inner product: multiply the numbers pairwise and add them up

    If all vectors are normalized to length 1, then \(\lVert \mathbf{q} - \mathbf{x} \rVert^2 = 2 - 2\,\mathbf{q}^\top \mathbf{x}\), and the three similarities give the same ranking. That is why most text-embedding pipelines normalize once and then use inner product everywhere. [Certain]

    Exact search is one matrix multiply

    Put the database in a matrix \(X \in \R^{N \times d}\) and a batch of \(B\) queries in \(Q \in \R^{B \times d}\). All similarities at once are \(S = Q X^\top \in \R^{B \times N}\), followed by a top-\(k\) per row. On a GPU this is a large matrix multiply, the operation GPUs do best (session 126). FAISS calls this a flat index: no structure, just the raw vectors.

    The cost has two parts. The work is \(N d\) multiply-adds per query. The memory traffic is reading all \(N d\) numbers. For one query at a time, reading memory is the bottleneck, so the time is about

    \[ t_{\text{flat}} \approx \frac{N \cdot d \cdot b}{\text{BW}} \tag{151.3} \]
    Read the symbols
    \(N, d\)
    number of stored vectors and their dimension
    \(b\)
    bytes per number: 4 for FP32, 2 for FP16, 1 for INT8
    \(\text{BW}\)
    memory bandwidth in bytes per second

    A batch of \(B\) queries reads the database once and reuses it \(B\) times, so batching makes exact search compute-bound and much cheaper per query. This is the same reuse argument as for decode in LLM serving (session 42).

    Worked example: 100 million documents, exact search

    Take \(N = 10^8\) vectors with \(d = 768\) in FP32. Storage: \(10^8 \times 768 \times 4 = 307.2\) GB. In FP16 it is 153.6 GB. Neither fits in one 80 GB GPU.

    One query needs \(10^8 \times 768 = 7.68 \times 10^{10}\) multiply-adds. If it reads the FP32 data at the 3.35 TB/s of an H100 (if the data could fit there), formula (151.3) gives \(307.2 / 3350 \approx 0.092\) s, so 92 ms. On a CPU server, assume about 100 GB/s: 3.07 s per query. A search engine needs a few milliseconds. We need to look at fewer vectors, store fewer bytes per vector, or both.

    Exact search is still the right choice more often than people think. Below a few million vectors, or with large query batches on a GPU, a flat index is simple, has perfect recall, and is fast enough. [Likely] It is also always needed to compute the ground truth that you measure every ANN index against.

    Approximate search and recall@k

    An ANN index returns a set \(\mathcal{A}_k(\mathbf{q})\) of \(k\) results that may differ from the true set \(\mathcal{N}_k(\mathbf{q})\). Its quality is measured by recall@k: the fraction of the true \(k\) nearest neighbors that the index found, averaged over many test queries:

    \[ \text{recall@}k = \frac{1}{|\mathcal{Q}|} \sum_{\mathbf{q} \in \mathcal{Q}} \frac{|\mathcal{A}_k(\mathbf{q}) \cap \mathcal{N}_k(\mathbf{q})|}{k} \tag{151.4} \]
    Read the symbols
    \(\mathcal{Q}\)
    a set of test queries (a few hundred to a few thousand)
    \(\mathcal{A}_k, \mathcal{N}_k\)
    the approximate answer and the exact answer, each with \(k\) items
    \(|\cdot \cap \cdot|\)
    how many items the two sets share

    Note that this recall is about the index, not about relevance. In session 150, recall@k compared the results with human labels. Here we compare with what exact search would return. A perfect index (recall 1.0) still returns wrong documents if the embedding model is bad. In practice, an ANN recall of 0.9 to 0.95 costs little end-to-end quality, because a reranker or the LLM sees the top results anyway. [Likely] Measure it on your own data.

    AnalogyA library with ten million books. Exact search reads every spine. IVF is the floor plan: walk only to the two or three shelves whose topic is closest to your question. PQ is the card catalog: a tiny card per book, so the whole catalog fits on one desk. HNSW is asking people: each reader knows a few others with similar taste, and you keep asking whoever is closer to what you want.

    Why not use a tree, like a k-d tree, to search exactly but fast? In 2 or 3 dimensions trees work very well. In hundreds of dimensions they do not: almost every branch can contain a near neighbor, so the tree ends up visiting most of the data. This is part of the curse of dimensionality. [Certain] ANN methods give up exactness and gain speed.

    IVF: search only the nearby clusters

    Training. Run k-means on (a sample of) the database to get \(n_{\text{list}}\) centroids \(\mathbf{c}_1, \dots, \mathbf{c}_{n_\text{list}}\). The centroids are called the coarse quantizer. Adding. Put each vector into the list of its nearest centroid. Each list is an inverted list (the name comes from text search, where a word points to the list of documents that contain it). Searching. Compare the query with all centroids, open the \(n_{\text{probe}}\) closest lists, and search exactly inside them.

    The cost of one query in multiply-adds, if lists have about equal size:

    \[ C_{\text{IVF}} = n_{\text{list}} \cdot d \;+\; n_{\text{probe}} \cdot \frac{N}{n_{\text{list}}} \cdot d \tag{151.5} \]
    Read the symbols
    \(n_{\text{list}}\)
    number of clusters (inverted lists)
    \(n_{\text{probe}}\)
    number of lists opened per query; the main speed/recall knob
    \(N / n_{\text{list}}\)
    the average number of vectors in one list

    The first term grows with \(n_\text{list}\), the second shrinks. Setting the derivative to zero gives the best number of lists and the smallest cost:

    \[ n_{\text{list}}^{*} = \sqrt{n_{\text{probe}} \, N}, \qquad C_{\text{IVF}}^{*} = 2\, d \sqrt{n_{\text{probe}}\, N} \tag{151.6} \]

    So the cost grows with \(\sqrt{N}\), not with \(N\). The FAISS guidelines recommend \(n_\text{list}\) between \(4\sqrt{N}\) and \(16\sqrt{N}\), and between \(30\) and \(256\) training vectors per centroid for k-means. [Certain] (More lists than the formula's optimum is fine, because the centroid search can itself be made fast, for example with a small HNSW over the centroids.)

    The weakness of IVF is the border problem. The true nearest neighbor of a query near the edge of a cell often lives in the cell next door. With \(n_\text{probe} = 1\) it is missed. Try it in Figure 1: put the query on a border between two clusters.

    Worked example: IVF for 100 million vectors

    \(\sqrt{N} = 10{,}000\), so the guideline range is 40,000 to 160,000 lists. Take \(n_\text{list} = 65{,}536\) (\(= 2^{16}\), which is \(6.55\sqrt{N}\)). Training needs at least \(30 \times 65{,}536 \approx 2.0\) million sample vectors.

    With \(n_\text{probe} = 64\), a query scans \(64 / 65{,}536 = 0.098\%\) of the data, about 97,656 vectors, plus 65,536 centroid comparisons. Total work by formula (151.5): \(1.25 \times 10^8\) multiply-adds instead of \(7.68 \times 10^{10}\), about 613 times less. Memory does not shrink: IVF-Flat still stores every full vector (307.2 GB), plus an 8-byte id per vector.

    Algorithm 1: IVF index (train, add, search)
    1. train(sample \(S\)): \(\{\mathbf{c}_j\} \leftarrow\) k-means\((S, n_\text{list})\) // 30 to 256 sample vectors per centroid
    2. add(\(\mathbf{x}_i\), id \(i\)): \(j \leftarrow \argmax_j s(\mathbf{x}_i, \mathbf{c}_j)\); append \((i, \mathbf{x}_i)\) to list \(L_j\)
    3. search(\(\mathbf{q}, k, n_\text{probe}\)):
    4. \(P \leftarrow\) the \(n_\text{probe}\) centroids with the largest \(s(\mathbf{q}, \mathbf{c}_j)\) // \(n_\text{list} \cdot d\) work
    5. \(H \leftarrow\) empty top-\(k\) heap
    6. for \(j \in P\), for \((i, \mathbf{x}) \in L_j\): push \((s(\mathbf{q}, \mathbf{x}), i)\) into \(H\), keep only the best \(k\)
    7. return the ids in \(H\), best first

    PQ: store each vector in a few bytes

    IVF reduces the work but not the memory. Product quantization (Jégou et al., 2011) reduces the memory. The idea: split each vector into \(M\) short sub-vectors of \(d/M\) numbers. For each of the \(M\) positions, learn a small codebook of \(K\) centroids with k-means (usually \(K = 256\)). Replace each sub-vector by the index of its nearest centroid. With \(K = 256\), each index fits in one byte:

    \[ \mathbf{x} \approx \big[\, \mathbf{c}^{1}_{i_1},\; \mathbf{c}^{2}_{i_2},\; \dots,\; \mathbf{c}^{M}_{i_M} \,\big], \qquad \text{bytes per vector} = \frac{M \log_2 K}{8} \tag{151.7} \]
    Read the symbols
    \(M\)
    number of sub-vectors (sub-spaces); each has \(d/M\) dimensions
    \(K\)
    centroids per codebook; \(K = 256\) gives 8 bits per sub-vector
    \(\mathbf{c}^{m}_{j}\)
    centroid number \(j\) of codebook \(m\)
    \(i_m\)
    the stored code: which centroid is closest to sub-vector \(m\)

    Why “product”? The \(M\) codebooks together describe \(K^M\) different vectors (with \(M = 96\) and \(K = 256\), that is \(256^{96}\)), but we only store and train \(M \times K\) small centroids. A single k-means with that many centroids would be impossible.

    Distances on codes: asymmetric distance computation

    At search time we do not decompress the database. The query stays exact (not quantized; this is why it is called asymmetric). For each sub-space \(m\), we compute the score of the query's sub-vector \(\mathbf{q}^m\) with all \(K\) centroids once, and store them in a table \(T_m\). Then the score of any stored vector is a sum of \(M\) table lookups:

    \[ \mathbf{q}^\top \mathbf{x} \;\approx\; \sum_{m=1}^{M} T_m[\, i_m \,], \qquad T_m[j] = (\mathbf{q}^{m})^\top \mathbf{c}^{m}_{j} \tag{151.8} \]

    Building the tables costs \(M \cdot K \cdot (d/M) = K d\) multiply-adds per query, the same as comparing with only \(K\) full vectors. After that, each database vector costs \(M\) lookups instead of \(d\) multiply-adds. For L2 distance it works the same way, with squared distances in the tables. FAISS also has a fast-scan variant with \(K = 16\) (4 bits), where the tables fit in CPU vector registers. [Certain]

    Worked example: ADC by hand, then at scale

    Tiny case: \(d = 4\), \(M = 2\), \(K = 2\). Codebook 1 has \(\mathbf{c}^1_0 = (1, 1)\) and \(\mathbf{c}^1_1 = (0, 2)\). Codebook 2 has \(\mathbf{c}^2_0 = (0, 1)\) and \(\mathbf{c}^2_1 = (1, 0)\). The stored vector \(\mathbf{x} = (0.8, 1.3, 0.9, 0.2)\) is encoded as codes \((0, 1)\): \((0.8, 1.3)\) is closest to \((1, 1)\), and \((0.9, 0.2)\) is closest to \((1, 0)\).

    Query \(\mathbf{q} = (1, 0, 0.5, 2)\). Tables: \(T_1 = [\,1 \cdot 1 + 0 \cdot 1,\; 0\,] = [1, 0]\) and \(T_2 = [\,0.5 \cdot 0 + 2 \cdot 1,\; 0.5 \cdot 1 + 2 \cdot 0\,] = [2, 0.5]\). Score: \(T_1[0] + T_2[1] = 1 + 0.5 = 1.5\). The exact score is \(\mathbf{q}^\top\mathbf{x} = 0.8 + 0 + 0.45 + 0.4 = 1.65\). The error comes from the compression.

    At scale: \(d = 768\) with \(M = 96\) gives 96 bytes per vector instead of 3,072 (FP32), a factor of 32. For \(10^8\) vectors: 9.6 GB of codes plus 0.8 GB of 8-byte ids, small enough for one GPU or one server. The tables have \(96 \times 256 = 24{,}576\) entries and cost \(256 \times 768 = 196{,}608\) multiply-adds to build.

    IVF-PQ and re-ranking

    The standard billion-scale index combines both ideas: IVF-PQ. IVF chooses the lists. Inside the lists, vectors are stored as PQ codes. Usually PQ encodes the residual \(\mathbf{x} - \mathbf{c}_j\) (the vector minus its IVF centroid), which is smaller and easier to compress than \(\mathbf{x}\) itself. [Certain]

    PQ scores are approximate, so the top-10 by PQ score are often not the true top-10. The fix is re-ranking (FAISS calls it refine): take the top \(k' \gg k\) by PQ score (for example \(k' = 10k\)), load their full vectors (from RAM, SSD, or a cheaper FP16 copy), compute exact scores, and keep the best \(k\). Compression decides which candidates you keep; the exact vectors decide the final order.

    Algorithm 2: IVF-PQ search with re-ranking
    1. input: query \(\mathbf{q}\), \(k\), \(n_\text{probe}\), re-rank depth \(k'\)
    2. \(P \leftarrow\) the \(n_\text{probe}\) nearest IVF centroids to \(\mathbf{q}\)
    3. for \(j \in P\):
    4. \(\mathbf{r} \leftarrow \mathbf{q} - \mathbf{c}_j\) // for L2 with residual encoding
    5. build tables \(T_m[\cdot]\) from \(\mathbf{r}\), \(m = 1..M\) // formula (151.8)
    6. for each code \((i, i_1..i_M)\) in list \(L_j\): score \(\leftarrow \sum_m T_m[i_m]\); keep the best \(k'\)
    7. load full vectors of the \(k'\) candidates; compute exact scores // re-rank
    8. return the best \(k\) by exact score

    HNSW: walk a graph toward the query

    IVF and PQ change what we compare. Graph methods change the order: start somewhere and repeatedly move to a neighbor that is closer to the query. If every vector is linked to its near neighbors, this greedy walk reaches the right area quickly. A graph where a few hops connect any two nodes, like a social network, is a small world.

    HNSW (Malkov and Yashunin) adds layers, like a highway system. Every vector is in layer 0. A random few are also in layer 1, fewer in layer 2, and so on. Upper layers have few nodes and long links, so a search can cross the space in a few hops. Lower layers are dense and give the fine detail. When a vector is inserted, its top layer is drawn at random:

    \[ \ell = \big\lfloor -\ln(u) \cdot m_L \big\rfloor, \quad u \sim \mathcal{U}(0, 1), \quad m_L = \frac{1}{\ln M} \;\Rightarrow\; P(\ell \ge L) = M^{-L} \tag{151.9} \]
    Read the symbols
    \(\ell\)
    the highest layer this vector appears in
    \(M\)
    the number of links each node keeps per layer (layer 0 usually keeps \(2M\))
    \(m_L\)
    the level multiplier; \(1/\ln M\) is the choice suggested in the paper
    \(P(\ell \ge L)\)
    with \(M = 32\): 1 node in 32 reaches layer 1, 1 in 1,024 reaches layer 2

    So each layer has about \(M\) times fewer nodes than the one below, and the number of layers grows like \(\log_M N\): about 5.3 for \(N = 10^8\) and \(M = 32\). Search cost grows roughly with \(\log N\) for well-behaved data. [Likely]

    Search: start at the single entry node in the top layer. In each upper layer, move greedily to the closest neighbor until no neighbor is closer; then go down one layer and continue from there. In layer 0, run a beam search that keeps the best \(ef\) nodes found so far (\(ef\) = efSearch), not just one. A larger \(ef\) explores more and finds more true neighbors. Insertion is a search too: find the \(ef_\text{construction}\) nearest nodes of the new vector in each of its layers, and link it to \(M\) of them (with a heuristic that prefers neighbors in different directions). Step through a search in Figure 3.

    HNSW has very good recall at low latency, which made it the default index in many vector databases. [Likely] Its costs: the graph must live in RAM, with random memory access; links add memory; building is slow; and deleting nodes is hard, because removing a node can cut paths through the graph. FAISS gives the memory of an HNSW index with full vectors as

    \[ \text{bytes per vector} = 4d + 8M \tag{151.10} \]

    (\(4d\) for the FP32 vector, and \(2M\) links of 4 bytes each in layer 0; upper layers add little). [Certain] The FAISS guidelines suggest \(4 \le M \le 64\): larger \(M\) is more accurate but uses more memory. HNSW can also store compressed vectors (for example HNSW32,PQ64 or HNSW32,SQ8) to save memory.

    Graphs also scale beyond RAM. DiskANN keeps a graph and full vectors on SSD and only PQ codes in RAM, so one machine can serve a billion vectors. CAGRA builds and searches graphs on GPUs. ScaNN from Google uses partitioning with an improved (anisotropic) quantization. [Certain]

    Memory and speed math

    Now put the pieces together. For any design, compute two numbers first: bytes per vector (does it fit?) and bytes or vectors touched per query (how fast can it be?). Figure 4 does this for each index family.

    Some rules of thumb follow from these numbers. [Likely]

    • Up to a few million vectors: Flat (exact) or HNSW. Memory is not a problem.
    • Tens to hundreds of millions, enough RAM: HNSW with full or 8-bit vectors, or IVF with SQ8. Fast and high recall.
    • Hundreds of millions to billions, or GPU: IVF-PQ with re-ranking, or an SSD graph like DiskANN.
    • Always: reduce \(d\) if the embedding model allows it (Matryoshka embeddings, session 150), and use FP16 or INT8 where recall allows. Halving \(d\) halves every number in Figure 4. Scalar quantization (SQ8: one byte per number, with a per-dimension scale) is the same idea as weight quantization in LLMs (session 103).

    The recall versus latency trade-off

    Every ANN index has a knob that trades speed for recall: \(n_\text{probe}\) for IVF, \(ef\) (efSearch) for HNSW, the re-rank depth \(k'\) for PQ. Plotting recall@k against queries per second (or against work per query) for many knob values gives a curve. The best index for you is the one whose curve is highest at your latency budget. This is how the public ANN-Benchmarks compare libraries. [Certain]

    Figure 5 builds three indexes in your browser on 4,000 random vectors with 32 dimensions (clustered, normalized, like small embeddings) and measures recall@10 on 60 queries against exact search. The PQ here uses 8 sub-vectors with 16 centroids each, so each vector is stored in 4 bytes instead of 128 (32 times smaller).

    FAISS on CPU and GPU

    FAISS describes an index with a short factory string. Read it from left to right: optional transform, then the coarse structure, then the vector encoding. [Certain]

    Factory stringMeaningBytes per vector (\(d = 768\))
    Flatexact search, FP32 vectors3,072
    HNSW32,FlatHNSW graph, \(M = 32\), full vectors3,072 + 256 = 3,328
    IVF65536,FlatIVF with \(2^{16}\) lists, full vectors3,072 + 8 (id)
    IVF65536,SQ8IVF, one byte per number768 + 8
    IVF65536,PQ96IVF-PQ, 96 one-byte codes96 + 8
    OPQ96,IVF65536,PQ96first a learned rotation (OPQ) that makes PQ more accurate96 + 8
    IVF65536,PQ96,RFlatIVF-PQ, then exact re-rank (refine) with stored full vectors96 + 8 + 3,072

    CPU vs GPU. On GPU, FAISS supports Flat, IVF-Flat, IVF-SQ and IVF-PQ, and a fast k-selection (top-\(k\)) kernel, which was a key part of the original FAISS paper. HNSW is not supported on GPU; the FAISS guidelines list it as CPU-only. [Certain] Newer FAISS versions can use NVIDIA cuVS, which adds the CAGRA graph index on GPU. [Likely] GPUs shine for large query batches and for building indexes quickly (k-means on millions of vectors). For single queries at low traffic, a CPU HNSW is often cheaper. GPU memory (80 GB on an H100) limits the index size unless you shard over GPUs or use compression.

    The PyTorch code below builds exact search, IVF and PQ from scratch on 20,000 random 64-dimensional vectors, and measures recall@10 on 200 queries. It is deterministic; the printed numbers are from a real run (torch 2.8, CPU).

    import torch
torch.manual_seed(0)
N, d, nq, k = 20000, 64, 200, 10

# synthetic "embeddings": 200 topics plus noise, L2-normalized (cosine = inner product)
topics = torch.randn(200, d)
def sample(n):
    x = topics[torch.randint(0, 200, (n,))] + 1.5 * torch.randn(n, d)
    return torch.nn.functional.normalize(x, dim=1)
xb, xq = sample(N), sample(nq)

# 1) exact search: one matrix multiply plus top-k, formula (151.1)
def exact(q, x, k):
    return (q @ x.T).topk(k, dim=1).indices
gt = exact(xq, xb, k)

def recall_at_k(found, gt):                    # formula (151.4)
    return sum(len(set(f.tolist()) & set(g.tolist())) for f, g in zip(found, gt)) / gt.numel()

# 2) k-means (used by IVF and by PQ)
def kmeans(x, K, iters=20, seed=0):
    g = torch.Generator().manual_seed(seed)
    C = x[torch.randperm(len(x), generator=g)[:K]].clone()
    for _ in range(iters):
        a = torch.cdist(x, C).argmin(dim=1)
        for c in range(K):
            m = a == c
            if m.any():
                C[c] = x[m].mean(0)
    return C, torch.cdist(x, C).argmin(dim=1)

# 3) IVF: cluster the database, search only the nprobe closest lists
nlist = 256
C, assign = kmeans(xb, nlist)
lists = [torch.nonzero(assign == c).squeeze(1) for c in range(nlist)]
def ivf_search(q, nprobe):
    out, scanned = [], 0
    for qi in q:
        probe = (C @ qi).topk(nprobe).indices
        cand = torch.cat([lists[c] for c in probe.tolist()])
        scanned += len(cand)
        out.append(cand[(xb[cand] @ qi).topk(min(k, len(cand))).indices])
    return out, scanned / (len(q) * N)
for nprobe in [1, 4, 16, 64]:
    found, frac = ivf_search(xq, nprobe)
    print(f"IVF nprobe={nprobe:3d}  recall@10={recall_at_k(found, gt):.3f}  scanned={100*frac:.1f}%")

# 4) PQ: M sub-vectors, 256 centroids each -> M bytes per vector, formula (151.7)
M, ks = 8, 256
ds = d // M
books, codes = [], torch.empty(N, M, dtype=torch.uint8)
for m in range(M):
    Cm, am = kmeans(xb[:, m*ds:(m+1)*ds], ks, iters=15, seed=m)
    books.append(Cm); codes[:, m] = am.to(torch.uint8)
books = torch.stack(books)                       # (M, 256, ds)
def pq_search(q, kk):                          # ADC, formula (151.8)
    T = torch.einsum('qmd,mkd->qmk', q.view(-1, M, ds), books)   # tables (nq, M, 256)
    cidx = codes.long()                                          # (N, M)
    scores = sum(T[:, m, cidx[:, m]] for m in range(M))          # M lookups per vector
    return scores.topk(kk, dim=1).indices
pq_top = pq_search(xq, k)
print(f"PQ  M={M} ({M} bytes/vector vs {4*d})  recall@10={recall_at_k(pq_top, gt):.3f}")
cand = pq_search(xq, 100)                        # re-rank 100 PQ candidates with exact vectors
rr = torch.stack([c[(xb[c] @ qi).topk(k).indices] for c, qi in zip(cand, xq)])
print(f"PQ + exact re-rank of top 100  recall@10={recall_at_k(rr, gt):.3f}")

    Filters and updates

    Metadata filters

    Real queries come with conditions: “only documents this user may read”, “only videos from 2025”, “only products in stock”. The fraction of the database that passes the filter is the selectivity \(s\). There are three ways to combine a filter with ANN search:

    • Post-filtering: run ANN search for more results, then drop those that fail the filter. To still get \(k\) results you must ask for about
    \[ k' \approx \frac{k}{s} \tag{151.11} \]

    results. With \(k = 10\) and a filter that keeps 1% of the data, that is 1,000 results, and for a filter that keeps 0.01%, it is 100,000. Post-filtering is simple but breaks down for strict filters.

    • Pre-filtering: compute the set of allowed ids first, then search only among them. For very strict filters, just do exact search over the allowed vectors; it is small. FAISS supports this with an IDSelector passed in the search parameters, which skips vectors that are not allowed. [Certain]
    • Filter during the search: the graph walk or list scan skips disallowed vectors but still uses them for navigation. This is what most vector databases do. With HNSW it has a known failure: if few nodes pass the filter, the allowed nodes are poorly connected, and the search gets stuck. Databases detect strict filters and switch to exact search, or add extra links (Filtered-DiskANN builds the graph with labels in mind). [Likely]

    A practical alternative for a few big categories (for example, one per language or per customer) is partitioning: one index per category. Then the filter costs nothing.

    Adds, deletes and drift

    Adds. IVF and PQ indexes accept new vectors without retraining: each new vector goes into its nearest list. HNSW inserts with a search, which is slower but online. Deletes. IVF can remove an id from its list. HNSW usually marks a deleted node with a tombstone (it stays in the graph for navigation but is never returned), and rebuilds the graph when too many tombstones collect. [Likely] Drift. The IVF centroids and PQ codebooks were trained on old data. If new data looks different (a new product line, a new language), lists become unbalanced and recall drops. Monitor list sizes and recall on fresh queries, and retrain when needed. Model change. If you change the embedding model, every vector must be re-embedded and the whole index rebuilt: vectors from two models are not comparable. Plan for it; it is often the largest cost of a model upgrade.

    Watch outMany production systems keep a small exact “fresh” index for recent additions and merge its results with the large ANN index, then rebuild the large index in the background on a schedule. [Likely]

    Common mistakes

    • Mixing metrics. Building an L2 index on vectors that the model trained for cosine, without normalizing. Normalize both database and queries, then use inner product, or the ranking is wrong.
    • Measuring recall against the wrong thing. Index recall must be measured against exact search on the same vectors. Do not report human-label recall as if it measured the index, and do not skip the exact baseline.
    • Training IVF or PQ on too little or unrepresentative data. Use 30 to 256 vectors per centroid, drawn from the same distribution as the data (not the first million rows, which may be sorted by date or source).
    • Leaving \(n_\text{probe}\) or efSearch at the default. FAISS's default \(n_\text{probe}\) is 1, which often gives poor recall. [Certain] Always sweep the knob and pick the point on the curve that meets your recall target.
    • Using PQ scores as the final ranking. Compression reorders close candidates. Re-rank the top few hundred with full or FP16 vectors.
    • Post-filtering with strict filters. With 0.1% selectivity, a top-100 ANN search returns almost nothing that passes. Detect strict filters and pre-filter or switch to exact search.
    • Forgetting HNSW memory and build time. The links add \(8M\) bytes per vector, the graph needs RAM, and building 100 million nodes takes hours. [Likely] Deletes need tombstones and rebuilds.
    • Mixing embeddings from two model versions in one index. Distances between them are meaningless. Re-embed everything when the model changes.

    Interview questions

    What is the difference between exact kNN and ANN search, and how do you measure an ANN index?basic
    Exact kNN compares the query with every vector and returns the true top-\(k\); it costs \(N d\) per query. ANN uses a structure (clusters, compressed codes, or a graph) to look at far fewer vectors and returns most, not all, of the true top-\(k\). Measure it with recall@k against exact search on a set of held-out queries (formula 151.4), together with latency or queries per second, and memory. Report a curve over the speed knob, not one point.
    Why do cosine, inner product and L2 give the same ranking for normalized vectors?basic
    \(\lVert \mathbf{q} - \mathbf{x} \rVert^2 = \lVert\mathbf{q}\rVert^2 + \lVert\mathbf{x}\rVert^2 - 2\mathbf{q}^\top\mathbf{x}\). With unit vectors this is \(2 - 2\mathbf{q}^\top\mathbf{x}\), a decreasing function of the inner product, and cosine equals the inner product. So all three orderings are identical. Without normalization, inner product favors long vectors, and the choice matters.
    Explain IVF. How do you choose nlist and nprobe?core
    Train k-means with \(n_\text{list}\) centroids; assign each vector to the list of its nearest centroid; at query time compare with all centroids and scan the \(n_\text{probe}\) nearest lists. Cost is \(n_\text{list} d + n_\text{probe} (N/n_\text{list}) d\), minimized at \(n_\text{list} = \sqrt{n_\text{probe} N}\), so it grows like \(\sqrt N\). FAISS suggests \(4\sqrt N\) to \(16\sqrt N\) lists and 30 to 256 training points per centroid. Then sweep \(n_\text{probe}\) on held-out queries and pick the smallest value that meets the recall target, because queries near cell borders need several lists.
    How does product quantization compress vectors, and how are distances computed without decompressing?core
    Split each \(d\)-dimensional vector into \(M\) sub-vectors, learn a k-means codebook of \(K\) (often 256) centroids for each sub-space, and store the centroid index of each sub-vector: \(M\) bytes per vector. At query time, compute a table of the query sub-vector's score with each centroid (\(K d\) work in total), then the score of a stored vector is the sum of \(M\) lookups (asymmetric distance computation; the query stays exact). For 768 dimensions and \(M = 96\), that is 96 bytes instead of 3,072, 32 times smaller.
    Explain HNSW search. What do M, efConstruction and efSearch control?core
    HNSW is a stack of proximity graphs; each node's top layer is random with \(P(\ell \ge L) = M^{-L}\), so upper layers are sparse with long links. Search starts at the entry node in the top layer, moves greedily to closer neighbors, drops a layer when stuck, and in layer 0 runs a beam search keeping the best \(ef\) candidates. \(M\) is the number of links per node (memory and accuracy), efConstruction is the beam width during insertion (build time and graph quality), efSearch is the beam width at query time (the recall/latency knob). Memory with FP32 vectors is about \(4d + 8M\) bytes per vector.
    You have 1 billion 768-dimensional vectors. Size the index.advanced
    Flat FP32 is \(10^9 \times 3{,}072\) bytes = 3.07 TB: too big for one machine's RAM, and a query would read it all. HNSW with full vectors is even larger. IVF-PQ with \(M = 64\) is 64 GB of codes plus 8 GB of ids, which fits on one large server or a few GPUs. Use \(n_\text{list}\) around \(4\sqrt N\) to \(16\sqrt N\) (126k to 506k; for example \(2^{18}\)), train on a few tens of millions of samples, sweep \(n_\text{probe}\), and re-rank the top few hundred with FP16 vectors stored on SSD. Alternatively DiskANN: graph and vectors on SSD, PQ codes in RAM. Shard over machines for throughput and replicate for availability, merge per-shard top-\(k\).
    Why does PQ-only search have a recall ceiling, and how do you remove it?core
    PQ scores have errors that are often larger than the score gaps between close neighbors, so the order among the top candidates is partly random. Probing more lists adds candidates but does not fix their order, so recall flattens below 1.0 (Figure 5). Re-ranking takes the top \(k'\) (for example \(10k\) to \(100k\)) by PQ score and rescores them with exact or FP16 vectors. Other help: more bytes per vector, encoding IVF residuals, and a rotation such as OPQ that spreads information evenly across sub-spaces.
    How do you combine ANN search with a metadata filter?advanced
    Post-filter (search for \(k/s\) results and drop failures; fine for loose filters), pre-filter (build the allowed id set and search only it; for strict filters, exact search on the allowed set is cheap), or filter during the search (skip disallowed nodes while still navigating through them). HNSW with strict filters can get stuck because allowed nodes are poorly connected; systems switch to exact search below a selectivity threshold, or partition the index by the filter field when there are a few large categories.
    When would you use FAISS on GPU instead of CPU?advanced
    GPU wins for large query batches (throughput), for exact or IVF search over a few hundred million compressed vectors that fit in GPU memory, and for fast index building (k-means, encoding) and offline jobs like de-duplication. FAISS GPU supports Flat, IVF-Flat, IVF-SQ and IVF-PQ but not HNSW; newer versions add CAGRA through cuVS. CPU HNSW is often better for low-traffic, low-latency single queries, for very large indexes in RAM, and when you need online inserts and deletes.
    How do you handle updates and deletes in a vector index?core
    IVF and PQ accept adds without retraining, and IVF can remove ids from lists. HNSW inserts online with a search, and deletes are tombstones until a rebuild. Over time, data drift makes centroids and codebooks stale, so monitor list balance and recall on fresh queries and retrain on a schedule. A common pattern is a small exact index for fresh data, merged with the main index, plus periodic full rebuilds. A new embedding model always means re-embedding and rebuilding everything.
    Why do trees like k-d trees not work for 768-dimensional embeddings?basic
    A k-d tree splits on one coordinate at a time and prunes branches that cannot contain a closer point. In high dimensions, distances concentrate (the nearest and the farthest points are at similar distances), so almost no branch can be pruned and the search visits most of the data, no better than exact search. ANN methods accept approximate answers instead.

    Key takeaways

    • Exact search is one matrix multiply (151.1) with perfect recall, but at 100 million 768-dimensional vectors it needs 307.2 GB and reads all of it per query (151.3). Normalize and use inner product (151.2).
    • ANN quality is recall@k against exact search (151.4); always report it as a curve over the speed knob, with memory.
    • IVF scans only \(n_\text{probe}\) lists; cost grows like \(\sqrt{N}\) (151.5, 151.6). It cuts work, not memory.
    • PQ stores \(M\) bytes per vector (151.7) and scores with table lookups (151.8). It cuts memory 10 to 100 times, but needs re-ranking for high recall.
    • HNSW walks a layered graph (151.9); it gives high recall at low latency, costs \(4d + 8M\) bytes per vector (151.10), and is CPU-only in FAISS.
    • Filters: post-filter needs \(k/s\) results (151.11); strict filters need pre-filtering or exact search. Plan for adds, deletes, drift and full rebuilds.
