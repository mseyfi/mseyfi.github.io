    Dissect a modern open model

    A modern open model is a config.json file, a pile of weights and a technical report. This session shows a fixed method to take one apart: read the config, count the parameters exactly, compute FLOPs per token, KV cache per token and the memory to serve it, then explain every design choice in the report with what you learned in this course. We do it for Llama 3.1 8B, Qwen3, DeepSeek-V3, Gemma 3 and the vision tower of Qwen2.5-VL, and every count matches the real checkpoints.

    Time: 3 to 4 hours (reading 2 hours, exercises 1 to 2 hours)Level: Interview level (capstone)Before this: Counting parameters and FLOPs (session 25), attention variants and the KV cache (sessions 26 and 80), Mixture of Experts (session 29)

    What you will learn

    • Read a Hugging Face config.json and know what every important field means (layers, heads, KV heads, head size, experts, vocabulary, RoPE, window, vision tower)
    • Count the parameters of dense, MoE and MLA models exactly, and check the count against the checkpoint size
    • Compute FLOPs per token, including the attention term that grows with context, and find where attention overtakes the weights
    • Compute KV cache per token for GQA, MLA and sliding-window models, and the memory and number of GPUs needed to serve them
    • Count visual tokens and vision-tower FLOPs for a native-resolution VLM (Qwen2.5-VL) and a fixed-resolution one (Gemma 3)
    • Read a technical report and explain each design choice (GQA, QK-norm, MLA, fine-grained MoE, auxiliary-loss-free balancing, local and global attention, window attention in the ViT) with the problem it solves

    Why this matters

    Every new open model arrives as three things: a config.json file, a folder of weights, and a technical report. If you can read those three, you can answer the questions that matter in practice: how big is it really, how fast can it run, how much memory does it need to serve 50 users with long prompts, and why did its authors build it this way.

    This is the last step of the course before the capstone project. Almost every earlier session gave you one tool: counting parameters and FLOPs (session 25), GQA and MLA (session 26), Mixture of Experts (session 29), RoPE and its scaling (session 14), the KV cache (session 80), number formats (session 105), and VLM vision towers (session 182). Here we use all of them at once, on real models, and we check every count against the real checkpoint files.

    Interview tipCommon questions: “Walk me through the architecture of Llama 3 / DeepSeek-V3.” “How much KV cache does a 128K-token request need?” “How many H100s do you need to serve this model?” “Why does DeepSeek use MLA and Qwen3 use GQA?” A candidate who opens the config and computes the answer on a whiteboard stands out. This session trains exactly that.

    We dissect five models that cover the main design families of 2024–2025 [Certain]:

    • Llama 3.1 8B: the plain dense baseline (GQA, SwiGLU, RoPE).
    • Qwen3-8B and Qwen3-235B-A22B: one family, dense and Mixture-of-Experts, with QK-norm.
    • DeepSeek-V3: MoE with 256 small experts plus Multi-head Latent Attention (MLA), the most memory-efficient KV cache here.
    • Gemma 3 27B: local (sliding-window) and global attention layers, plus a SigLIP vision encoder.
    • Qwen2.5-VL-7B: a vision-language model with a native-resolution ViT, for the vision-tower part.

    The same method works for any newer model (Gemma 4, the next Qwen, the next DeepSeek). The last exercise gives you a fresh config to practice on.

    The method: config, count, cost, report

    A dissection has a fixed order. You first collect the shapes, then turn shapes into counts, then counts into costs, and only then read the report. Reading the report first is tempting, but then you only repeat the authors’ claims. Computing first lets you check them.

    AnalogyA car mechanic does not trust the advertisement. He opens the hood, reads the engine plate (the config), measures the parts (the counts), runs it on the test bench (FLOPs and memory), and only then reads the manual to understand why the engineers chose a turbo instead of a bigger engine (the report).
    Algorithm 1: dissect a model
    1. input: config.json, model.safetensors.index.json, the technical report
    2. Read the shapes: \(d\), \(L\), \(h\), \(h_{kv}\), \(d_h\), \(d_{ff}\), vocabulary \(V\), tied or not, experts \(E\), top-\(k\), expert size \(f\), shared experts, attention type (GQA, MLA, sliding window), RoPE base and scaling, context length, vision tower
    3. Count parameters per block with formulas (234.1)–(234.3); multiply by \(L\); add embeddings
    4. Check: the checkpoint’s total_size in bytes ÷ bytes per value must equal your count. If not, find the missing piece (a bias, a norm, a vision tower)
    5. Split into total and active parameters (MoE uses only top-\(k\) experts per token)
    6. KV cache per token with (234.4)–(234.6); FLOPs per token with (234.7)
    7. Memory to serve with (234.9) for your target context and number of users
    8. Read the report. For each design choice, write: what problem it solves, what it costs, and which number above shows it

    Step 2: count the parameters

    A decoder block has an attention part and an FFN part, plus small norm vectors. Write each projection as a matrix and add up the sizes. For GQA attention with \(h\) query heads, \(h_{kv}\) key-value heads and head size \(d_h\):

    \[ N_{\text{attn}} = \underbrace{2\,d\,h\,d_h}_{W_Q,\ W_O} + \underbrace{2\,d\,h_{kv}\,d_h}_{W_K,\ W_V} \;\big(+\,2 d_h \text{ for QK-norm}\big) \tag{234.1} \]

    For a SwiGLU FFN with inner size \(d_{ff}\) there are three matrices (gate, up, down). An MoE layer has \(E\) such experts, each with a small inner size \(f\), plus a router; a token uses only \(k\) of them (plus \(n_s\) shared experts, if any):

    \[ N_{\text{ffn}} = 3\,d\,d_{ff}, \qquad N_{\text{moe}}^{\text{total}} = (E + n_s)\, 3\,d\,f + d\,E, \qquad N_{\text{moe}}^{\text{active}} = (k + n_s)\, 3\,d\,f + d\,E \tag{234.2} \]

    The whole model is \(L\) blocks plus the embedding table, the output head (the same matrix if tied) and the final norm:

    \[ N = L\,\big(N_{\text{attn}} + N_{\text{ffn}} + n_{\text{norm}}\, d\big) + c\, V d + d, \qquad c = \begin{cases} 1 & \text{tied} \\ 2 & \text{untied} \end{cases} \tag{234.3} \]
    Read the symbols
    \(d\)
    hidden size, the width of the residual stream
    \(h, h_{kv}, d_h\)
    number of query heads, number of key-value heads, size of one head
    \(d_{ff}, f\)
    inner size of a dense FFN, inner size of one expert
    \(E, k, n_s\)
    number of routed experts, how many each token uses, number of shared experts (always used)
    \(n_{\text{norm}}\)
    norm vectors per block: 2 for Llama and Qwen, 4 for Gemma (norms before and after each sub-layer)
    \(V, c\)
    vocabulary size; 1 if input and output embeddings share one matrix, else 2
    Worked example: Qwen3-8B, to the last parameter

    Attention per layer: \(W_Q\) and \(W_O\) are \(4096 \times 4096\) each, \(W_K\) and \(W_V\) are \(4096 \times 1024\) each (8 heads × 128). With the two QK-norm vectors of size 128: \(2 \cdot 16{,}777{,}216 + 2 \cdot 4{,}194{,}304 + 256 = 41{,}943{,}296\).

    FFN per layer: \(3 \times 4096 \times 12{,}288 = 150{,}994{,}944\). Two RMSNorm vectors: 8,192. Block total: 192,946,432. Times 36 layers plus the final norm: 6,946,075,648. This is the “6.95B non-embedding parameters” on the model card [Certain].

    Embeddings: \(151{,}936 \times 4096 = 622{,}329{,}856\), twice because they are not tied. Total: 8,190,735,360.

    Check: the checkpoint index says total_size = 16,381,470,720 bytes. In BF16 (2 bytes) that is exactly 8,190,735,360 parameters. The count matches to the last digit [Certain].

    The same formulas give exact matches for every model in Figure 1: Llama 3.1 8B has 8,030,261,248 parameters, Qwen3-235B-A22B has 235,093,634,560, and Gemma 3 27B has 27,432,406,640 including its vision tower [Certain]. Note what Qwen3-8B tells us: with a 152K vocabulary, the two embedding matrices are 15% of the model. That is why small models (Qwen3-0.6B to 4B) tie their embeddings [Certain, from the report’s table].

    MoE: total versus active

    Qwen3-235B-A22B has 94 layers, each with 128 experts of size \(3 \times 4096 \times 1536 = 18{,}874{,}368\). A token uses 8 of them. Formula (234.2) gives 235.09B total and 22.19B active, which is the “A22B” in the name [Certain]. So each token pays for 9.4% of the weights in compute, but all 100% must sit in GPU memory. This one fact explains most of MoE serving: memory is set by total parameters, compute by active parameters.

    MLA: the attention that compresses itself

    DeepSeek-V3 does not store keys and values per head. It projects the hidden state down to a small latent vector \(\mathbf{c}^{KV}\) of size \(d_c = 512\), and stores that, plus one shared RoPE key of size \(d_r = 64\). Keys and values for all 128 heads are rebuilt from the latent by an up-projection. Queries are also compressed (to 1,536) to save training memory [Certain]. Per layer, the matrices are:

    MatrixShapeParameters

    query up \(W^{UQ}\) (128 heads × (128 + 64))1536 × 24,57637,748,736
    KV down \(W^{DKV}\) plus RoPE key7168 × (512 + 64)4,128,768
    KV up \(W^{UK}, W^{UV}\) (128 heads × (128 + 128))512 × 32,76816,777,216
    output \(W_O\)16,384 × 7168117,440,512

    Then add 3 dense layers (FFN 18,432), 58 MoE layers (256 routed + 1 shared expert of size 2,048, a router, and a 256-entry routing bias), and untied embeddings. Formula (234.3) gives 671,026,419,200 parameters, the 671B of the report, and 36.6B active per token without the input embedding (a lookup has no FLOPs) [Certain]. The Hugging Face checkpoint is 685B because it also stores the Multi-Token Prediction (MTP) module: 11.5B unique parameters plus a copy of the embedding and head [Certain].

    Step 3: KV cache per token

    During generation, every layer keeps the keys and values of all earlier tokens (the KV cache). Its size per token is often the number that decides how many users a GPU can serve. For standard attention or GQA, each layer stores \(h_{kv}\) keys and \(h_{kv}\) values of size \(d_h\):

    \[ m_{\text{KV}} = 2 \cdot L \cdot h_{kv} \cdot d_h \cdot b \quad \text{bytes per token} \tag{234.4} \]

    where \(b\) is bytes per value (2 for BF16, 1 for FP8). For MLA, each layer stores only the latent and the shared RoPE key, with no factor 2 and no heads:

    \[ m_{\text{KV}}^{\text{MLA}} = L \cdot (d_c + d_r) \cdot b \quad \text{bytes per token} \tag{234.5} \]

    For sliding-window attention, a local layer never keeps more than \(w\) tokens. With \(L_g\) global and \(L_l\) local layers, the cache for a context of \(T\) tokens is:

    \[ M_{\text{KV}}(T) = 2\, h_{kv}\, d_h\, b \,\big(L_g\, T + L_l \min(T, w)\big) \tag{234.6} \]
    Worked example: KV cache per token in BF16

    Llama 3.1 8B: \(2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) bytes = 128 KiB. Qwen3-8B: \(2 \cdot 36 \cdot 8 \cdot 128 \cdot 2\) = 144 KiB. Qwen3-235B-A22B: \(2 \cdot 94 \cdot 4 \cdot 128 \cdot 2\) = 188 KiB: a model 29 times bigger than Qwen3-8B needs only 31% more cache per token, because it has only 4 KV heads.

    DeepSeek-V3: \(61 \cdot (512 + 64) \cdot 2 = 70{,}272\) bytes = 68.6 KiB. If the same 128 heads cached full keys (192) and values (128), it would be \(61 \cdot 128 \cdot 320 \cdot 2 = 4{,}997{,}120\) bytes: 71 times more. That factor is the reason MLA exists.

    Gemma 3 27B: a global layer costs \(2 \cdot 16 \cdot 128 \cdot 2 = 8{,}192\) bytes per token. At \(T = 32{,}768\), formula (234.6) gives \(8192 \cdot (10 \cdot 32{,}768 + 52 \cdot 1024) = 3.12\) GB, against 16.6 GB if all 62 layers were global: 18.75%.

    (1 KiB = 1,024 bytes. Totals below are in GB = \(10^9\) bytes.)

    Step 4: FLOPs per token

    A forward pass costs about 2 FLOPs per weight that the token actually uses (one multiply, one add), plus attention, which grows with the context. For one new token at position \(T\), each layer computes scores against \(T\) keys and a weighted sum of \(T\) values:

    \[ C(T) \approx 2\,N_{\text{act}} + \sum_{\ell=1}^{L} 2\, h\, (d_{qk} + d_v)\, T_\ell, \qquad T_\ell = \begin{cases} T & \text{global layer} \\ \min(T, w) & \text{local layer} \end{cases} \tag{234.7} \]
    Read the symbols
    \(N_{\text{act}}\)
    active parameters used in matrix multiplies: everything except the input embedding (a lookup) and the idle experts
    \(d_{qk}, d_v\)
    size of a query-key head and of a value head (128 and 128 for most models; 192 and 128 for DeepSeek-V3)
    \(T_\ell\)
    how many tokens layer \(\ell\) attends to

    For a uniform model (all layers global, same head sizes) the attention term equals the weight term at the crossover context:

    \[ T^{*} = \frac{N_{\text{act}}}{L\, h\, (d_{qk} + d_v)} \tag{234.8} \]

    Llama 3.1 8B: \(N_{\text{act}} = 7.505\)B (8.03B minus the 0.525B input table), so \(T^* = 7.505 \times 10^9 / (32 \cdot 32 \cdot 256) \approx 28{,}630\) tokens. Beyond that, a decoding step spends more FLOPs on attention than on all the weights. For MoE models the crossover comes much earlier, because \(N_{\text{act}}\) is small compared with their many attention heads: about 14,000 tokens for both Qwen3-235B-A22B and DeepSeek-V3. Gemma 3’s local layers push its crossover past 300,000 tokens.

    Watch outFor DeepSeek-V3 we count attention in its “naive” form (\(d_{qk} = 192\), \(d_v = 128\)). Decode kernels often use the “absorbed” form, which works directly on the 576-wide latent: per layer \(2 \cdot 128 \cdot (576 + 512)\) FLOPs per cached token, 3.4 times more, in exchange for reading the tiny cache. MLA trades compute for memory traffic, which is the right trade during decoding.

    The same count, times 3 for the backward pass, gives the training cost \(C_{\text{train}} \approx 6\,N_{\text{act}}\,D\) for \(D\) training tokens:

    \[ C_{\text{train}} \approx 6\, N_{\text{act}}\, D \tag{234.9} \]

    DeepSeek-V3: \(6 \times 36.6 \times 10^9 \times 14.8 \times 10^{12} \approx 3.25 \times 10^{24}\) FLOPs. Llama 3 405B (dense, 15.6T tokens): \(3.79 \times 10^{25}\), close to the \(3.8 \times 10^{25}\) the Llama 3 report gives [Certain]. A 671B MoE model trained with about 12 times less compute than a 405B dense one: that is the economic argument for MoE in one line.

    Step 5: memory to serve

    To serve a model you need the weights (all of them, including idle experts), the KV cache of every running request, and some room for activations, CUDA workspace and fragmentation:

    \[ M_{\text{serve}} = N\, b_w + B\, T\, m_{\text{KV}} + M_{\text{other}}, \qquad n_{\text{GPU}} = \left\lceil \frac{M_{\text{serve}}}{u \cdot M_{\text{GPU}}} \right\rceil \tag{234.10} \]
    Read the symbols
    \(b_w\)
    bytes per weight: 2 (BF16), 1 (FP8), about 0.5 (INT4, plus small scales)
    \(B, T\)
    number of concurrent sequences and their length (prompt plus output)
    \(u\)
    the usable fraction of GPU memory; serving engines reserve about 90% by default [Likely]; we use \(u = 0.9\)
    Worked example: Qwen3-235B-A22B on H100s

    Weights in BF16: \(235.09 \times 10^9 \times 2 = 470.19\) GB. KV cache for 8 requests of 32,768 tokens: \(8 \times 32{,}768 \times 192{,}512 = 50.47\) GB. Total 520.65 GB. One H100 gives \(0.9 \times 80 = 72\) GB, so we need \(520.65 / 72 = 7.23\), rounded up to 8 GPUs, one full 8-GPU node.

    In FP8 the weights drop to 235 GB, and 4 GPUs are enough for the same load. Qwen3-8B in BF16 with 16 requests of 32K tokens: \(16.38 + 77.31 = 93.69\) GB: more than one H100, and 83% of it is KV cache. For small models with long contexts, the cache, not the weights, decides the hardware.

    Algorithm 2: plan the hardware to serve a model
    1. input: counts from Algorithm 1, target context \(T\), concurrent requests \(B\), GPU memory \(M_{\text{GPU}}\), formats \(b_w, b_{kv}\)
    2. \(W \leftarrow N \cdot b_w\) // total parameters, not active
    3. \(K \leftarrow B \cdot M_{\text{KV}}(T)\) at \(b_{kv}\) bytes // formula (234.4), (234.5) or (234.6)
    4. \(n \leftarrow \lceil (W + K) / (0.9\, M_{\text{GPU}}) \rceil\); round up to a tensor-parallel size (1, 2, 4, 8)
    5. if \(W \gt 0.9\, n\, M_{\text{GPU}}\) with room for almost no cache: lower \(b_w\) (FP8, INT4) or add GPUs
    6. if \(K\) dominates: quantize the KV cache, use prefix caching, or limit \(T\)
    7. check speed: decode time per step ≥ (bytes of active weights + bytes of KV read) / memory bandwidth
    8. return \(n\), the formats, and the maximum batch that still fits

    Step 6: the vision tower

    A VLM adds a vision encoder and a connector. You dissect them the same way, but the important number is different: how many tokens one image or one second of video becomes, because each visual token costs as much LLM compute and KV cache as a text token.

    Qwen2.5-VL-7B [Certain, config and report]: a 32-layer ViT, hidden size 1,280, 16 heads, patches of 14 × 14 pixels, RMSNorm and SwiGLU. Most layers use window attention over 112 × 112-pixel windows (8 × 8 patches); only 4 layers (indexes 7, 15, 23, 31) use full attention. Images keep their native size, rounded to a multiple of 28. A merger concatenates each 2 × 2 group of patches and maps it with a 2-layer MLP to the LLM width of 3,584. For video, two consecutive frames form one temporal patch. So:

    \[ n_{\text{img}} = \frac{H'}{28} \cdot \frac{W'}{28}, \qquad H' = 28 \cdot \operatorname{round}\!\left(\frac{H}{28}\right), \qquad n_{\text{video}} = \left\lceil \frac{F}{2} \right\rceil \cdot \frac{H'}{28} \cdot \frac{W'}{28} \tag{234.11} \]

    where \(F\) is the number of sampled frames. The vision tower has 632M parameters and the merger 45M; with the 7.62B LLM the checkpoint holds 8,292,166,656 parameters, again an exact match [Certain].

    Gemma 3 27B [Certain, config and report]: a 400M SigLIP encoder (27 layers, width 1,152, patch 14) that always sees a 896 × 896 square: \(64 \times 64 = 4{,}096\) patches, pooled to 256 tokens per image. Non-square or detailed images can be cut into several crops (“pan and scan”) at inference, 256 tokens each.

    Worked example: one 1280 × 720 frame

    Qwen2.5-VL: \(H' = 728\), \(W' = 1288\), so \(52 \times 92 = 4{,}784\) patches and \(26 \times 46 = 1{,}196\) tokens. The ViT spends about 6.6 TFLOPs on it (linear layers \(2 \times 630\text{M} \times 4{,}784\) plus attention), and the LLM prefill of 1,196 tokens costs another \(2 \times 7.07\text{B} \times 1{,}196 = 16.9\) TFLOPs. In the KV cache, one such frame takes \(1{,}196 \times 56\) KiB = 68.6 MB.

    Gemma 3: the frame is squashed to 896 × 896 and becomes 256 tokens, whatever its size. A minute of video at 2 frames per second and 448 × 448 is 15,360 tokens in Qwen2.5-VL. The fixed budget is cheap and predictable; the native resolution keeps small details such as text and far-away players.

    Two patterns repeat across all five models. First, every design fights the KV cache: GQA (Llama, Qwen), very few KV heads (Qwen3 MoE has 4), MLA (DeepSeek), sliding windows (Gemma). Second, every recent model adds something for training stability: QK-norm (Qwen3, Gemma 3), a dense architecture (Llama 3), FP8 with fine-grained scales (DeepSeek-V3). When you read the next report, look for these two first.

    Interview tipWhen asked “why X?”, answer in the shape “X solves problem P; it costs C; the number that shows it is Z.” Example: “MLA solves the KV-cache size of 128 heads; it costs extra up-projection compute during attention; it gives 68.6 KiB per token instead of about 5.0 MB.”

    The code: a config-driven calculator

    This script counts parameters and KV cache from a config dict, and first checks the formula against a real PyTorch module with the same structure. It runs on CPU in under a second.

    import torch, torch.nn as nn
torch.manual_seed(0)

def count_params(c):
    """Parameters of a Qwen3-style decoder (dense or MoE) from its config.json dict."""
    d, L, V = c["hidden_size"], c["num_hidden_layers"], c["vocab_size"]
    h, hkv, dh = c["num_attention_heads"], c["num_key_value_heads"], c["head_dim"]
    attn = 2 * d * h * dh + 2 * d * hkv * dh + 2 * dh          # formula (234.1), with QK-norm
    if c.get("num_experts"):                                    # MoE block, formula (234.2)
        E, k, f = c["num_experts"], c["num_experts_per_tok"], c["moe_intermediate_size"]
        ffn_total, ffn_active = E * 3 * d * f + d * E, k * 3 * d * f + d * E
    else:                                                       # dense SwiGLU
        ffn_total = ffn_active = 3 * d * c["intermediate_size"]
    emb = V * d * (1 if c["tie_word_embeddings"] else 2)
    total = L * (attn + ffn_total + 2 * d) + emb + d           # formula (234.3)
    active = L * (attn + ffn_active + 2 * d) + emb + d
    return total, active

def kv_bytes_per_token(c, bytes_per_value=2):                  # formula (234.4)
    return 2 * c["num_hidden_layers"] * c["num_key_value_heads"] * c["head_dim"] * bytes_per_value

class Block(nn.Module):
    def __init__(s, d, h, hkv, dh, ff):
        super().__init__()
        s.q, s.k = nn.Linear(d, h * dh, bias=False), nn.Linear(d, hkv * dh, bias=False)
        s.v, s.o = nn.Linear(d, hkv * dh, bias=False), nn.Linear(h * dh, d, bias=False)
        s.qn, s.kn = nn.RMSNorm(dh), nn.RMSNorm(dh)            # QK-norm, one gain per head dim
        s.gate, s.up = nn.Linear(d, ff, bias=False), nn.Linear(d, ff, bias=False)
        s.down = nn.Linear(ff, d, bias=False)
        s.n1, s.n2 = nn.RMSNorm(d), nn.RMSNorm(d)

    Common mistakes

    • Using active parameters for memory. A 235B-A22B model needs memory for 235B weights. Active parameters set compute, not memory.
    • Using total parameters for FLOPs. The opposite mistake: an MoE token costs \(2 N_{\text{act}}\), not \(2N\).
    • Using \(h\) instead of \(h_{kv}\) in the KV cache. For Qwen3-235B this overestimates the cache 16 times.
    • Applying the GQA formula to MLA or sliding-window models. DeepSeek-V3 has num_key_value_heads: 128 in its config, but it caches a 576-wide latent. Gemma 3’s local layers stop at 1,024 tokens. Always check the attention type.
    • Trusting max_position_embeddings as the context length. Qwen3 says 40,960 but is 32K native and 128K with YaRN; read the model card.
    • Forgetting the vision tower and the MTP module. They are in the checkpoint and in GPU memory. Your count will not match total_size until you add them.
    • Counting tied embeddings twice. Gemma 3’s 262K-entry table is stored once and used twice.
    • Ignoring visual tokens in VLM serving. One 720p frame in Qwen2.5-VL is about 1,200 tokens: a 10-image prompt is a long-context request.

    Interview questions

    Given a config.json, how do you compute the parameter count? How do you check it?basic
    Per block: attention \(2dhd_h + 2dh_{kv}d_h\) (plus QK-norm vectors and biases if present), FFN \(3dd_{ff}\) for SwiGLU (or experts plus router for MoE), plus norm vectors. Multiply by \(L\), add \(Vd\) once or twice depending on tie_word_embeddings, plus the final norm. Check by dividing total_size in model.safetensors.index.json by the bytes per value. For Qwen3-8B both give 8,190,735,360.
    How much KV cache does Llama 3.1 8B need for one 128K-token request?basic
    Per token \(2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) bytes (128 KiB). Times 131,072 tokens: 17.2 GB in BF16, 8.6 GB in FP8. That is about the same as the 16 GB of BF16 weights, so one long request doubles the memory needed.
    What does “235B-A22B” mean, and what does each number decide?core
    235B total parameters, 22B active per token (8 of 128 experts in each of 94 layers, plus attention and embeddings). The total decides memory: 470 GB in BF16. The active count decides compute per token: about \(2 \times 21.6\)B FLOPs for the weights. MoE gives the quality of a large model at the per-token compute of a small one, but not at its memory.
    Explain MLA and compute how much it saves for DeepSeek-V3.core
    MLA projects the hidden state down to a 512-dimensional latent and caches only that plus a 64-dimensional shared RoPE key; per-head keys and values are rebuilt by an up-projection (which can be folded into the query and output projections at decode time). Cache per token: \(61 \cdot 576 \cdot 2 = 70{,}272\) bytes. Full MHA with the same 128 heads (keys 192, values 128) would cache \(61 \cdot 128 \cdot 320 \cdot 2 = 4{,}997{,}120\) bytes, 71 times more. The decoupled RoPE key is needed because RoPE rotates by position and would break the folding of the up-projection.
    Gemma 3 uses 5 local layers per global layer with a 1,024 window. What does that buy at 32K context?core
    With 10 global and 52 local layers, the cache is \(8192 \cdot (10T + 52 \min(T, 1024))\) bytes. At \(T = 32{,}768\): 3.12 GB versus 16.6 GB if all layers were global, 18.75%. The cost: local layers cannot look further than 1,024 tokens, so long-range information must flow through the 10 global layers. The report keeps a 1M RoPE base on global layers and 10k on local ones.
    At what context length does attention cost more FLOPs than the weights for Llama 3.1 8B?core
    Weights: \(2N_{\text{act}} = 2 \times 7.505\)B = 15.0 GFLOPs per token. Attention: \(L \cdot 2h(d_{qk} + d_v)T = 32 \cdot 2 \cdot 32 \cdot 256 \cdot T\). Equal at \(T^* = 7.505 \times 10^9 / (32 \cdot 32 \cdot 256) \approx 28{,}600\). For MoE models with many heads the crossover is much earlier: about 14,000 for Qwen3-235B-A22B and DeepSeek-V3.
    How many H100s do you need to serve Qwen3-235B-A22B in BF16 for 8 users with 32K contexts?core
    Weights 470.19 GB, KV cache \(8 \times 32{,}768 \times 192{,}512\) bytes = 50.47 GB, total 520.65 GB. At 72 GB usable per H100, 7.23 GPUs, so 8 (one node, tensor parallel 8). With FP8 weights, 235 + 50 = 285 GB fits in 4 GPUs. Then check speed: decode reads the 22B active weights and the cache every step, so bandwidth sets tokens per second.
    Why did Qwen3 add QK-norm and Gemma 3 replace soft-capping with QK-norm?advanced
    Attention logits are dot products of queries and keys; if their norms grow during training, logits become huge, softmax saturates and the loss spikes. QK-norm normalizes each query and key head vector (RMSNorm with a learned gain) before the dot product, which bounds the logits. Soft-capping (\(c \tanh(x/c)\)) also bounds them, but it is an extra element-wise operation on the full score matrix and does not fit well with fused attention kernels [Likely]. QK-norm costs only \(2 d_h\) parameters per layer.
    How did DeepSeek-V3 balance its experts without a big auxiliary loss?advanced
    Each expert has a bias that is added to its affinity score only when choosing the top-8 experts, not when weighting their outputs. After each step, the bias goes down for overloaded experts and up for underloaded ones. So balance is enforced by routing, not by a gradient that fights the language-modeling loss. A very small sequence-wise balance loss remains to avoid extreme imbalance within one sequence. Routing is also limited to 4 nodes per token to bound communication.
    A 1080p image goes into Qwen2.5-VL-7B and into Gemma 3 27B. Compare the token counts and explain the trade-off.advanced
    Qwen2.5-VL rounds to 1092 × 1932, so \(39 \times 69 = 2{,}691\) tokens. Gemma 3 resizes to 896 × 896 and outputs 256 tokens (more with pan and scan). Qwen keeps fine detail (small text, distant objects) and native aspect ratio, at about 10 times the LLM cost and KV cache. Gemma has a fixed, cheap budget but loses detail on large or very wide images, which is why pan and scan exists.
    DeepSeek-V3 reports 2.788M H800 GPU hours. Is that consistent with its size?advanced
    Training compute \(\approx 6 \times 36.6\text{B} \times 14.8\text{T} = 3.25 \times 10^{24}\) FLOPs. Divided by \(2.788 \times 10^6 \times 3600\) GPU-seconds, that is about 324 TFLOP/s per GPU. That is plausible for FP8 training on H800s with good utilization. The GPU hours include context extension and post-training, so the pretraining rate is a bit higher. This sanity check is what interviewers want: the claim is consistent with \(6ND\).

    Key takeaways

    • Dissect in a fixed order: config, counts, costs, report. Compute first, then read the claims and check them.
    • Formulas (234.1)–(234.3) give the exact parameter count of real models; the checkpoint’s total_size confirms it to the last parameter.
    • Memory is set by total parameters; compute by active parameters (234.7). MoE models such as Qwen3-235B-A22B (9.4% active) and DeepSeek-V3 (5.5% active) separate the two.
    • KV cache per token (234.4)–(234.6): 128 KiB (Llama 3.1 8B), 188 KiB (Qwen3-235B), 68.6 KiB (DeepSeek-V3, MLA); Gemma 3’s windows cut the cache to 18.75% at 32K.
    • Serving memory (234.10) for small models with long contexts is dominated by the KV cache; for large MoE models by the weights.
    • A VLM’s cost is set by visual tokens (234.11): Qwen2.5-VL grows with image area, Gemma 3 is fixed at 256 per crop.
    • Every modern design fights the KV cache and adds a stability fix (QK-norm, dense architecture, FP8 with fine scales).
